- 检测主链路 ✅：真实 MySQL 8.0.28（3307 在线）9/9 PASS（含 time/stacked）；真实 PG 18.3（PGlite）拟真靶场 8/8 PASS（含 JSON body、需登录、二阶）；CLI `--dbs` 与引擎一致。
- 拖库 ✅/❌ 分库：PG 93 请求取全表正确；**MySQL 拖库行数据错位**（users 真实 5 行 → 落 1 行，且第 2 行 email 串进第 1 行 username），同为 dumpRowLimit=10。定位在 MySQL 路径行切分。

- 接管（file read/write、UDF、os-shell、注册表）⚠️：全部 mock 单测，零真实 DBMS 验证；EXPLOIT_ENABLED 默认关。
- 默认跨库拖库：把同实例 netsec 库一并拖出 → 授权面风险（scopeGuard 只管 host 不管 schema）。

### 关键环境坑（本机）
- **系统代理污染本地扫描**：`HTTP_PROXY/HTTPS_PROXY=127.0.0.1:60124`、`NO_PROXY` 为空 → 引擎连 127.0.0.1 也走代理；代理对 POST 失败时该点记「已检测 0 漏洞」→ 二阶场景假阴性。
  实测对照：`node e2e/detection-runner/run.js` = 18 PASS/1 FAIL（second_order_store 1 请求 0 检出）；清代理后 `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy NO_PROXY=127.0.0.1,localhost node e2e/detection-runner/run.js` = **19 PASS/0 FAIL**。
  → **本机跑任何 e2e 回归/本地靶场扫描前必须先清代理环境变量**，否则结论不可信。
- 连续 5xx 时 `scanValidityGuard` 生效（verdict=inconclusive / reliable=false），但零星网络失败不触发 → 仍是假阴性口子。
- MySQL 靶场：端口 3307（3306 被占），root/root，库 sqli_lab；`createMysqlLabApp(pool)` **必须传 mysql2 pool**，否则全部 500。

### F2 MySQL 拖库（P0）✅ 挖出 3 个连带缺陷
- 行分隔符缺失（GROUP_CONCAT 默认 ',' 连行）→ 显式 SEPARATOR
- **真 MySQL 8.0.28 的 SEPARATOR 只收字面量**：`SEPARATOR CHAR(30)` = 1064 → 用 0x1E/0x0A
- **分页作用于聚合结果（恒 1 行）**：第 2 页起恒空、第 1 页=整表聚合再被 group_concat_max_len 截断 → 全方言分页下推进子查询 `FROM (SELECT cols FROM t LIMIT.. OFFSET..) __p`
- CONCAT_WS 跳过 NULL 参数 → 列位左移 → escColsNN/escColsNNJoin/nullSafeQuoteCol（IFNULL/COALESCE/ISNULL/NVL 按方言）
- 新文件：`server/tests/dumpRowSplit.sqlshape.test.js`（7 条形状锁死）、`e2e/real-mysql-lab/dump-correctness.e2e.mjs`（真库闭环 8/8，无 MySQL 自动 SKIP）
- 验收：真 MySQL 拖库 users 5 行/audit_logs 8 行逐行正确；exploiter.test PG 断言同步更新（COALESCE+子查询）
