## 一、收口：批量编排的故障隔离

竞品坐标（2026-10-02 核实）：

- **ghauri**：`-m BULKFILE` 标注 experimental；第三方评测原话
  "The bulk scanning functionality lacks sophisticated rate limiting or **failure isolation**.
  One unresponsive target can **stall the entire queue**, and there's **no built-in reporting**
  to aggregate results across multiple hosts."
- **sqlmap 2.0(WIP)**：CHANGELOG 已列 **OpenAPI 目标生成**、JSON 报告、WAF 自动绕过等。

本批落地（语义三条）：

1. **故障隔离**：单个目标抛错只进 `failures`，其余照常跑完；已跑完的报告照常落盘。
2. **摘要点名**：失败目标逐个打印 URL + 原因（只报数字 = 把"哪个没扫"变成悬案）。
3. **退出码三分**：有高危 2 / **全批失败 1** / 其余 0 —— "扫了但没高危"与"一个都没扫成"必须可分。

**缺陷注入 4/4 杀**（scanRunner 1 + batchPool 3），注入前 `cp`、还原用备份 + `cmp`。

## 二、竞品合并：`-m` 支持请求集合（对标 sqlmap 2.0 的 OpenAPI 目标生成）

三条既有事实凑出的一个缺口：

- `-r` 能吃集合（Burp XML / HAR / Postman / OpenAPI）但**只取第 1 条**，其余打一句
  「要逐个测请拆分文件后分别用 -r」；
- `-m` 能吃多目标但**只认一行一个 URL 的纯文本** ⇒ 真实接口清单全被当成非法 URL 扔掉；
- 批量池刚补齐并发与故障隔离，正缺"目标从哪来"。

⇒ 新增 `server/bin/cli/batchTargets.js`：集合 → N 个目标 → 批量池。

### 真机抓到的缺陷（不是推理）

```
[1/1] http://127.0.0.1:PORT/form → 失败：Unexpected token 'a', "name=alice" is not valid JSON
```

`args.body` 的消费侧是 `JSON.parse`，而 HAR 里的 POST body 是 urlencoded。
留到扫描期才发现 ⇒ **整条目标崩**（不是"少测一个参数"，是这个目标根本没扫）。
修法：把 body 的 JSON 化**前移到展开期**（复用 args.js 既有的 `bodyToJsonString`）。

### 三类"跳过并点名"而不是硬扫

| 形态 | 为什么跳 |
|---|---|
| 非 http(s) 协议 | 解析器走「原始报文」往返（只留 pathname+search+Host）⇒ `ftp://h/3` 出来是 `http://h/3`，**目标被静默改了** |
| `multipart/form-data` | JSON 化会把整份 body 塌成一个垃圾键（TODO §O 有完整记录） |
| 无法转 JSON 的 body | 带着空 body 扫 POST 端点 = 0 注入点 = 根本没测 |

判据的取舍：**扫出来的会是一个与抓包不同的目标** —— 那才是假阴性之源，所以宁可跳过并说清楚。
