### 1.2 API 速率限制缺失（P0 · 安全漏洞）

**现象**：[server/index.js](file:///D:/projects/sqli-scanner/server/index.js) 有完整的鉴权 + CORS + CSRF + CSP，但**没有任何速率限制**。

**风险**：持有 token 的客户端可以无限制并发调用 `/scan/start`（仅受并发槽约束）、`/exploit/sql`、`/report/ai`（外发 LLM 请求烧钱）等。

**修法**：
```js
// server/src/api/rateLimit.js
import { rateLimit } from 'express-rate-limit';
export const scanLimiter = rateLimit({
  windowMs: 60_000, max: 10,           // 每分钟最多 10 次新扫描
  standardHeaders: true, legacyHeaders: false,
  keyGenerator: (req) => req.headers['x-api-token']?.slice(0, 8) || req.ip,
});
export const exploitLimiter = rateLimit({ windowMs: 60_000, max: 30 });
export const aiLimiter = rateLimit({ windowMs: 3600_000, max: 20 }); // AI 报告按小时
```
在 `index.js` 的 `scanRoutes` / `exploitRoutes` / `reportAiRoutes` 挂载前插入。

**验收**：`server/tests/rateLimit.test.js` 至少 3 条用例：窗口内允许 / 超限 429 / 不同 token 独立计额。

### 1.4 服务端可观测性（P2 · 运维盲区）

**现状**：日志走 winston（写文件），但**没有 `/metrics`、没有 tracing、没有结构化请求日志**。

**建议**（按性价比排序）：

1. **`/api/metrics`（Prometheus 格式）** —— 暴露：
   - `scan_total{status}` / `scan_duration_seconds` 直方图
   - `http_requests_total{endpoint,status}` / `http_request_duration_seconds`
   - `engine_scan_concurrent_slots` 当前并发槽占用
   - `payload_template_total` / `tamper_plugin_total`（静态但有助于运维确认部署正确性）
2. **请求级 traceId** —— 在每个请求上生成 `crypto.randomUUID()`，注入 logger 上下文，让"一次扫描"的所有日志可被 grep
3. **慢请求日志** —— >5s 的 API 请求自动 warn 并记录 body 摘要（脱敏后）

**验收**：`curl /api/metrics` 返回合法 Prometheus 文本；扫描一次后 `scan_total{status="done"}` 递增。

### 1.5 台账无保留策略（P1 · TODO.md 已挂账）

**现状**：`data/ledger/` 无界增长，163 个真实台账已经积累。

**修法**：

**验收**：`server/tests/scanLedgerRetention.test.js`：构造 1001 条记录触发淘汰 → 最老的 1 条 404、其余可读。

## 3. 引擎内核（Scanner 核心能力）

### 3.1 payloadRegistry.js 167 KB 的懒加载（P1 · TODO §4 已记录）

**现状**：[payloadRegistry.js](file:///D:/projects/sqli-scanner/server/src/engine/payloadRegistry.js) 17.3 KB 主文件 + `payloads/registry.json` 681 条声明式注册表 + 1920 条模板，全量加载。

**问题**：
- 启动时同步加载所有方言的所有 payload，冷启动慢
- Tauri 桌面版首次扫描会卡顿

**修法**：
- 按 DBMS 分片：`payloads/registry.mysql.json` / `payloads/registry.pg.json` / ...
- 引擎启动时只加载「通用 + 未定库」payload
- 定库成功后（DBFingerprinter）异步加载该库的专属 payload
- 利用 `import()` + `with { type: 'json' }`（Node 22+ 已支持）

**验收**：启动时间从当前 X ms 降到 < 500 ms；内存占用降 30%+；判定测试 `npm run test:server` 不破。

### 3.2 真实 WAF 验证覆盖（P1 · TODO §1 已部分完成）

**已完成**：ModSecurity 真机对拍已进入 CI（`modsec-live` job），但样本仍只有 19 条。

**下一步**：
1. **提打穿链数**而不是继续加形态：当前分母 10、过 WAF 的链只有 1 条，是链侧能力问题
2. 加 Coraza 作为第二引擎对拍（Go 实现，与 ModSecurity 互补）
3. 把云 WAF（Cloudflare / AWS WAF / 阿里云盾）的指纹接入 `wafFingerprint` 实测

### 3.3 检测策略自适应（P2 · 智能化方向）

**现状**：检测通道全开（9 种），无智能剪枝。

**优化方向**：
- 根据 WAF 指纹结果**禁用必挂的通道**（如已识别 Cloudflare 就跳过某些必被拦的 union 形态）
- 根据响应时间特征**动态调整 time 盲注的 sleep 时长**（目标本身 200ms 时 sleep 5s 浪费）
- 根据历史扫描结果**推荐下次扫描的最优 level/risk**（需要台账数据回填）

## 9. 不推荐做的事（反向清单）

为避免「为优化而优化」，**明确不做**的事：

1. **不要重写引擎为 Rust/Go** —— 当前 Node.js 引擎已经过 2577 单测 + 全套 e2e 验证，重写成本远超收益。性能瓶颈在 IO 不在 CPU
2. **不要引入 GraphQL** —— 当前 REST API 已经稳定且配套完善（含 readme:check 自动核对），换 GraphQL 会破坏既有契约
3. **不要把测试覆盖率硬推到 95%+** —— 前端 func 72% 已经是「真逻辑覆盖完整」的健康状态，硬推等于测 JSX 样板
4. **不要给所有函数加 JSDoc** —— 关键公开 API 已有注释；内部函数的 JSDoc 是噪音
5. **不要追新框架** —— React 18 + MUI 5 + Vite 7 已经稳定；升 React 19 / 换 shadcn 等都是高成本低收益

## 10. 总结

sqli-scanner 已经是一个**功能完备、测试可信、安全合规**的 SQL 注入检测工具。当前的优化重点不是"加新功能"，而是：

1. **拆掉 5 个上帝文件** —— 直接决定下一个贡献者的上手成本
2. **统一前端样式体系** —— MUI 与 Tailwind 并存是最大的持续性税
3. **补上速率限制** —— 唯一的安全漏洞（即便有 token，也应该有配额）
4. **加可观测性** —— `/api/metrics` 让运维从「黑盒」变「白盒」

完成这四件事后，项目将从「个人/小团队的优秀工具」跨越到「可被企业采用的生产级产品」。
