## 0. 结论先行

**这不是一个"漏洞百出"的项目——恰恰相反，SSRF / CSRF / 越权利用 / 报告脱敏 / 日志打码这五条最容易出事的线，做的是同类自研工具里少见的扎实（有实证）。真正的问题集中在「默认部署形态」和「桌面端 sidecar」两处：一个是 Docker 单端口部署前端必白屏，一个是本机 4567 端口的无鉴权引擎可被劫持。**

| # | 问题 | 等级 | 可利用路径 | 现状 |
|---|---|---|---|---|
| S1 | Docker/单端口部署 CSP 误伤静态资源 → 前端白屏 | **高（交付阻断）** | `docker compose up` 后开 4567 即中 | 未修 |
| S2 | 默认无鉴权 API（Dockerfile `HOST=0.0.0.0` 且无 token；compose token 空） | **高** | 无 token 下 `/api/scan/start`、`/api/scan/:id/report` 全可达 | 未修 |
| S3 | 桌面端 sidecar 固定 `127.0.0.1:4567` 无 token + spawn `expect` panic | **中高** | 本机先占 4567 → 前端把目标 Cookie/拖库结果发给劫持者 | 未修 |
| S4 | sqlmap 桥接 `--eval`（Python 表达式）经 API 可达 | **中高** | `POST /sqlmap/start {config.evalCode}` | 设计使然，缺开关 |
| S5 | 会话落盘含 `point.originalValue`（可能是会话 Cookie 明文），卷持久化 | **中** | 读 `sessions/*.json` / compose volume | 未修 |
| S6 | SSE token 走 query + 前端 token 存 localStorage | **中** | 日志/代理/历史泄露；XSS 可窃 token | 未修 |
| S7 | 无全局速率限制（仅并发 8 / AI 3min / 利用 5s） | **中** | 批量 `/scan/start` 打外部目标＝扫描放大器 | 未修 |
| S8 | `X-Powered-By` 暴露；业务错误一律 200+code；`index.js` 全栈打印 | **低** | 指纹 / 监控失真 / 堆栈带入入参 | 部分补偿 |
| S9 | `SSRF_ALLOW_PRIVATE=1` 一键关闭内网防护，无启动警示 | **中** | 误配即引擎可打内网与云元数据 | 未修 |

**已做得好（点名，避免空泛）**：egressGuard SSRF + DNS 钉死（实测拒绝 169.254.169.254）、CSRF 三重守卫（实测 403/415）、利用能力默认关闭 + scope 红线（管到每一跳重定向）、报告 PoC 凭据脱敏、日志 Authorization/Cookie 打码、sessionStore 剥离 config 凭据 + 原子写、scanId 形状校验（防 CRLF/路径遍历）、容器非 root + tini、compose 绑定回环。

## 1. 架构、技术栈、数据流与信任边界

### 1.1 拓扑

```
[React18 + Vite + MUI] ──HTTP──▶ [Express 4 (单进程)]
        ▲                            │  ├─ /api/scan/*  (ScanManager: 9 检测器 / Extractor / Exploiter)
        │                            │  ├─ /api/sqlmap/* (spawn python sqlmap.py)
        │                            │  ├─ /api/exploit/* (默认 403)
        │                            │  └─ dist/ 静态托管（Docker 单端口）
        │                            ▼
[Tauri v2 壳]──sidecar spawn──▶ node engine (127.0.0.1:4567，固定端口)
                                     │
                                     ▼
                        目标站点（HTTP/S）＋ 可选代理（Burp/SOCKS）
```

- 三端同源：Web（Vite 5173 → API 4567）、Docker（Express 同端口托管 dist）、桌面（Tauri sidecar）。
- 存储：内存（scans Map）+ 文件会话 `server/sessions/*.json`（compose 挂 named volume）+ `logs/engine.log`（10MB×5 轮转）+ 系统临时目录（sqlmap outDir）。
- 外部依赖：PGlite（靶场/直连）、mysql2/pg/mssql/oracledb/sql.js（直连模式）、winston、undici/axios。

### 1.2 核心数据流

1. `POST /scan/start` → `sanitizeStart()`（白名单化 config）→ `assertSafeHttpTarget()`（DNS 解析 + 私网/元数据拒绝）→ `sm.start()` → Scheduler 并发调度 → 检测器 → Extractor（UNION/盲注/堆叠）→ `ReportGenerator` → SSE 推前端 / 报告导出。
2. 请求出口统一走 `httpClient`：`pinnedLookup`（DNS 钉死防 rebinding）+ `scopeGuard`（逐跳重定向越界拒发）+ Cookie Jar + 限速。
3. 利用流：`/api/exploit/*` 受 `EXPLOIT_ENABLED` + 独立限速 + scope 三重约束。

### 1.3 信任边界（关键）

| 边界 | 现状 | 评价 |
|---|---|---|
| 浏览器 → 引擎 | Origin/Sec-Fetch-Site/content-type 三重校验（实测有效） | 强 |
| 引擎 → 目标 | SSRF 硬底线 + DNS 钉死 + scope 授权圈 | 强 |
| 本机进程 → 引擎 | **无鉴权（token 默认空）** | **弱（S2/S3）** |
| 引擎 → 第三方 AI | opt-in（`AI_REPORT_API_BASE` 必填） | 中（合规待补） |
| 引擎 → 磁盘 | 会话/日志脱敏部分覆盖 | 中（S5） |
| 桌面壳 → sidecar | 固定端口、无 token、无完整性校验 | **弱（S3）** |

## 2. 攻击者视角：可利用面枚举

### 2.1 认证与会话

- **S2 默认无鉴权（高）**：`server/index.js:151` `if (API_TOKEN)`——没设 token 就整条中间件不安装。
  - Dockerfile：`HOST=0.0.0.0`、`SCAN_API_TOKEN` 未设（仅告警）；compose：`SCAN_API_TOKEN=` 空 + 只绑 127.0.0.1。
  - 实测（探针）：无 token `POST /api/scan/start` → 路由可达（本次被 SSRF 拒，非鉴权拦）：
    `{"code":1003,"message":"目标 IP 位于禁止访问的地址段（SSRF 防护）"}`。换公网目标即真发起扫描。
  - 影响：① 引擎被当"扫描放大器"打第三方（取证难、IP 被封、法律风险）；② 任意可读报告（含拖库数据、目标凭据）。
- **S6 token 传输/存储（中）**：`src/hooks/useEvents.ts:128` `token=<...>` 拼进 SSE URL；`localStorage.scanApiToken`。token 会出现在代理日志/浏览器历史，XSS 可直接窃。
- **无会话/无用户**：单机单用户模型，无登录、无审计归属（合规留痕缺口）。

### 2.2 授权与越权

- 水平/垂直越权：**不适用**（无多用户）。
- **越权"利用"防线到位**：`exploitRoutes.js:80` `EXPLOIT_ENABLED` 默认关；实测 `POST /api/exploit/sql` → `code 6005 利用能力未启用`。`authorized:true` 已降级为审计字段（不是安全边界）——正确。
- **scope 红线**：`scopeGuard` 注册在 `ScanManager.start`，逐跳重定向校验 + 利用路由复用（`assertExploitScope`）。这是同类工具罕见的能力，保持。

### 2.3 输入校验

- `sanitizeStart` 白名单化 config（KNOWN_CFG_KEYS + 双向守卫测试防漂移）；`numOpt/boolOpt` 显式挡 NaN 与字符串布尔（注释里记了真实踩坑）。质量高。
- `scanId` 形状校验（`scanRoutes.js:708`）：实测 `/api/scan/..%2f..%2fetc%2fpasswd/report` → `400 scanId 格式非法`。
- 残留：`query.token` 无长度上限（低危，仅日志噪声）；无 Host 头校验（API-only 服务，影响小）。

### 2.4 注入风险

- **自身 SQL 注入面**：直连模式（mysql2/pg/mssql/OracleDB）多数走参数化；payload 由模板拼装（业务需要），非外部输入直拼。
- **命令注入**：`sqlmapBridge.js:296` `spawn(py, [script, ...args], { env: 白名单 })` —— 数组传参、无 shell、env 最小化 → **无注入面**。
- **表达式执行（S4，中高）**：`sqlmapBridge.js:221-224` `config.evalCode` → `--eval <python 表达式>`。sqlmap 会在服务端执行它。`sqlmapRoutes.js:47` 只有 SSRF + 全局 token 门控，**没有独立开关**。装了 sqlmap 且无 token ⇒ HTTP 触发服务端代码执行（容器非 root 缓解）。历史日志 `server/logs/engine.log` 可见该能力被实际调用过（`--eval import hashlib; pwd=***`）。
- **模板/日志注入**：日志经 `redact()`（Authorization/Cookie 打码）；报告 HTML 有 `esc()`/`safeHref()`。

### 2.5 第三方依赖与配置

- 依赖：`npm audit --omit=dev`：服务端 3×moderate（全部来自 `express→qs` DoS，CVSS 5.3/3.7），前端 prod 0。`npm audit fix` 或升 Express 5 可解。
- 配置面（S9，中）：`SSRF_ALLOW_PRIVATE=1` / `SSRF_ALLOW_CIDRS=` 一键放开内网（合法用途：授权内网目标），但**启动无警示、文档未标红**；误配 = 引擎可打 169.254.169.254 与内网段（实测默认状态下该地址被拒，符合预期）。
- `AI_REPORT_API_BASE` opt-in 设计正确；一旦开启，脱敏报告发第三方（**需字段白名单审计**，见 §5 待补信息）。

### 2.6 密钥与敏感信息

- **S5（中）**：`sessionStore.js:89` 落盘 `points[].originalValue`——若注入点是 Cookie 参数，该值即会话 token 明文。`sessionStore` 只剥了 `config.auth/proxy/cookieParams/headerParams`（第 35 行），**没剥 point 原始值**。compose 把 `sessions` 挂 named volume（持久、可备份、可被其他容器挂载读取）。
- 日志：`logs/engine.log` 5.2MB，URL 经 `logSafeUrl` 打码，但参数名/路径仍保留；轮转 10MB×5（磁盘有界，合规需看留存期）。
- 前端：历史记录写 localStorage 前剥离敏感配置（`scanStore.ts:34/139`），已加固；token 明文存 localStorage 待改（S6）。
- 无硬编码密钥（key 全部走 env：AI key、API token）。

### 2.7 文件与接口处理

- 报告导出：`format` 白名单 + scanId 校验 + `esc/safeHref`（已修）；导出不落盘（仅 CLI `--out`）。
- 上传面：**几乎没有**（只接受 JSON，2MB 上限，非 JSON 415）——攻击面小，这点做得好。
- 静态托管：SPA fallback 对未匹配 API 返 404 JSON（防悬挂）。

### 2.8 日志与错误信息泄露

- `index.js:226` 兜底 `logger.error(...err.stack)` **打全栈**（与 `scanRoutes.js:767` 的"只留栈顶两帧"策略不一致）→ 异常路径可能把调用方入参（config/headers 片段）写进任何人可读的 `logs/engine.log`。建议对齐。
- 统一 200+code：业务错误不可被 `curl -f` 与网关识别（已有 `X-Error-Code` 头补偿，实测 `X-Error-Code: 1003`）。

### 2.9 部署与运维暴露面（本次重灾区）

- **S1（高，交付阻断）**：`index.js:142-147` 的安全头中间件对所有响应设置 `Content-Security-Policy: default-src 'none'`，**包括 `express.static` 与 SPA fallback**。实测：
  ```
  GET /            -> 200  content-security-policy: default-src 'none'; frame-ancestors 'none'
  GET /assets/*.js -> 200  content-security-policy: default-src 'none'（同源策略无 'self'）
  ```
  `dist/index.html` 引用 `<script type="module" src="/assets/...">` → 浏览器按 CSP 拒绝执行 ⇒ **Docker/单端口部署打开就是白屏**。Vite dev(5173) 与 Tauri（自有 CSP）不受影响，**所以本地开发永远测不出来**。
- **S2**：Dockerfile `HOST=0.0.0.0` 与 compose `HOST=127.0.0.1` 不一致；按 README 直接 `docker build && docker run -p 4567:4567` 即全网无鉴权暴露。
- **S3**：`src-tauri/src/lib.rs` sidecar 固定 4567、无 token；`sidecar.spawn().expect(...)` 与 `.expect("找不到 sidecar")` —— 端口被占/引擎缺失时 panic；更糟的是若恶意进程先监听 4567，WebView（CSP 允许该 origin）会把目标 Cookie、扫描配置、拖库结果发过去。
- 无 `/metrics`、无审计日志（谁在何时扫了谁）。

## 3. 工程质量

### 性能

- 并发：API 层 `MAX_SCAN_API_CONCURRENT=8`；扫描内 `concurrency` 默认 4；无全局速率限制（S7）。
- 单进程、无队列：崩溃/重启即在途扫描丢失（有会话断点续跑，但仅点级）。
- 内存：报告 + 事件日志全量在内存（`rec.logs` 有 LOG_CAP 上限；报告无上限，大表拖库 + PoC 缓存 `POC_CACHE` 无 TTL 淘汰）。
- 盲注提取有 `_extractCache` 复用（避免重复二分），设计到位。
- 提取链路已做分页下推与截断降级（上次修复，真库实测 users 5 行 / audit_logs 8 行逐行正确）。

### 可维护性

- 33,766 行（server/src + src），模块边界清晰（core / engine / api / services），注释密度高且**记录踩坑原因**（不是复述代码）。
- 大文件：`httpClient.js` 1255、`ScanManager.js` 1022、`payloadRegistry.js` 982、`scanRoutes.js` 957、`Exploiter.js` 942 —— 前两个建议继续拆。
- 测试：服务端 node:test（基线 1568 通过）+ 前端 vitest + e2e 真库靶场（MySQL/PGlite/CRS），**拒绝 mock 自证**的红线执行到位。
- 契约债：HTTP 200 + code 的错误形态（前端已依赖），灰度改造需前后端协同。

### 错误处理与可观测性

- 有全局兜底 + `unhandledRejection`/`uncaughtException`（不自杀、优雅收尾）——长驻引擎该有的样子。
- 可观测性偏弱：`/api/health` 仅 `{status,version}`；无 `/metrics`、无 scanId 贯穿日志、无请求级审计、无延迟/错误率指标。排障靠读 `engine.log`。
- `X-Error-Code` 头是好的过渡设计，下一步应灰度到真实 4xx/5xx。

### 顺带定位到的一处**既有 flaky**（与本次改动无关，未擅自修）
`server/tests/poc.evidence.test.js:415`「同报告多次导出逐字节一致」：单独复跑 3 次挂 1 次。

- 现象：`toMarkdown(report)` 连续两次的输出在跨毫秒边界时不等。
- 根因（代码定位）：`ReportGenerator.js:247` 的 `POC_CACHE` 是 **WeakMap，键为 vuln 对象引用**；
  而导出路径的 `_forExport` 会对报告做深拷贝，克隆后的 vuln 不是原键 → 缓存不命中 →
  每次重新生成 `poc.generatedAt`（`Date.now()`）→ 同一报告两次导出的时间戳不同。
- 建议修法（二选一，各约 0.5d）：① 缓存键改为稳定键 `scanId|pointId|payload|redactAuth`；
  ② 在 `_forExport` 之前先把 poc 原地挂到 `report.vulns` 上，克隆自然携带。
- 归类：工程质量（B6/测试稳定性），不是安全项；建议下一批与 B1 一起做。
