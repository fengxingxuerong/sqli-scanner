## 一、口径问题（比缺功能更要紧，客户验收第一眼就看这里）

### 1.1 README 声明但 CLI 不存在的参数（7 个）

`csrf-url`、`csrf-token`、`eval`、`identify-waf`、`skip-urlencode`、`keep-alive`、`null-connection`

README「CLI 55+ 参数」一节把它们列为已支持，但 `node bin/cli.js --help` 里查无此参。
实际核验：这些键**只出现在 `server/src/engine/sqlmapBridge.js`**——即"透传给外部 sqlmap 进程"的桥接参数，
**本项目自有引擎并不消费**。

| 处置 | 说明 |
|---|---|
| 推荐 | README 拆成两栏：**原生能力** / **sqlmap 桥接能力**，避免客户按 README 用原生引擎时踩空 |
| 备选 | 真正实现（`--identify-waf` 尤其简单：引擎已有 62 个 WAF 指纹，只缺 CLI 暴露） |

### 1.2「保留接口」= 收参数不生效（3 个）—— **已处置（2026-09-12）**

| 参数 | 处置 | 说明 |
|---|---|---|
| `--hex` | ✅ **已实现** | 新增 `engine/hexLiteral.js`，按方言生成十六进制字面量（MySQL/PostgreSQL/SQLite/SQL Server/MariaDB/TiDB），**未验证方言显式抛错**（不产出错误 SQL）。实测 MySQL：带/不带 `--hex` 搜索结果完全一致，只改传输形态 |
| `--no-escape` | ❌ **已移除** | 语义与本项目转义实现不同源，无法对齐；传入时显式告警并忽略 |
| `--union-char` | ❌ **已移除** | 需改 `marker.js` 的 `MARKER_RE` 与 tamper 标记保护链（P0-D3 高危区），风险 > 收益；传入时显式告警并忽略 |

**顺带修掉一个真 bug（比这三个参数更值钱）**：`scanHelpers.mergeExtracted` 是逐字段白名单合并，
有 `currentDb/users/counts`… 却**没有 `search`** → `--search` 的结果在合并层被丢弃，报告里恒为 `null`。
用户以为"搜不到"，实际是结果丢了（实测：直连提取层有数据、报告里为空）。`meta`（dumpUnconfirmed）同源丢失。
已修 `mergeExtracted` / `mergeExtractedForResume` / `hasData` 三处。

## 二、sqlmap 对标缺口（真功能缺失）

| # | 缺失项 | 现状 | 实战影响 | 优先级 |
|---|---|---|---|---|
| 2.1 | **`--common-tables` / `--common-columns`**（字典爆破表名/列名） | 引擎 **零实现**（grep 0 命中） | **最高**。当 `information_schema` 被 WAF 拦、权限不足、或目标不是 MySQL 时，这是唯一出路。本轮评测的 WAF 靶点正好拦了 `information_schema`——检出没问题，但**拖库走不通**，只能停在"确认注入" | P0 |

| 2.8 | 后渗透：`--os-shell` / `--os-pwn` / `--reg-read` / `--udf-inject` / `--priv-esc` | 部分仅桥接；引擎侧 README 自认未真机验证 | 定位问题：这是"要不要做完整 DBA 后渗透链"的产品决策，不是 bug | 决策项 |

## 三、实测中发现的能力缺口（有靶场证据）

### 3.1 编码参数（base64 / hex / 双重 URL 编码）

**证据**：靶点 `D14`（`id` 为 base64 编码的数字）最终靠 **error 通道偶然命中**——
并非引擎"解码参数后再注入"，而是报错恰好回显。真实 SPA 常把参数 base64 编码，
这类目标目前只能碰运气。

**建议**：参数值可被识别为 base64/hex 时，自动尝试「解码 → 注入 → 重新编码」链路；
至少在报告里标注"该参数疑似编码，未解码检测"。

### 3.2 OOB 带外通道未验证

引擎有 `oobReceiver` 与 `oob` 技术位，但**没有任何实测证据**（README 未给口径）。
这是无回显 + 强 WAF 场景的终极手段，价值高于后渗透。建议按 `fileRead` 的方式补真机验证，
并在 README 给出「已跑通 / 未验证」的诚实标注。

### 3.3 利用链验证缺口

README 自认：`fileWrite` / UDF / `os-shell` / 注册表**仅有 mock 单测**，属实验特性。
建议：要么补真机闭环（像 `fileRead` 那样），要么在能力矩阵里降级标注——**不要留在"声明可用"状态**。

### 3.4 二阶注入的开关数量 —— 【已更正：原结论有误】

**初版结论（错）**：曾写「要同时给 `--second-order` + `--allow-second-order-writes` + `--no-production-mode` 三个开关才生效」。

**消融测试后的实测事实**：

| 命令组合 | 结果 |
|---|---|
| 仅 `--second-order <url>` | ✅ 命中 second_order（High） |
| `--second-order` + `--allow-second-order-writes` | ✅ 命中 |
| `+ --no-production-mode` | ✅ 命中（该开关与二阶无关） |

**结论：单个 `--second-order` 即可**。`--allow-second-order-writes` 只在显式指定
`--second-method` 为非幂等方法时才需要（`resolveSecondOrderMethod` 的抑制条件）；
`--no-production-mode` 是高危 payload 池的护栏，与二阶无关。

**原结论错在**：初次测试时把三个开关一次给全，未做消融实验就归因。教训与 5.1 同源 ——
**开关类结论必须做消融，否则会把"无害的额外开关"误报成"必需条件"**。

因此本条**不再是缺口**，无需自动推导。

## 四、API 接口层

### 4.1 已实现但未写进 README 的端点

`GET /api/scan/:id/events`（SSE 实时事件）、`POST /api/scan/:id/pause|resume`、
`GET /api/payloads`、AI 报告端点（`/:id/report/ai` 及其配置查询）。
建议补齐文档——对外是能力，藏着反而浪费。

### 4.2 建议新增：单点重测接口

现状：发现某点漏报后调整参数（如 level/technique/tamper），**只能整站重扫**。
建议：`POST /api/scan/:id/point/:pointId/retest`，带新 config 只重跑该注入点。
实战中"调参验证"是高频动作，这个接口省的是分钟级的等待。

### 4.3 建议新增：两次扫描差异对比

交付场景常用：修完漏洞要证明"确实修好了"。建议 `GET /api/scan/:id/diff?base=<scanId>`，
输出新增/已修复/仍存在的漏洞集合。
