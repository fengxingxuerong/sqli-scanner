## 1. 待解决的问题

`binaryGuessColumns`（`server/src/engine/columnGuess.js`）只有两条判据：

```js
if (status >= 500 || len < baseLen * 0.5) { hi = mid - 1; }  // 超出列数
else { ans = mid; lo = mid + 1; }                            // 成功
```

在「**SQL 报错也返回 200 + 错误页回显 SQL**」的目标上**两条同时失效**：

```
实测（e2e/blackbox-lab/diag-colguess.mjs，A1 点真实 4 列，baseLen=213，阈值=106）
n    status  len   实际应为   工具判定
1-4  200     224   成功       成功 ✓
5    200     209   超出       成功 ✗   ← 错误页只比正常页短 15 字节
6-7  200     209   超出       成功 ✗
```
→ 一路判「成功」→ **收敛到 maxCols（50）** → UNION 提取按 50 列构造 → **提取必败**。

## 2. 两次尝试为什么失败（具体数据）

两次都改 `columnGuess.js` 加「形态判据」（`responseSkeleton` 剥数字取骨架 + 与失败基准比对），
两次都被 `tests/columnGuess.test.js` 拦下：

| 尝试 | 失败用例 | 断言 |
|---|---|---|
| 第 1 次（预取基准，循环外） | 4 个 | 请求数超限 |
| 第 2 次（惰性：`!lenEvidence` 单轮触发） | 2 个 | `callCount <= 7` ✗；`maxProbed === 10` 实际 11 ✗ |

### 根因（第 2 次，已定位到具体机制）

**① 测试 2 失败 = 启用条件太松**

mock：`n<=5` → 成功；`n>5` → 500。二分路径：
```
mid=25 → 500 ✓有证据 → hi=24
mid=12 → 500 ✓       → hi=11
mid=6  → 500 ✓       → hi=5
mid=3  → 成功 ✗无证据 → 【我在这里触发了基准探针】+2 请求 → callCount=8 > 7 ✗
```
**单轮判断 `!lenEvidence` 是错的** —— 二分中途**必然**出现成功轮。

**② 测试 5 失败 = 基准探针必须探 n > maxCols**

mock：全 200 / 200 字节；`maxCols=10`。原逻辑收敛到 `ans=10`（顶到上限）。
我的基准取 `probe(maxCols+1)=probe(11)` → 断言 `maxProbed === 10` ✗（实际 11）。

**这一条是设计使然**：要判断「是不是因为判据失效才顶到上限」，**必须探一个超出 maxCols 的值**。

## 3. 8 个 mock 的逐条分析（实施前必读）

| # | 用例 | mock 形态 | baseLen / maxCols | 断言 | 新判据影响 |

| 5 | **maxColumnsGuess 上限** | **全 200/200B** | 200 / **10** | `cols===10`、**`maxProbed===10`** | **顶到上限 → 触发 → 探 11 → 断言 ✗ 需适配** |

## 4. 新的设计（第三次实施）

### 4.1 启用条件：仅「顶到上限」时才怀疑

```js
// 先按原两条判据跑完整二分 —— 有明确 500/短错误页的目标，行为与今天完全一致（零额外请求）
const { n: ans } = await doGuessColumnsOriginal(probe, baseLen, maxCols);
if (ans < maxCols) return ans;          // 没顶到上限 → 判据有效 → 直接返回

// 只有顶到上限才可能是「判据失效」→ 才做形态验证（此时多花 1~2 个请求是值得的）
const failShape = await getFailureShape(probe, maxCols);   // probe(1) + probe(maxCols+1)
if (failShape == null) return ans;      // 基准不可区分（骨架相同/过短）→ 保持原结果，零回归

// 用形态判据重跑二分（这次带着 failShape）
return await doGuessColumnsWithShape(probe, baseLen, maxCols, failShape);
```

**为什么这样最优**：
- **有 500/短错误页的目标**：`ans < maxCols` → **一次形态探针都不发**（测试 1/2/7/8 全不受影响）
- **顶到上限的目标**：才做验证。这类目标**本来就可疑**（50 列很少见），多花 1~2 请求是合理的
- **缓存测试 3**：顶到上限 → 会触发，但断言只看"第二次调用"→ 不受影响

### 4.2 形态判据本身

```js
// responseSkeleton 剥掉数字与连续空白 → 同一份模板产生的页面骨架相同，
// 避免 payload 里那个变化的数字（ORDER BY 4 / 5）打断比对
const overByShape = failShape != null && responseSkeleton(body) === failShape;
if (status >= 500 || len < baseLen * 0.5 || overByShape) { hi = mid - 1; }
else { ans = mid; lo = mid + 1; }
```

`getFailureShape` 必须**自带可区分性检查**（防误启用）：
```js
const okShape = responseSkeleton(probe(1) 的响应);
const failShape = responseSkeleton(probe(maxCols+1) 的响应);
if (!okShape || !failShape || okShape === failShape || failShape.length < 8) return null;
```

### ⚠️ 但真实靶场的提取链**仍失败**（与修复前同一形态）

```
node e2e/blackbox-lab/dump-verify.mjs
→ 7 分钟无产出、报告未生成
→ 输出停在：[检测] union/error/boolean → [命中] boolean   ← 检测完成，提取阶段无任何输出
```

**重要判断**：失败形态与修复前**逐字相同**（同样 7 分钟、同样停在检测之后），
且列数探测在单元层面已被证明修好 —— 因此
**提取链的问题大概率不在列数，而在提取阶段本身**（静默卡住，无日志、无产出）。

**结论**：M2 的修复**应予保留**（证据：单测 + 133 引用方全绿），
但**「提取链不可用」这个发布阻断项没有被 M2 解决** —— 它是**另一个独立问题**，
需要单独定位（下一步应从"提取阶段的入口为什么不产出日志"入手，而非继续查列数）。

**未验证项（如实标注）**：真机靶场零回归尚未跑（`e2e/real-mysql-lab` / `multi-engine-lab` /
`oracle-lab` / `mssql-lab`）—— 因为黑盒提取链本身跑不通，无法用端到端结果反证无回归。

## 7. 教训（写下来免得第三次也栽）

> **"机制正确"和"能通过既有契约"是两件事。**

形态判据的**逻辑**我用独立脚本验证过是对的（5 个样本全对）；但**启用条件**（`!lenEvidence` 单轮）
与既有测试的 mock 语义冲突。**判据逻辑没问题，门槛有问题。**

**下次动手前，先把 8 个 mock 的 n 边界与断言列成表（本文档第 3 节）** ——
这张表能提前暴露"测试 5 必然冲突"，省掉一次来回。
