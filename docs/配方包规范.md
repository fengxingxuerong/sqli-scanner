# 配方包规范（CVE 定向检测）

> [D179] 2026-10-26 立。定位：**把「某个已披露漏洞的定向检测」做成可装载、可校验、可复现的包**，
> 同时把「不许吹牛」写成机器判据。配方格式**复用官方扩展点** `--payload-file`（[D24]），
> 不新增引擎语法——配方包只是「条目 + 元信息 + A/B 口径」打成一个目录。

## 一、为什么按「包」而不是按「一堆 payload」

竞品里单 CVE 扫描器能在几天内冲起来（本周 assetnote 的 php2shell 扫描器 4 天 905★，
见 [`竞品对标-2026W44.md`](./%E7%AB%9E%E5%93%81%E5%AF%B9%E6%A0%87-2026W44.md) §一/C），
靠的是「**一个明确的洞 + 一条明确的验证 + 修复建议**」。本仓已有 payload 扩展点，但散落成一堆条目时：

- 没人知道这堆条目对应哪个洞、修了没有；
- 「验证」留在作者脑子里，读的人无法复核；
- 容易顺手写下 `; DROP TABLE` 这类条目当「更强的证据」。

配方包解决的就是这三件事：目录即单元，元信息是契约，校验器是闸门。

## 二、目录与字段

```
recipes/<pack-id>/
  pack.json     # 唯一必需文件
```

```json
{
  "id": "demo-postgres-wrapper",
  "title": "演示配方：PostgreSQL wrapper 下的报错 / 布尔形态",
  "demo": true,
  "why": "为什么这个配方存在（一句话，写清它不是什么）",
  "targetHints": ["参数值被包进单引号后拼进 WHERE", "DB 错误原样回显"],
  "ab": { "baseline": "在哪个靶场/目标上跑", "expect": "修前/修后各自期望", "watch": "什么现象说明条目有问题" },
  "remediation": ["参数化查询", "统一异常处理：不向客户端回显 DB 错误"],
  "entries": [ /* 与 --payload-file 同 schema，见 docs/自定义检测条目.md */ ]
}
```

| 字段 | 必填 | 说明 |
|---|:-:|---|
| `id` | ✅ | 小写 kebab，≥3 字符；**同一 id 不允许在两个配方里出现** |
| `title` | ✅ | 人读标题 |
| `entries` | ✅ | 非空数组，走引擎同一条校验（`validateCustomEntries`）与冲突检查（`mergeCustomEntries`） |
| `demo` | ✅（语义上） | `true` = 形状演示，**禁止**带 `cve` |
| `cve` | 非 demo 必填 | 形如 `CVE-2024-12345`；必须配 `affected` + `ab` |
| `affected` | 非 demo 必填 | 受影响产品/版本（写清来源，别只写「某产品」） |
| `ab` | ✅ | A/B 验证口径（在哪跑、期望什么、什么算条目出错） |
| `remediation` | ✅ | 至少一条可执行修复建议 |
| `targetHints` | 建议 | 目标特征（决定这个配方在哪种站上才有意义） |

## 三、机器判据（`scripts/recipe-pack.mjs`）

```bash
node scripts/recipe-pack.mjs --check                                    # 校验 recipes/ 全部配方
node scripts/recipe-pack.mjs --export recipes/<id> --out payloads.json  # 导出成 --payload-file
node scripts/recipe-pack.mjs --selftest                                 # 自证判据有牙
```

判据（每条都有反向夹具；`--selftest` 11 种回归）：

1. 条目过引擎校验（字段缺失 / technique 越界 / 包内 id 重复都会红）；
2. 与内置注册表 id 冲突 ⇒ 红（只追加，不覆盖）；
3. **破坏性条目必须自己声明 `risk: 3`**——配方不是高危池后门（`DROP TABLE`/`INSERT`/`INTO OUTFILE` 等语句判据）；
4. `demo: true` 带 `cve` ⇒ 红（**没有真机验证就不许写 CVE 号**）；
5. 非 demo 缺 `cve`/`affected`/`ab`/`remediation` ⇒ 红；
6. 缺 `ab` 或缺 `remediation` ⇒ 红（修不好等于只交付一半）。

已进收口清单：`--check` 与 `--selftest` 两项（`npm run gate:close` 会跑）。

## 四、A/B 怎么交（拿不出这个就别发配方）

以演示配方在 `e2e/real-world-lab`（PGlite 真 PG）上的实测为例：

```bash
node scripts/recipe-pack.mjs --export recipes/demo-postgres-wrapper --out /tmp/demo.json
SSRF_ALLOW_PRIVATE=1 node server/bin/cli.js -u "http://127.0.0.1:8130/items?cat=1"                       # 基线：exit 2、N 条
SSRF_ALLOW_PRIVATE=1 node server/bin/cli.js -u "http://127.0.0.1:8130/items?cat=1" --payload-file /tmp/demo.json  # 带配方：仍 exit 2、同 N 条
SSRF_ALLOW_PRIVATE=1 node server/bin/cli.js -u "http://127.0.0.1:8130/blog?id=1"  --payload-file /tmp/demo.json  # 安全对照：exit 0
```

**判据**：带配方后的检出集合必须与基线**一致**（多出来 = 条目判据有问题；变少 = 条目把内置路径挤掉了），
安全对照必须 0 命中。修后 0 命中只能来自「修复后的同一点位」，不能拿另一个干净站点冒充。

## 五、红线

- **不做目标发现**：配方的 `targetHints` 是「这类站点才适用」的说明，不是搜索引擎批量撒网的清单（AGENTS §0）；
- **不发未验证的 CVE 配方**：`demo` 与 `cve` 互斥由校验器强制，写 `cve` 就要给 `affected` + 真机 A/B；
- **破坏性条目默认拒绝**：真要做写操作验证，必须 `risk: 3` 且在 `why` 里写副作用与回滚方式；
- **配方不改证据等级**：`dbmsEvidence` 仍按真引擎验证分层，配方不会把「模板适配」抬成「真引擎验证」。

## 六、与其它扩展点的分工

| 扩展点 | 能加什么 | 不能加什么 |
|---|---|---|
| `--payload-file` / 配方包 | 检测条目（payload 模板） | 新通道、新判据 |
| `--request-script` | 请求形态变换（签名/加密） | 检测逻辑 |
| tamper 插件 | payload 变换（WAF 绕过） | 条目与判据 |
