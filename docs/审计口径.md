# 安全配置审计口径（`--audit`，D181）

> 对标 sqlmap `--audit`（2026-10-19 新增）。定位：**连上库之后，除了「能不能注入」，再看一眼
> 「这个库自身配置有多松」** —— 交付型测试的客户会问「除了这个洞，我们的库还有什么问题」，
> 这一节就是回答，且必须能复核。

## 一、什么时候会跑

| 条件 | 结果 |
|---|---|
| 直连模式（`-d <连接串>`）+ `--audit` | 执行审计，结果进 `report.audit` / `summary.audit` 与报告 Markdown/HTML 小节 |
| 直连但**没加** `--audit` | 完全不执行，报告里没有 `audit` 字段（默认关，不偷偷摸底） |
| HTTP 目标 + `--audit` | **不静默跳过**：写一条 `ran:false` + 原因「需要直连模式」（留白会被读成「审计过了没问题」） |
| 直连但驱动取不到 | 同上报 `ran:false` + 失败原因 |

## 二、检查项（真源：`server/src/engine/auditChecks.js`）

### PostgreSQL（PGlite 真 PG 18 已实测）

| id | 检查 | 命中风险 |
|---|---|---|
| `pg-version` | 版本串（信息项） | — |
| `pg-current-user` | 当前连接身份（信息项） | — |
| `pg-superuser` | 是否超级用户 | **high**（一次注入 = 整库接管） |
| `pg-createrole` | 是否可创建角色 | medium（提权跳板） |
| `pg-password-encryption` | 口令加密方式（md5 可离线爆破） | medium |
| `pg-public-create` | public schema 是否允许建表 | medium |
| `pg-file-read` | 能否执行 `pg_read_file` | **high**（读服务器文件） |

### SQLite（sql.js 真引擎已实测）

| id | 检查 | 命中风险 |
|---|---|---|
| `sqlite-version` | 版本（信息项） | — |
| `sqlite-foreign-keys` | 外键约束是否开启（默认关） | low |
| `sqlite-trusted-schema` | schema 内容能否调用危险函数 | medium |

### MySQL / MariaDB（MariaDB 10.11 与纯 MySQL 8.0.28 双真机已验证，D184/D185）

`mysql-version` / `mysql-current-user` / `mysql-file-priv` 三条已真机双验证：**2026-10-27 在真实
MariaDB 10.11.19（本机便携靶场，:3306，D184）与真实 MySQL 8.0.28 Community Server（D:/mysql 便携版，
:3307，D185）各跑通一轮**：两轮均 3 项全执行、`unknown=0`，root 连接的 FILE 权限均如实判 fail
（见「四、复验」实测）。两个引擎共用这组检查项（`CHECKS_BY_DIALECT` 同表），方言差异按
`summary.dbmsEvidence` 的同类 caveat 口径标注。

直连凭据两种给法（[D184] 起 DSN userinfo 不再被静默丢弃；特殊字符需 percent-encode，sqlmap 同要求）：

- **DSN 内嵌（sqlmap -d 同形）**：`-d "mysql://root:root@127.0.0.1:3306/sqli_lab"`（D184 实测）或
  `-d "mysql://root:root@127.0.0.1:3307/sqli_lab"`（D185 纯 MySQL 实测）；
- **环境变量兑底（user 缺省 root；D184 前唯一通路，行为不变）**：
`MYSQL_PASSWORD=... node server/bin/cli.js -d mysql://127.0.0.1:3306/test --driver mysql --audit`。

> ⚠️ 这与 README 的「数据库支持验证等级」是同一套纪律：没有真引擎证据的能力只能标注，
> 不能写成已验证。审计项的方言覆盖同理。

### SQL Server（SQL Server 2022 真机已验证，D186）

`mssql-version` / `mssql-current-user` / `mssql-sysadmin` 三条于 **2026-10-27 在真实 SQL Server 2022
（RTM 16.0.1000.6）引擎上验证**：检查项 SQL 与判据先经 LocalDB（同源引擎，.NET SqlClient 通道）逐条实跑；
随后经 `mssql://audit_probe:***@127.0.0.1:14330/sqli_lab_mssql` 直连驱动端到端跑通
`audit.ran=true dialect=mssql`，3 项全执行、`unknown=0`，sysadmin 连接如实判 fail
（见「四、复验」实测）。注意：mssql 包不支持 LocalDB 实例名直连（tedious 仅 TCP），
本机取证经本地 TDS 桥（TCP⇄命名管道）完成，属临时取证工具不入仓；可 TCP 的 SQL Server
实例可直接 DSN 直连（`mssql://user:pass@host:port/db`，sa 直连时 sysadmin 必判 fail）。

直连凭据三种给法（[D184] 起 DSN userinfo 不再被静默丢弃；特殊字符需 percent-encode，sqlmap 同要求）：

- **DSN 内嵌（sqlmap -d 同形）**：`-d "mssql://sa:***@127.0.0.1:65039/sqli_lab_mssql"`；
- **环境变量兑底**：`MSSQL_PASSWORD=... node server/bin/cli.js -d mssql://127.0.0.1:65039/test --driver mssql --audit`；
- **无凭据时走 Windows 集成认证**（本地默认实例 / LocalDB 常态；mssql 包对 LocalDB 实例名不支持，
  需经 TCP 口，见上）。

> ⚠️ 这与 README 的「数据库支持验证等级」是同一套纪律（下同）：没有真引擎证据的能力只能标注，
> 不能写成已验证。审计项的方言覆盖同理。

### Oracle（Oracle AI Database 26ai Free 真机已验证，D187）

| id | 检查 | 命中风险 |
|---|---|---|
| `oracle-version` | 版本串（信息项） | — |
| `oracle-current-user` | 当前连接身份（信息项） | — |
| `oracle-sysdba` | 是否以 DBA 特权身份连接（`SYS_CONTEXT('USERENV','ISDBA')`） | **high**（一次注入 = 整实例接管） |
| `oracle-dba-role` | 是否被授予 DBA 角色 | medium（提权跳板） |
| `oracle-password-verify` | 默认 profile 是否启用口令复杂度校验函数 | medium（弱口令可直接登录） |
| `oracle-directory-priv` | 能否创建目录对象（`CREATE ANY DIRECTORY`，配合 UTL_FILE 读写服务器文件） | **high** |

**2026-10-28 双真机实测（Oracle 26ai Free 23.26.3.0.0，FREEPDB1）**：

- **SYS / SYSDBA**：6 项全部执行、`unknown=0`；`oracle-sysdba` / `oracle-dba-role` /
  `oracle-password-verify`（默认 profile 的 `PASSWORD_VERIFY_FUNCTION` 为 `NULL`）/
  `oracle-directory-priv` 四项如实判 **fail**；
- **低权账号（仅 `CREATE SESSION`）**：5 pass / **1 unknown**（`dba_profiles` 不可见，
  `ORA-00942` 带 reason）—— 查不到标 unknown，绝不计入通过。

Oracle 的 `SYS` 必须以特权身份连接，DSN 用查询参数表达（其余方言忽略该键）：

```bash
# DSN 内嵌身份 + 口令；?privilege=SYSDBA 映射 oracledb.SYSDBA（也认 SYSOPER/SYSASM/…）
node server/bin/cli.js -d "oracle://SYS:***@127.0.0.1:1521/FREEPDB1?privilege=SYSDBA" --audit
# 环境变量兜底（口令 / 特权身份）
ORACLE_PASSWORD=... ORACLE_PRIVILEGE=SYSDBA node server/bin/cli.js -d oracle://SYS@127.0.0.1:1521/FREEPDB1 --audit
```

`--driver` 可省略：D187 起 `-d` 的连接串 scheme 会推断驱动（`oracle://` → `oracle`，
`mysql://` → `mysql`；只有显式 `memory` 才是自检桩）。见「三、三条硬口径」下方对
「静默回退 memory」缺陷的说明。

### IBM Db2（IBM Db2 v11.5.8.0 容器真机已验证，D189）

| 检查项 | 判什么 | 风险档 |
|---|---|---|
| `db2-version` | `sysibmadm.env_inst_info` 的 `service_level` | info |
| `db2-current-user` | `SESSION_USER`（`sysibm.sysdummy1`） | info |
| `db2-instance-authority` | `SYSPROC.AUTH_LIST_AUTHORITIES_FOR_AUTHID` 里 SYSADM/SYSCTRL 是否直接授予（d_user/d_group） | **high** |
| `db2-dbadm-holders` | `syscat.dbauth` 中 DBADM 授予面（>2 判风险） | medium |

**2026-10-29 双形态实测（ibmcom/db2:latest = DB2 v11.5.8.0，testdb，VMware Ubuntu 24.04 VM）**：

- **属主 db2inst1**：4 项全部执行、`unknown=0`；`db2-instance-authority` 如实判 **fail(high)**
  —— 属主的 SYSADM 经组授予（表函数返回 `d_user='*'`、`d_group='Y'`），判据认
  `d_user='Y' or d_group='Y'`，`'*'+'N'` 不算持有；
- **低权 db2fenc1**：4 项全部 pass、`unknown=0`——四项查询对 PUBLIC 均可读，无假 unknown；
- 授权面实测：DBADM 授予 1 个身份（属主自身）⇒ pass。

两处「不猜」的落地：实例级权限**不在** `syscat.dbauth`（那是库级授权表，实测 SQL0206N），
必须走 SYSPROC 表函数；`auth_list_authorities_for_authid` 的 `d_user='*'` 只表示
「经组授予路径存在」，是否真持有看 `d_user`/`d_group` 的 `'Y'`。

驱动为**用户自备**：`npm install ibm_db`（内置 IBM clidriver，体积数百 MB，故不进 server 依赖，
防 npm 包体回退 D182 瘦身成果）；未安装时 `--driver db2` 报 `DIRECT_DRIVER_UNAVAILABLE`（6011），
不静默回退 memory。

```bash
# DSN 内嵌身份 + 口令（ibm_db 同形）；--driver 可省略（db2:// scheme 自动推断）
node server/bin/cli.js -d "db2://db2inst1:***@192.168.59.137:50000/testdb" --audit
# 环境变量兜底（口令）
DB2_PASSWORD=... node server/bin/cli.js -d db2://db2inst1@192.168.59.137:50000/testdb --audit
```

## 三、三条硬口径（写进代码，不是描述）

1. **只读**：检查项的 SQL 只允许 `select` / `show` / `pragma` 开头（单测 ⑤ 强制，连字符串字面量里的
   `CREATE` 都先剥掉再判，避免误报）。真机用例跑完会逐表比对行数与 schema，证明库内容一字未变。
2. **不猜**：查询报错 / 方言未收录 ⇒ 该条 `unknown` + `reason`。`summary` 里 `unknown` **单独计数**，
   页面上也单独列出并写「不等于通过」；`pass` 只统计真查成的项。
3. **可复现**：每条结果带 `sql`，第三方拿同一连接串重跑即可得到同一结论。

### [D187] 直连驱动不再静默回退 `memory`（真缺陷，2026-10-28 现场实证）

`-d <DSN>` 不传 `--driver` 时，CLI（`args.driverType || 'memory'`）、REST
（`String(b.driverType || 'memory')`）与模型层（`input.driverType || 'memory'`）三处都把
驱动类型写死成**内存自检桩**：`-d "mysql://root:root@127.0.0.1:3306/sqli_lab"` 实际打的是
`MemoryRecordDriver`，报告照常出 `dbmsVersion=5.7.25-sqlite-sim`、`audit.dialect=sqlite`，
**High 命中与审计结论全部产自假库**。这违反本仓「中间层自报成功、无人校验外部事实」的治理口径。

修法：`createTarget` 统一走 `normalizeDirectDb()`，未显式声明时按 DSN scheme 推断
（与 `getDriver` 同源），CLI/REST 去掉写死默认。A/B（同一条命令，MariaDB 10.11.19 真机）：

| | 修复前 | 修复后 |
|---|---|---|
| `target.db.driverType` | `memory` | `mysql` |
| `points[0].dbmsVersion.raw` | `5.7.25-sqlite-sim` | `10.11.19-MariaDB` |
| `audit.dialect` | `sqlite`（3 项假结论） | `mysql`（version/current_user/file-priv） |

  --sql-template "SELECT * FROM users WHERE id={INJECT}" --audit -o out/

# 真机（sql.js 真 SQLite）：外键默认关 ⇒ 判 fail；开 pragma 后同判据转 pass

  --audit -o out/

## 五、边界（别把它当「安全评估」）

- 只覆盖**配置面**的少数几项，不等于基线加固检查清单（缺口令策略、审计日志、网络暴露面等）；
- 判定是**启发式**：例如「可创建角色」在有专门 DBA 的团队里可能是正常设计，报告只陈述事实；
- 不改配置、不给修复脚本（修复建议写在报告的通用基线里；真正的加固需按组织规范做）；
- 只支持直连。HTTP 目标无法查库自身配置——这不是缺陷，是通道限制。
