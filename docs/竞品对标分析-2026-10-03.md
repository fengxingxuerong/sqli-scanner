## 一、结论先行

**三句话版本：**

1. **赛道选对了，产品形态是唯一的差异化护城河。** 全部同类项目里，**没有一个**同时提供 Web UI + 桌面壳 + CLI 三端。ghauri / pocsuite3 / PowerUpSQL 全是纯 CLI，nuclei / ZAP 是通用平台不是 SQLi 专精。
2. **工程可信度是绝对优势，但市场不感知 —— 这是最尖锐的问题。** 变异门禁、facts 指纹、artifact:drift、17 套件验收，这些在同类里**没有第二家**。但数据摆在这里：ghauri 只有 **2 个贡献者**却拿了 **4,081 star**。用户不为门禁付费，只为"能不能扫出来"点 star。**当前投入产出严重失衡。**
3. **技术天花板真实存在。** 真机 ModSecurity 对拍：19 条样本、直连上界 10、真机**打穿插件只有 1 个**。9 种 DBMS 里 6 种只有模板没有真机。**这不是"未完成的验证"，是"验证证实了能力不足"。**

## 三、能力维度逐项对标

### 3.1 产品形态 —— 唯一的绝对优势 ✅

| 项目 | CLI | Web UI | 桌面壳 | 批量编排 | 交付报告格式 |
|---|:-:|:-:|:-:|:-:|---|
| sqlmap | ✅ | ❌ | ❌ | `-m` ✅ | txt / html / maigx |
| ghauri | ✅ | ❌ | ❌ | ❌ | txt |
| pocsuite3 | ✅ | ❌ | ❌ | ✅ | txt / json |
| nuclei | ✅ | ❌ | ❌ | ✅ | json / md |
| ZAP | ✅ | ✅（仅 addon） | ❌ | ✅ | html / json / md / xml |
| **sqli-scanner** | ✅ | ✅ | ✅ Tauri | ✅ Burp XML / HAR / Postman / OpenAPI | **html / json / md / sarif / csv / manifest** |

**这是真实的差异化，没有任何同类项目占这个位。** 尤其是 **SARIF 2.1.0**（对接 GitHub Security / DefectDojo）+ **manifest.json**（含授权声明）+ **CLI 退出码 0/1/2** 三件套 —— 这是把工具变成"可进 CI 的交付件"的正确路径，sqlmap 至今没有。

### 3.2 检测技术通道

| 通道 | sqlmap | 本项目 | 备注 |
|---|:-:|:-:|---|
| union / error / boolean / time / stacked | ✅ | ✅ | sqlmap 的 U/E/B/T/S |
| OOB（带外） | ✅ | ✅ | 本项目内置 HTTP+DNS 接收端 |
| 二阶注入 | ✅ | ✅ | 本项目独有**跨角色双身份**（低权写 / 高权读） |
| 内联注入（inline） | 部分 | ✅ | 独立通道 |
| **NoSQL 注入** | ❌ | ✅ | CWE-943 |
| XML/SOAP 叶子路径 | 部分 | ✅ | 但**注释/CDATA/DOCTYPE 一律放弃** |

**通道数 9 > sqlmap 的 6-7。** 这是真优势。
⚠️ 但通道多 ≠ 打得深：sqlmap 的 U/E/B/T 是 14 年打磨，本项目在 WAF 真实环境下的有效打穿数**只有 1 个插件**（见 3.4）。

### 3.3 库支持 —— 分层诚实，但暴露短板

| 等级 | 数量 | 具体 |
|---|:-:|---|
| ✅ 真实引擎全链路 | 6 | MySQL、MariaDB、PostgreSQL、SQLite、Oracle、SQL Server |
| ⚠️ 部分通道 | 3 | H2、HSQLDB、Derby（CRS PL1 下布尔 9/9，定库不达） |
| ⛔ **仅模板** | **9** | TiDB、DM8、ClickHouse、DB2、Sybase、Firebird、Informix、Access、MonetDB |

sqlmap 支持 6 种：MySQL / PostgreSQL / Oracle / MSSQL / SQLite / Firebird。**数量上我更多（18 vs 6），但 9 种是纸面数字。**

**诚实的说法**：差异化不在"支持 18 种库"，而在"**对每种库都标注了证据等级**"。sqlmap 声称 6 种，不会告诉你哪几种没真机验。**分层披露本身就是产品能力**，但它不构成性能优势。

### 3.4 WAF 对抗 —— 全场最强工程，最弱实战 ⚠️

**工程侧（碾压级）**

- 228 个 tamper 插件，**对齐 sqlmap 官方 1.9.11 tamper 全集 70/70**（`npm run tamper:parity` 门禁钉住）
- 62 个 WAF 厂商指纹
- 自实现 CRS 执行器，**用官方回归集钉自己**：族 942 = 99.6%、族 930 = 100.0%
- WAF 通道降级策略（A3）、定向变异搜索器（A2）、语义等价变换库（A1）

**实战侧（坦白说很弱）**

| 轮次 | 样本 | 直连上界 | 真机打穿插件 | 放行 PL1/PL3 |
|---|:-:|:-:|:-:|:-:|
| 第四轮（2026-09-29） | 19 | 10/19 | **1 个**（`unionvaluesrow`） | 25 / 25 |

**"放行 25 个" vs "打穿 1 个"，差一个数量级。** sqlmap 的 tamper 在真实 WAF 上也远谈不上好用（社区公认），但它 14 年积累了 5000+ issue 的真实对抗反馈。

> **2026-10-09 更正**：原句「本项目目前是自建尺子、自己出题、自己判卷」**不准确**，两头都错了一半：
> - **尺子不全是自造**：CI `modsec-live` 跑的是官方 `owasp/modsecurity-crs:nginx` 镜像（真实
>   ModSecurity + libinjection + CRS 4.30.0），`e2e/sqli-labs` 是**第三方**靶场 ⇒ 打穿 1 个插件这个
>   结论建立在**真实引擎**上，不是自实现执行器。
> - **卷子确实是自造**：靶站应用是自建的 5 种 SQL 拼接形态（`e2e/waf-real/modsec-target.mjs`），
>   37 个 e2e 靶场里除 sqli-labs 外全是自建 ⇒ **误报率**这个扫描器命门没有第三方复杂应用的证据。
> ⇒ 真缺口精确表述为：**只验了一家 WAF + 没有第三方复杂应用卷子**（详见 §八）。

⚠️ CRS 保真度 99.6% **不能外推到 XML 接口**（942 家族 66 条里 54 条声明读 `XML:/*`，本执行器不解析 XML）—— README 已如实标注，做得对。

### 3.5 报告与交付 —— 第二强项 ✅

| 维度 | sqlmap | 本项目 |
|---|---|---|
| 输出格式 | txt / html / maigx | html / json / md / **sarif** / **csv** / **manifest** |
| CWE / OWASP 分类 | ❌ | ✅ CWE-89 / CWE-943 + OWASP A03:2021 |
| CVSS v3.1 | ❌ | ✅ score / vector / severity |
| 逐条 PoC（curl + 原始报文） | 部分 | ✅ |
| 修复建议 | ❌ | ✅ 按通道定制 + 通用基线 |
| 结论可信度标注 | ❌ | ✅ `dbmsEvidence` 写进每份报告 |
| CI 退出码 | 模糊 | ✅ 0 / 1 / 2 三分 |
| 扫描范围声明 | ❌ | ✅ scope + 逐跳重校验 + SSRF 拒绝 |
| 字段漂移防护 | — | ✅ `readme-consistency` 判据 ⑭b + 源码守卫 |

sqlmap 的输出是"给渗透工程师看的终端文本"，本项目是"**给客户和 CI 看的交付件**"。这是完全不同的定位，而且这个定位比"又一个 sqlmap"更有商业价值。

### 3.6 部署与安全基线 —— 独有优势 ✅

sqlmap / ghauri 都是**默认裸奔**（无鉴权、无 scope 约束、无 SSRF 防护）。

本项目：

- `HOST=0.0.0.0` 且未设 token ⇒ **拒绝启动**（fail-closed）
- SSRF：内网 / 回环 / 链路本地 / 云元数据默认拒绝
- scopeGuard：越界目标**在发起任何请求前**拒绝，每一跳重定向重校验
- Tauri 侧：一次性 token 经 stdout 回传、端口自动避让、不会被冒充引擎
- 目标认证：Basic / Digest / **NTLMv1**（自实现 DES）+ mTLS

**这一整块在同类里基本是空白。** 面向企业内网交付时这是硬门槛。

## 五、建议（按 ROI 排序，不含"再写个门禁"）

### P0 —— 曝光层，几乎零成本，回报最大（2026-10-03 晚已执行，见 §七）

1. ✅ **补 `description` + `topics`** —— 初稿漏了这条，当晚复核时发现是**最上游**的缺口
   （`description: null`、`topics: []` 意味着在 GitHub 搜索里连第一屏都进不去）。
2. ✅ **写 `README.en.md`** —— 独立英文 README，**数字不重复声明**，统一委托给 `README.md`
   （由 `facts:check` 与 `readme:check` 守护），避免制造第二个会漂移的声明点。
3. ⏳ **发第一个 Release**：`v1.0.0` / `v1.1.0` 两个 tag 已存在，只差发版本体。CHANGELOG 已有 2,840 行，是白捡的信任状。
4. ⏳ **录 30 秒 GIF**（终端 → HTML 报告）放首屏。同类标配，缺失等于隐形。

### P1 —— 定位层，决定"卖给谁"

5. **定位从"另一个 sqlmap"改成"CI 里的 SQLi 门禁"**。理由：SQLi 专精赛道已衰退（见二①），但"SQLi 扫描进 CI + 产出 SARIF 给 DefectDojo / GitHub Security"**没有同类在占位**。这句话就是差异化。
6. **README 首屏只留三样**：30 秒 GIF · 一条 CI 命令 + 退出码说明 · 一份真实 HTML 报告截图链接（`deliverables-demo/` 里已有素材）。当前 602 行 README 没人会读完。

### P2 —— 能力层，昂贵但决定长期

7. **WAF 侧别再自建尺子**。找 2-3 个**第三方公开 WAF 靶场**（OWASP Benchmark / DVWA+WAF / 公开 CTF 靶机）做交叉验证，把"1 个插件打穿"建立在**别人出的卷子**上。当前自建尺子的结论外部不可采信。
8. ❌ **"9 种模板库是纸面数字、需降级"不成立 —— 已核实 README 早就分层披露**（第 138 行总览 /
   第 151 行 ⛔ 档 / 第 190 行客户段点名），初稿这条是误判。真缺口只剩"缺真机证据"，
   属长期项（补 9 个真机的成本远高于收益），**暂不做**。
9. ⏳ **对齐 sqlmap 剩余开关 —— 优先级低，暂不做**。上游核实后，真正缺的只有 `--answers`、
   Windows 注册表 `--reg-*`、OS 接管 `--os-pwn/--priv-esc`、`--purge`/`--eta`/`--dump-format`，
   **均低频或平台相关**，ROI 低于 P1 各项。初稿提到的 `--hashes`（不存在）与 `--replicate`
   （非 sqlmap 开关）已作废。若日后要做，**唯一值得做的是把已实现的 `--passwords` 从"读到哈希"
   推进到"认哈希算法 + 标注弱口令风险"**（离线识别，非爆破），并必须在 README 如实标注识别范围。
10. ❌ **爬虫不需要补** —— 初稿把它列为缺口是误报，见 §四更正说明。`LinkCrawler` + `browserCrawler` 均已实现并接线。

### 明确不建议做

- ❌ **不要为了 star 去加"更多扫描器"**（XSS / SSRF / LFI）。nuclei 31k star 的教训是：通用平台的护城河是**模板生态 + 云端协作**，不是检测能力；单点工具扩品类只会稀释焦点。
- ❌ **不要砍门禁去换 star**。ghauri 2 个人 4k star 证明"没门禁也能有 star"，也证明它永远只能是 sqlmap 的替代品。**要卖的是可信度，不是数量。**
