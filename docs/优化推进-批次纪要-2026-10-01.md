## 三、P0-2 API 速率限制（与审计建议的两处有意偏差）

新增 `server/src/api/rateLimit.js`（固定窗口 · 进程内 · **零新增依赖**）：
`createRateLimiter({ windowMs, max, name, keyOf })` + `tokenKeyOf`（token 前 8 位 || req.ip，
与 index.js 鉴权取值顺序一致）+ `ErrorCode.RATE_LIMITED(4290)` 形状的 429 响应 + 标准限流响应头
（RateLimit-Limit/Remaining/Reset + Retry-After）。环境变量 `RATE_LIMIT_SCAN_MAX`（默认 10/分钟，
0=关闭），已登记 `server/.env.example`。

1. **不引 express-rate-limit**：服务端依赖清单刻意极简（仓内已有 tokenBucket.js 先例），
   固定窗口计数器 ~90 行完全可测，无供应链面。
2. **只挂 `POST /scan/start`（`scanStartLimiter`），不整 router 限流**：审计建议在
   scanRoutes/exploitRoutes 挂载前插入——实测 scanRoutes 同时承载 GET /scan/:id/status
   （UI 每秒轮询）与 /scan/:id/report 读取，整 router 限流直接打断前端。且经核实：
   exploit/* 已有 5 req/s 令牌桶（exploitRoutes.js L137，抛 4290，guards 测试钉着其恢复时序）、
   /report/ai 已有每 IP 每分钟 3 次内联限速（reportAiRoutes.js L15-35）——审计「无限调」
   对这两处已过时，真正的缺口只有 /scan/start。限流在鉴权/CSRF 上游之后，被 401/403/415
   拒绝的请求不消耗配额（未持 token 者无法枯竭受害者配额）。

**验证**：`tests/rateLimit.test.js` 4/4——窗口内允许/超限 429+头/不同 token 独立计额/
窗口翻新重置+OPTIONS 不计额+max<=0 直通/真实 app 第 11 次 start 得 429 且 token B 不连坐
（审计验收口径 §1.2 的 3 条全覆盖）。

## 四、P0-3 Tailwind 退役（方案偏差：自有化而非全量 sx）

**方案**：审计方案 A 是「全 MUI，删 Tailwind，className 全改 sx」。本批执行了「删 Tailwind」，
但 className 保留、以**自有化 utilities.css** 替代 sx 全量改写：

- `src/utilities.css`（5.8KB）= 从 dist 构建产物**逐字提取**的 86 条在用工具类规则 +
  收窄版 preflight 7 条（通用 border 底线 / 表单元素继承 / p,pre 与块级 margin 归零 /
  placeholder 颜色 / html 行高）。提取脚本按花括号深度分词、选择器全等匹配，零猜测；
  级联位置与退役前的 Tailwind 产物完全相同（index.css 同一 import 点），等价性由构造保证。
- `npm uninstall tailwindcss postcss autoprefixer`；删 `tailwind.config.js` / `postcss.config.js`；
  index.css 的三条 `@tailwind` 指令换为 `@import './utilities.css'`。

**偏差理由**：212 处工具类分布在 20 个文件， sx 全量改写需逐处判断元素类型（sx 不作用于原生
input/select，得先转 Box/TextField），而前端没有视觉回归测试——高回归风险、低边际收益。
自有化后 className 不动（测试零风险），样式体系统一为「MUI 主题/sx + index.css 全局样式 +
utilities.css 纯 CSS」，Tailwind 引擎/配置/依赖全部出仓，双体系债（第二套引擎 + 双设计令牌 +
新人困惑）消除。逐处 sx 化可搭 §2.2 组件拆分的便车渐进做。

**验收实测**：`vite build` 后 CSS 12,514B → 7,142B（审计预估的「gzip -80KB」基于 Tailwind 2
全量时代，JIT 3.4 本就按用 purge，实际存量没有那么多可省——以实测为准）；前端 472/475 全绿
（见下）；**视觉基线对比**：退役前先按审计建议拍 5 条路由全页截图（home/scan/history/exploit/
report 存 `.box-agent-scratch/visual-baseline/`），退役后重拍逐张比对，布局/间距/颜色/字体一致。

## 六、P1-4 payloadRegistry 懒加载 —— 实测否决（留证）

审计 §3.1 的前提是「全量加载导致冷启动慢 / Tauri 首扫卡顿」。本机实测（Node 24）：

```
payloadRegistry 模块冷加载（含全部依赖链）: 8.9 ms
registry.json 读取 + 纯 JSON.parse:        1.37 ms（150KB / 681 条）
selectPayloads × 1000（681 条线性过滤）:    18.6 ms
```

而实现审计方案的结构成本：`PAYLOAD_REGISTRY` 是**同步可变数组**（测试直接 push 探针条目）、
selectPayloads 被四个检测器在扫描流水线内同步调用，「定库后异步加载该库分片」要把整条检测链
改造成异步或引入预热屏障——2600+ 服务端用例的回归面，换 1~9ms 的启动收益。按本仓反向清单
（「不要为优化而优化」）与拆分纪律判定：**不做**。若未来 payload 库增长到 MB 量级，按 DBMS
分片 + `import() with {type:'json'}` 的审计方案仍有效，届时再做（数据：收益需先重新实测）。
