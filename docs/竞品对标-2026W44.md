## 二、三条结构性判断（判断，不是数据）

1. **分发形态从「工具」变成「宿主里的一个命令」**。本周最强的量（2,728 个新 skills 仓、
   Claude-Red 9.1k★、open-sesame 5 天 90★）都不在「更强的检测引擎」上，而在**装载方式**上。
   含义：本仓的能力（9 通道 / 18 方言 / 证据链）再好，如果没有「装一下就能用」的形态，
   在 agent 生态里等于不存在。
2. **卖点从「检出率」转向「可验证」**。VulnHunter 卖 executable PoC、open-sesame 卖 validate findings、
   Sequester 卖 triage。本仓恰好有全行业少见的**证据纪律**（`poc.curl`/`poc.raw`、`manifest.json`、
   triage 指纹、`dbmsEvidence` 分级、`unverifiedSurfaces` 披露），但这些资产目前只对**读报告的人**可见，
   没有变成**给 agent 用的一等产物**（可执行复现、修复指令、口径断言）。
3. **CVE 披露窗口是流量入口，但入口只给「高保真 + 非破坏」**。本仓的自定义条目机制已能承载，
   缺的是打包与证据；这条优先级低于 1/2，因为它不改变分发结构，只增加一个内容品类。

## 四、对齐路线（按性价比排序；每条给验收判据，落地时按本地 `git log` 顺延 D 编号）

### P0-A · [D175 建议] agent 分发层：`npx` 一行 + 插件清单 + 带口径的 SKILL

- **做什么**：① `server` 包发布到 npm（或先出 `npx` 可跑的 tarball 通道），`npx sqli-scan -u <url>` 一行出报告；
  ② 仓库加 `.claude-plugin/plugin.json` + `skills/sqli-scan/SKILL.md`（内含三条硬口径：`inconclusive` ≠ 未检出、
  `unverifiedSurfaces` 必须声明、`risk=3`/`--confirm-destructive` 不可代开）；③ 文档补 Claude Code / Cursor 装载步骤。
- **不做什么**：不写「自主决策」话术；skill 里不放任何越过 AGENTS §0 的动作（目标发现、批量 dorking）。
- **验收判据**：干净容器 `npx` 一条命令产出 `report.json`；宿主里 `/plugin marketplace add` 后 9 个 MCP 工具可见；
  skill 被诱导「扫一批站」时按红线拒答（负样本用例）；`npm run refs:check` 绿。
- **成本**：中（发布链路 + 清单 + 一份 skill 文档 + 3 个负样本测试）。

### P0-B · [D176 建议] 修复回路：`--fix-prompt` + 增量复扫

- **做什么**：按技术通道生成**给 AI 编码代理的修复指令**（参数化/白名单/ORM 改写 + 复测命令 + 期望断言），
  与 `appsecradar` 的 fix prompt 等价但**带本仓的证据字段**；`--only-diff` 只扫 agent 新写的端点/参数（复用 `--diff-base`）。
- **验收判据**：vulnlab/DVWA 靶场：把生成的修复提示词交给编码代理应用后，重扫该点转 0 命中；
  增量模式对既有 findings 不重复报（A/B 各一次）；安全对照点 0 误报。
- **成本**：中（渲染 + 一遍 A/B 证据）。

### P1-C · [D177 建议] 可执行复现件：`repro.sh` + 一致性断言

- **做什么**：把 `poc.curl` 升级为可直接执行的 `repro.sh` + `expect.json`（重放 2 次结果一致才标「已复现」），
  报告新增「已复现 / 单次命中」标记，并进 `manifest.json`。
- **验收判据**：靶场命中项 `repro.sh` 复现率 100%；安全对照点 0；「单次命中」在时间/布尔通道上有可解释样本。
- **成本**：低-中（生成器 + 判据 + 靶场回归）。

### P1-D · [D178 建议] 把内部纪律变成对外台账（独特性最高、成本最低）

- **做什么**：`docs/质量台账.md` 由脚本生成（`gate:close` 项目数、`_claims-ledger.json` 状态分布、
  外部裁判 5 号、acceptance 套件数），发布为静态页；数字**只从脚本产出，不手写**。
- **为什么**：本周所有竞品都在喊「high fidelity / evidence-bound」，但没有一家有可核查的台账；
  本仓的 29 项收口门禁 + 28 条 claim 台账是现成弹药，目前完全不可见。
- **验收判据**：页面数据全部来自脚本；台账页与 `_claims-ledger.json` 不一致时门禁报错（防手改）；
  `refs:check` 绿。
- **成本**：低。

### P2-E · [D179 建议] CVE-day 配方包（内容品类，不改架构）

- **做什么**：按已披露 SQLi CVE 出「定向配方包」（注入点指纹 + 非破坏验证 + 修复建议 + A/B 靶场证据），
  走 `--payload-file` / 自定义检测条目机制。
- **红线**：只做**用户给定目标**上的验证，不做目标发现/批量撒网（AGENTS §0；W43 对 dorking 的判定不变）。
- **验收判据**：一个真实 CVE 靶场 A/B（修前命中 / 修后 0 命中），配方文件带误用警示。

### P2-F · [D180 建议] 对齐 sqlmap `--audit`：DBMS 安全配置审计（opt-in、只读）

- **做什么**：复用已有直连/枚举通道，输出「默认账户 / 危险配置 / 补丁级别 / 权限过宽」四类只读检查，
  与「凭据风险标注」并列为报告一节。
- **验收判据**：MySQL + PostgreSQL 真机容器各一轮，审计项有真值对照；无直连时明确「不可用」而非静默跳过。

## 五、不吸收 / 红线（与 W43 一致的部分只列结论）

| 项 | 处置 | 理由 |
|---|---|---|
| 自主渗透循环（ARTEX / DeepAudit / xalgorix） | **不吸收** | 与本仓「结论必须有可复现证据」冲突；这些项目普遍缺误报/漏报数据，接过来只会把「不确定」包装成「已检出」 |
| 拦截代理套件（opentrap） | **不做本体**，最多做「导出为可粘贴请求/URL」互操作 | 与定位无关；已有 `-r` 请求导入覆盖反向需求 |
| Google Dorking / 目标发现 | **不做** | 违 AGENTS §0（只扫用户明确给出的目标） |
| 星数当能力证明 | **不引用** | 本周清单里星数与证据质量**不相关**（905★ 的单 CVE 扫描器有 A/B，5k★ 的 agent 平台没有误报数据） |
| nuclei 模板生态 | 维持 W43 结论 | 见 [nuclei模板生态可行性调研-2026-10-25.md](./nuclei%E6%A8%A1%E6%9D%BF%E7%94%9F%E6%80%81%E5%8F%AF%E8%A1%8C%E6%80%A7%E8%B0%83%E7%A0%94-2026-10-25.md) |
