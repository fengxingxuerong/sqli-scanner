## 一、结论先行

**一句话：作为「无 WAF 环境下的快速普查 + 拖库 + 出报告」工具，它已经能干活且数据正确；
但只要目标前面挂了任何关键字级过滤（云 WAF / 安全狗 / 宝塔 / 自研正则），它全程交白卷——
而且这次实测证明：那个漏洞手工 3 秒就能绕过。**

| 能力 | 判定 | 本次实测证据 |
|---|---|---|
| 无防护常规注入（GET/POST/Cookie/JSON/二次编码） | ✅ 好用 | 10 场景中 9 个检出，union 通道 100–400ms |
| 拖库数据正确性 | ✅ 正确 | 真 MySQL `users` 6 行全对（中文/`o'brien`/ID 跳号/逗号全部正确） |
| 误报控制 | ✅ 优秀 | 参数化对照场景 3 次重复均 0 检出 |
| 判定稳定性 | ✅ 稳定 | 每场景跑 3 次，检出技术集合完全一致（0 抖动） |
| 阴性结论守卫 | ✅ 实战价值高 | WAF 场景输出 `verdict=inconclusive` + 降速/加白名单复扫建议，**不谎报"安全"** |
| **WAF / 关键字过滤场景** | ❌ **全通道失守** | 唯一漏检场景；手工 `1 \|\| 1=1` 可绕过（6 行 vs 1 行差异），引擎 0 检出 |

## 三、P0：WAF / 关键字过滤下全通道失守（本次最严重发现）

### 现象

```
[FAIL(漏检)] waf403  检出=[-]  均耗时=1713ms   （3 次重复，次次 0 检出）
```

### 不是靶场太狠——手工 3 秒绕过（`waf-bypass-proof.mjs` 实测）

| 请求 | 结果 | 回显行数 |
|---|---|---|
| `id=1`（基线） | 200 放行 | 1 |
| `id=1 AND 1=1` | 403 拦截 | 0 |
| `id=1 \|\| 1=1`（**`\|\|` 代 OR**） | 200 放行 | **6** |
| `id=1 \|\| 2=1`（假值对照） | 200 放行 | 1 |
| `id=1 %26%26 1=1`（`&&` 代 AND） | 200 放行 | 1 |

布尔差异 6 行 vs 1 行，肉眼可判。**引擎一个都没试。**

### 为什么没救回来（逐层排查）

| 配置 | wafDetected | 检出 |
|---|---|---|
| 默认 | `null`（基线页无 WAF 特征 → 被动识别不到） | - |
| `wafEvasion.autoRetry` + tamper 全开 | `null` | - |
| 指定 tamper 链 space2comment/randomcase/between | `null` | - |
| `activeWafProbe=true` + autoRetry | `generic_block conf=0.6` | - |

- **被动识别失效**：`scanRunner.js:500` 只用指纹阶段的**基线响应**识别 WAF。真实站点基线请求干净、
  只有带 payload 的请求才被拦 → 识别率天然为 0。
- **主动探测能识别，但带不动后续动作**：开了 `activeWafProbe` 能识别 `generic_block`，
  但 `blockPolicy=null`、autoRetry 未产生任何检出。
- **225 个 tamper 全是"形态变形"，没有一个是"算子/关键词替换"**：实测 5 组链
  （space2comment / randomcase / charencode / percentage / equaltolike / space2dash）**全部 0 检出**。
  词被拦的时候，改大小写、改编码、改空格形态都没用——得换词（`OR`→`||`、`AND`→`&&`、
  `=`→`RLIKE/BETWEEN/LIKE`、` `→`%0a`）。

### 危害

真实互联网目标 90%+ 有 WAF 或框架层过滤。按当前能力，扫这类目标会得到"0 漏洞"报告。
**唯一救它的是结论守卫**：报告给了 `verdict=inconclusive` + "疑似 WAF/封 IP：降速并加抖动、
套用 tamper 规避链、申请加白名单复扫"——不会把"没测出来"写成"没漏洞"。这一点比不少商业扫描器强，必须保留。

### 修法（按性价比）

1. **补算子替换型 payload / tamper（最高优先）**：boolean 池加 `||`、`&&`、`RLIKE`、`BETWEEN .. AND ..`、
   `LIKE`、`DIV`、`REGEXP`、`NOT BETWEEN` 变体；写 3 个 tamper：`or2pipes`（` OR `→` || `）、
   `and2amp`（` AND `→` && `）、`eq2rlike`（`=1`→` RLIKE 1`）。这条能直接把 waf403 场景打穿。
2. **拦截响应驱动的自适应**：检测到 403/406/429/503 或拦截页文案时，不是只发建议——
   自动降速（ratePerSec≤1）+ 换算子族 + 换编码族，最多 2 轮。
3. **`activeWafProbe` 默认开**：成本只有几个包，收益是让 autoRetry 有输入。
4. **`blockPolicy` 落盘进 `summary`**，让前端能显示"本次被 WAF 压制了哪些点"。

## 四、P1：空基线场景通道退化（参数原值查不到行）

- 现象：`/empty?name=ghost_user_not_exist`（真库里没这人）→ 布尔真值 `AND 1=1` 与假值 `AND 1=2`
  **都返回空** → 布尔/UNION 通道双双失效，只剩 error。
- 交叉验证：把 `alice` 插回真 MySQL 后，同类型 `/str?name=alice` 立刻从 `[error]` 变成
  `[union,error,boolean]`——**差别只是"原值查不查得到数据"**。
- 真实度：极高。失效 id、已删除用户、需鉴权才可见的记录，全都是这个形态。
- 现状：引擎已有 `invalidValue`（bignum/logical/string，对标 sqlmap `--invalid-*`），但
  `config/defaults.js:139` 默认 `null`，没开。
- 修法：布尔检测器在"真值响应 == 假值响应"时自动降级为 **OR 型注入**
  （`x' OR '1'='1` / `-1 OR 1=1`），或自动启用 `invalidValue=logical` 重跑一轮。

## 五、P1：头注入只有半条命

- `/ua`（User-Agent 拼接进 SQL，报错直出）：只 error 命中，union/boolean 全 miss。
- 影响：真实世界里 UA/Referer/XFF 型注入**没有报错回显**时（生产环境通常关 display_errors），
  这个点就会被判"无漏洞"。
- 修法：header 参数点补齐 union 列数枚举 + 布尔统计判定（当前疑似只走 error 快速层）。

## 六、P1：过滤 / 编码 / LIMIT 位只靠报错兜底

`bl`（关键字被删）、`limit`（LIMIT 位）均只 error 命中。
报错通道拿不到数据（最多拿版本/库名），**无法拖库**，漏洞评级会被压成"信息泄露"。
真实渗透里这类点要么放弃，要么手工构造——目前引擎做不到自动打穿。

1. **拖库数据正确性过关**（CLI 实测）：

2. **误报 0**：参数化 + 强转场景，3 次重复全部 0 检出。
3. **判定零抖动**：11 场景 × 3 次，检出技术集合完全一致。
4. **阴性结论守卫**：403 场景给 `inconclusive` + 可执行处置建议（降速/抖动/加白名单/复扫）。
5. **速度**：union 通道 83–400ms；盲注（噪声页/302）4.9–5.7s，同一量级内可接受。

## 八、与 sqlmap 同场景对拍（决定性证据）

同靶场、同 MySQL、逐场景手工对拍（sqlmap 1.x，`--level=3 --risk=2 --dbms=mysql`）：

| 场景 | 本引擎 | sqlmap | 判定 |
|---|---|---|---|
| `waf403`（关键字 403） | ❌ 0 检出 | ✅ boolean-based blind | **引擎落后：同一 WAF sqlmap 能打穿，引擎不能** |
| `bl`（关键字被删） | ⚠️ error | ❌ 0 检出 | 引擎不落后（多一条报错通道） |
| `empty`（空基线） | ⚠️ error | ❌ 0 检出 | 引擎不落后（sqlmap 同样空基线失效） |
| `enc`（二次编码） | ✅ union+error+boolean，**103ms** | ✅ boolean+error+time+union，约 30s | 打平，**速度 300 倍** |

> `waf403` 这一行是本次评估最重的一击：**不是"WAF 场景无解"，是"引擎无解"**——
> sqlmap 靠算子/语法族切换（含 `||`、`&&`、RLIKE、BETWEEN 等替代算子）绕过去了。
> 补上算子替换族，这个场景就能从 0 检出变成命中。

对拍脚本 `e2e/pentest-lab/sqlmap-compare.mjs` 已内置（注意：Windows 控制台输出为 GBK，
脚本已改为 stdout 重定向文件 + latin1 读取，避免 `Type:` 行匹配失败）。
本机自动对拍受 sqlmap history 清理与沙箱影响不稳定，建议按 §11 手工跑关键场景。

# 修复记录（2026-09-10 晚，全部经真靶场回归）

## F1 — P0 拦截证据驱动的自适应重跑（waf403 场景 0 检出 → 命中）

| 文件 | 改动 |
|---|---|
| `server/src/engine/scanRunner.js` | 新增「拦截证据驱动」分支：`validity.counts.blockHits > 0` 且有未命中点 → 不依赖 WAF 厂商指纹，直接用算子替换族重跑；`summary.blockPolicy` / `summary.wafAdaptive` 落盘 |
| `server/src/config/defaults.js` | 新增 `wafEvasion.adaptiveOnBlock`（默认 true，可关） |
| `server/src/core/waf/wafRecommend.js` | 新增 `generic_block` 专属链（算子替换前置）+ 导出 `OPERATOR_SWAP_CHAINS`；`_default` 前置 `symboliclogical` |

根因：原 autoRetry 要求「识别到高置信 WAF 厂商」，而真实站点基线响应永远干净（只有带 payload 才被拦），
识别率天然为 0 → 开关等于死代码。

## F2 — tamper 链验证器的探针盲区（链被误判「仍被拦」→ 重跑被跳过）

`core/waf/chainVerify.js` 原只用单探针 `{orig}' AND 1=1-- -`。真实 WAF（含本次靶场）普遍拦 `--`，
于是**无论套什么链探针都恒 403** → 所有链判为无效 → 自适应重跑直接跳过。
改为探针族（追加 `{orig}' AND '1'='1`，无注释无空格依赖）：
裸探针需**全部**被拦才认定 WAF 敏感；链验证**任一**探针放行即通过。

## F3 — 布尔 OR 对只覆盖了「基线有数据」形态（空基线失效）

`BooleanBlindDetector._getBooleanPairs` 只有一对 OR 变体（`{ti:6, fi:7}`，且 risk≥2 才投放）：
真=`OR '1'='1'`、假=`OR '1'='2'`，对应 sqlmap 的「原值为空/负 → OR 恒真补出数据」语义，
只适用于**基线已有数据**的目标。

**空基线**（原值查不到行）下语义恰好相反：真条件应是 `OR '1'='2'`（仍空、≈基线）、
假条件是 `OR '1'='1'`（命中全表、≠基线）。故追加第二对 `{ti:7, fi:6}` 作为兜底，
排在所有 AND 对之后，仅当前面对全部失败才轮到。

代价：主轮未命中的点 +2 请求（已同步更新 `tests/clause.level2.test.js` 的请求数契约：8 → 10）。
关闭：`config.booleanOrFallback = false`。

## F4 — 真实 MySQL 靶场一键可复现

`e2e/real-mysql-lab/init-db.mjs` 从「只自检」改为「建库 + 建表 + 种子数据」，
种子刻意含中文 / 单引号 / 逗号竖线 / ID 跳号；默认端口 3307 → 3306；
`password` 默认值改用 `??`（本机 root 空密码不再被 fallback 成 'root' 而认证失败）。
同改 `real-mysql-lab/lab-app.js`、`verify.mjs`、`pentest-lab/lab-app.js`。

## F5 — 新增「插入式双写」tamper 插件（关键词静默过滤专用，已默认启用自动绕过）

> 更新（2026-09-10 晚）：本条原先只交付了「插件 + 手动链」，`filterAdaptive` 默认关。
> F8 的三项使能修复后自动重跑已生效，**`filterAdaptive` 改为默认开启**——
> 实测 `bl` 场景 `[error]`（830ms）→ `[error,boolean]`（1.2s），安全点零影响。


`core/tamper/plugins/keywordinterleave.js`（已注册，插件总数 227 → 228）

背景：真实过滤器分两类——
1. **只删一次**（`s.replace(/and/i,'')`）：`ANDAND` 与 `ANANDD` 都能绕过；
2. **全局删除**（`s.replace(/and/gi,'')`，更常见的自研/云 WAF 规则）：`ANDAND` 被删干净（语法错误），
   只有插入式 `ANANDD` 有效（删掉中间 `AND` 后正好剩 `AND`）。

现有 `nonrecursivereplace` 产出 `ANDAND`，只覆盖第 1 类。新插件造插入式中点双写
（`AND`→`ANANDD`、`UNION`→`UNIUNIONON`、`SELECT`→`SELSELECTECT`），两类下都成立，属严格更优解。

**必须与 `dash2hash` 同链**——过滤器通常同时删 `--`，只上双写会因注释符被删而语法错误。
实测链 `keywordinterleave,dash2hash`：

```
bl（删 union/select/and/or/--）  默认 [error] 830ms  →  套链后 [error,boolean] 94ms
```

用法：`--tamper=keywordinterleave,dash2hash`（也已导出为 `FILTER_BYPASS_CHAINS` 供自动路径消费）。

## F7 — 自动兜底链在 CRS 下必然空转（本轮修复）

`OPERATOR_SWAP_CHAINS` 原先以 `symboliclogical` 打头，而 **CRS 942120 的正则里直接写着 `&&` / `||`**
→ 三条候选链在 CRS 下必被拦 → 链验证全灭 → 自动重跑永不触发（日志实测：
`WAF 链验证：3 条候选链探针均被拦截，跳过自动重跑`）。

修正：按「通用收益」重排，`dash2hash` 提为第一位（减少标点是 CRS 下唯一有效方向），
并新增 `['dash2hash','hexliterals']`；`symboliclogical` 退居末位（它对关键词级黑名单才是正解）。
同时修正 ModSecurity 厂商链——原链含 `space2comment`（`/**/` 是 4 连非词字符，942460 必拦）
与 `versionedkeywords`（942500 定点检测），均为负收益，已替换为
`['dash2hash','hexliterals','uniontable','odbcbrace']`。

效果：自动路径技术位 **0 → 4**，日志可见引擎自行选中 `dash2hash`
（`WAF 链验证：[dash2hash] 探针放行`），安全对照仍零误报。新增 `npm run waf-auto` 作为该路径的验收脚本。

## F8 — 自动绕过路径打通（4 → 11 技术位，超过人工基线）

上一轮把自动路径从 0 拉到 4/10 后，用 `SQLI_UNION_DEBUG` 逐层插桩定位到**四个独立缺陷**，逐个修掉后
自动路径达到 **11 技术位**（人工挂 `dash2hash` 基线为 10）：

| # | 缺陷 | 证据（插桩原话） | 修法 |
|---|---|---|---|
| 1 | 自动链首位是 `symboliclogical`，而 CRS 942120 直接检测 `&&`/`\|\|` | `WAF 链验证：3 条候选链探针均被拦截` | 链表重排为 `['dash2hash','hexliterals'] → ['dash2hash'] → ['symboliclogical']` |
| 2 | 重跑复用主轮 boundary，而主轮探测 payload 不带 tamper、被 942460 拦光 → 空串 | `gate boundary="" truePayload="alice AND 1=1#" trueLen=138 falseLen=138` | 重跑前用带 tamper 的 config 重探（实测 `重探闭合前缀："" → "'"`） |
| 3 | 重跑候选只取「未命中点」，主轮只中 boolean 的点被排除 → union 永远补不上 | num/blind 卡在 8/10 | 候选放宽为「未命中 或 快速层技术位 < 2」 |
| 4 | 链验证的「响应缩水 50% = 软拦截」启发式套在链验证上 → payload 生效后结果集变空被误判 | `3 条候选链探针均被拦截，跳过自动重跑`（blind） | 链验证改 strict：只认状态码与拦截页文案 |

另修两处口径/接线的坑：
- `hexliterals` 必需与 `dash2hash` 同链——CRS **942300** 的正则含 `["'`]\s*?(?:[#\{]|--)`，
  **引号后紧跟 `#` 即拦**，而 union 的标记回显探测 `1 UNION SELECT 'SQLISCANNER0'#` 正是该形态；
  `hexliterals` 把标记转 `0x...` 去掉引号锚点后即通过。
- `waf-verify.mjs` 的 `off` 档必须同时关 `adaptiveOnBlock`，否则它不再是「无规避基线」
  （实测会串味成 3/3）；`off` 的值本身即 `wafEvasion` 内容，多套一层会被静默丢弃。

**干净 A/B（复验）**：`off 2/5 → on 10/5 技术位`，安全对照零误拦。

## F11 — 空基线下 union 缺失根因定位与修复（最后一条限制）

现象（`pentest-lab` 的 `ua` / `empty` 场景）：只出 `error,boolean`，union 恒 0。
**根因不在 union 检测器，而在闭合前缀探测的歧义**：

```
[union-debug] gate payload="Mozilla OR 1=1-- -" → 无引号闭合（boundary=""）→ 真假定同长 142
```

`probeBoundary` 用「响应 ≈ 基线」判定候选闭合前缀，候选表以空前缀 `''` 打头。
**参数原值查不到行**时（`WHERE username='Mozilla'` 恒 0 行），**所有**候选都落在同一个空结果页
→ 全部"相似于基线" → 取第一个即 `''` → 探针无闭合 → 真假同长 → 门控判「参数不在 SQL 上下文」。

修法（与门控空基线降级同源，`Detector.js`）：
当**多个候选同时相似**时，用 OR 型复核消解歧义——正确闭合时 `OR 1=1` 命中全表（偏离基线空页）、
`OR 1=2` 回到原空集（仍≈基线）；错误闭合则语法错误、两者都不像基线。
复核候选上限 4 个（`''` / `'` / `')` / `'))`），把探测预算钉死在 8 请求内。

**顺带修正一处误判**：`UnionDetector._gateInjection` 也补了 OR 型复判（AND 型判相似后追加）。

效果：`ua` `[error,boolean]` → **`[union,error,boolean]`**（2540ms → **823ms**，更快是因为
union 命中后不再走盲注回路）；`empty` 同步升为 `[union,error,boolean]`（777ms）。

**性能求证（避免"修复变拖慢"）**：`ua` 场景曾测到 96s，一度怀疑探测爆炸。逐层插桩后确认：
闭合探测仅 58ms、union 探针仅 7 条且无列枚举请求——**96s 全部来自命中后的拖库**
（`enableExtract=true` 且目标实例上有 netsec/agentdaily 等历史库）。
对照实测：`enableExtract=false` **283ms** / `true` 96s。即非本次改动引入，属预期行为。
