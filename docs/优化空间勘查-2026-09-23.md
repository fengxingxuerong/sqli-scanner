1. ❌ **C1 的核心推断错了**。原写「单点约 10–15 次字节级相同的请求」，实测**跨检测器完全相同的请求只有 1 种、冗余 5 份**（就是那份 `q=1` 基线，被 5 个检测器各发一次）→ **可省上界 5/148 = 3.4%**。

2. ✅ **真正的开销在 union / error 的 payload 试探**：两者合计 123 条 = **83%**，其中 `UNION SELECT` 52 条 + 报错类 45 条。
   ⚠️ 值得单独记一笔：`ErrorDetector.js:33-35` 的注释写着「避免原实现『无 dbms 时 14+ 库 × N 模板全量连发』的请求爆炸（43+ → **≤8** / 命中 2-4）」，

   「≤8 上限」只对 dbms **未知**那条分支成立；注释描述的是未知分支的收益，却没说已知分支没有上限。
   （62 条里我的分类器识别出 45 条报错类 + 13 条归入「其他变体」，合计 58，其余 3 条落在别的类别 —— 分类器只做归因展示，未覆盖全部变体写法。）
   **这是当前最大的可优化点**：把已知 dbms 的路径也加上限（或按 `ERROR_SIG_BY_DBMS` 的高频优先 + 上限）。
   **但省多少必须靶场验检出率**——本次只做到「把事实量出来」，没有改动任何代码。
   union 的 52 条超过了 `PAYLOADS.MySQL.union` 的 31 个模板，说明它来自「列位置 × 标记族」的组合试探（具体组合数未拆细）。

> 未采样（别当成「无浪费」）：time/stacked/oob（会真 sleep 或需真靶场）、提取阶段（需真实 DB 回显）、
> WAF 自适应重跑（需真被拦截）。本表是「最小配置 + 安全点」下的**下界**。
>
> 探针口径：所有检测器都收敛到 `httpClient.request(opts)`（`Detector.js:660`），故用记录型 stub 顶替

### D1. 体积门禁只数行 → 167 KB 的文件在盲区 `[事实]`

`scripts/arch-guard.mjs:50-53`：

```js

  const t = fs.readFileSync(path.join(ROOT, rel), 'utf8');
  return t.split('\n').length;   // ← 唯一判据
}
```

`MAX_LINES=1200` / `HARD_MAX_LINES=2000`（`:22-23`）。
`payloadRegistry.js` **983 行 / 167.2 KB / 平均 174 字节每行 / 567 行超 200 字符 / 最长 382** —— 22 行 import 之后全是单行对象字面量。它是**数据文件**，按代码行数管它本就不对，但 167 KB 单文件在 SEA/sidecar 打包与 diff 可读性上都是实打实成本，而门禁永远不会报警。

同一病：**8 个 800 行级文件挤在硬线 66%–84%，基线里一个都没登记**（`.arch-baseline.json` 只有 `httpClient.js: 1115`）。任何一个下次迭代都可能一次性撞线，而「只有撞线当天才被发现」正是这类门禁要防的。

缺口形式建议：给 `arch-guard` 加**第二判据**（字节数 / 平均行长），对数据型文件走数据型口径。这与 §Q「feature продуктов pessimistic」同源 —— 判据要能看见它声称在管的东西。

## J. E2 落地：枚举 / 拖库动作族打通三端（2026-09-23 第五段）

### J1 根因（比原先记的更具体）

原标题写「枚举动作族 REST 无端点」。核实后发现真相比"缺端点"更简单也更难看：

> **`extractScope` 从来没进过 REST 白名单。**

CLI 一路的做法是把 `--dbs/--tables/--dump/--dump-all/--users/...` 解析成 **`config.extractScope`**
交给引擎（`bin/cli/config.js:314 buildExtractScope` → `ScanManager._extractByScope`
→ `engine/extractScope.js:109` 的 18 分支 switch）。

而 `KNOWN_CFG_KEYS` 里**没有** `extractScope` → REST 传它会被当「未知字段」丢弃（只留一条 `logger.warn`），
调用方拿到 `200 + scanId`，报告写「未检出」。

**旁证**：`scanRoutes.js:845-846` 有一句 `delete merged.extractScope` ——
是重测端点为了「别把历史报告里继承来的枚举配置再跑一遍」而写的。
**代码知道这个键会出现在 config 里，但白名单不认它** —— 这处突兀的 delete 正是断链留下的疤痕。

所以不需要新增任何端点：**把键接进白名单 + 加校验 + 给 UI 入口**即可。

### J3 安全口径（为什么这里不做字符集白名单）

- 库名/表名/列名会被拼进 SQL，但**引擎侧所有拼接点都已过 `escSql()`**
  （`extractionMaps.js` 全文一致，形如 `WHERE table_schema='${escSql(db)}'`）。
- 在 REST 层再加窄字符集只会**与引擎口径并存成两份真相**，且真实库表名可能含中文/连字符/点号 → 误拒合法输入。
- 判据与危害同源：这里能造成的危害是「形状不对 → 引擎 `switch` throw / 无界枚举」，**不是注入**。
  故只校验形状。（`§D` 有一条测试专门断言单引号可进入标识符值，注释写明「若此处被拒，说明有人加了白名单，请先读口径注释」。）
- 相对风险参照：本项目**已有** `/api/exploit/sql`（任意 SQL 执行）、`file-read/file-write`、`os-shell`
  等远更强的入口（需 `EXPLOIT_ENABLED=1`）。枚举动作并不新增更高风险面。

### J4 顺带修掉一个守卫盲区

契约测试 ① 的「面板键」提取正则原先只认 `handle*('k')` / `setConfig('k')` / `set('k')` 三种写法。
本轮 UI 用的是 `onChange({ extractScope: … })` —— **整类写法不在视野内**（又是「守卫看不见它声称在管的东西」）。
