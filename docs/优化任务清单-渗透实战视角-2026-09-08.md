## P0 检出正确性（修了才敢说"能测"）

### 1. DBMS 指纹：补 SQLite 报错签名（实测已漏检 2/35）
- **问题**：`server/src/engine/payloads/index.js` 的 `ERROR_SIG_BY_DBMS` 不含 SQLite 特征。Python sqli-labs L04/L14（双引号括号场景，SQLite 靶场）指纹误判为 MySQL → payload 族错配 → 漏检。强制 `dbms=SQLite` 后立即检出（已实测）。
- **修改点**：
  - `engine/payloads/index.js`：`ERROR_SIG_BY_DBMS` 增加 SQLite 条目 `/unrecognized token|SQLite.*error|sqlite3\.\w+Error/i`（SQLite 三个典型报错形态）。
  - `engine/DBFingerprinter.js` 报错定库路径（L111-123 `dbmsFromError` 调用处）无需改动，自动生效。
- **验收**：新增单测（复用 sqli-labs.py 的报错文本 `unrecognized token: ""1"")"`）；Python sqli-labs L04/L14 在不指定 dbms 时检出；全量回归 1433+ 不破坏。
- **注意**：SQLite 报错特征要与 MySQL `near 'xxx' at line 1` 区分，正则锚定 `unrecognized token` 前缀即可，避免误吞 MySQL 报错（MySQL 报错也含 near）。

### 2. 未知 DBMS 指纹遍历耗时（time 场景 28.9s）
- **问题**：`DBFingerprinter` 报错定库失败后按 `TIME_VECTORS` 逐库注入时间向量粗筛（9 库串行），真实 MySQL 靶场 time 场景整扫描 28.9s（占 90%+）。SQLite 的 RANDOMBLOB 向量单条就要数秒。
- **修改点**：
  - `engine/payloads/index.js` `TIME_VECTORS`：顺序按"响应报错已排除的库"动态剪枝——若报错页已拿到某库报错签名，跳过该库时间向量；
  - `engine/DBFingerprinter.js`：时间粗筛并发化（参照 `Detector.sendConcurrent`，限并发 2-3；注意时间向量并发会互相污染延迟，建议每库向量间加基线 RTT 复核，或并发度=2 + 每向量后置 1 次基线复核）；
  - 命中第一库后立即停止（现状已是，保持）。
- **验收**：真实 MySQL time 场景整扫描 < 12s；mock e2e time_only 19 PASS 保持。
- **红线**：并发化不得引入时间误报——若并发实现复杂，优先只做"报错签名剪枝"（零风险，预计省 2-3 库）。

### 3. 堆叠检测的 baseline 延迟污染
- **问题**：`StackedDetector` 基线只测 1 次（L62-66），并发采样改造后若目标有排队延迟，5 样本并发同时打过去会互相排队，`effectiveThreshold = baselineMs + sleep*1000/2` 可能被并发排队时间触发误判。
- **修改点**：`engine/detectors/StackedDetector.js`：基线采样 2-3 次取中位数（复用 `sendConcurrent`，1 批）；并发采样后对"命中样本"追加 1 次串行复验（与 `blindRobust.extractVerify` 思路一致），复验不达标不确认。
- **验收**：新增抖动 mock 用例（随机 0-800ms 抖动 + 偶发排队延迟）不误报；真实靶场 stacked 检出保持。

## P1 检出深度（缩小与 sqlmap 的残差）

### 4. 边界闭合候选补全（8 → sqlmap 同级）
- **问题**：`engine/Detector.js` `probeBoundary` 候选 8 种，缺 `'))`、`")`、`'\`、数字直连减法（`1-1`）等 sqlmap 支持的形态；Python sqli-labs 的 `'))` 双括号场景目前靠 payload 矩阵硬试兜底（多花 10+ 请求）。
- **修改点**：`probeBoundary` candidates 增加 `'))', '")', "\\'"`（尾反斜杠转义场景）；探测顺序按命中频率先 `'`、`')` 再扩展。
- **验收**：mock paren/双括号场景请求数下降（e2e requestCount.max 不变但实际值降低）；无新增误报。

### 5. JSON/XML 请求体的注入点解析（覆盖率缺口）
- **问题**：`TargetParser`/`crawler` 只解析 query/form/cookie/header；JSON body 的嵌套字段（`{"user":{"id":"1"}}`）不做注入点发现。真实 API 场景（fp_json 对照里该场景请求 205 次全靠硬试）。
- **修改点**：`engine/TargetParser.js` 增加 JSON body 递归叶子节点发现（字符串/数值叶子 → bodyParams 路径如 `user.id`）；`engine/injection.js` `buildInjectionRequest` 支持按路径替换 JSON 叶子值（保持其他字段不变重序列化）。
- **验收**：fixture 新增 `json-nested` 场景（嵌套 JSON 注入）检出 union/error；fp_json 零误报保持。

### 6. 第二个参数联动探测（AND 联合注入）
- **问题**：某些注入点需要另一参数同时为有效值（如 `?a=1&b=2` 只保持 b 有效时 a 才进 SQL）。当前每个点独立测。
- **修改点**（可放 P2）：`scanRunner` 调度层在点失败时做一次"其他参数保原值、仅注入当前点"的确认轮（现状疑似已隐式满足，需验证——若已满足则关闭此项）。
- **验收**：构造 mock（联动参数）场景验证。

## P1 性能（实测数据支撑）

### 7. fp_strict 类"校验型报错"目标的请求削减（205 请求）
- **问题**：目标对任何非法输入返回同构 400 错误页时，预筛选判定"有信号"保守保留，完整检测 205 请求。sqlmap 同样全量测，但我们可以更聪明。
- **修改点**：`engine/ScanManager.js` `_prefilterPoints`：单引号探针报错后，追加 1 个"良性非法值"探针（如 `1zz9x`，无 SQL 特征）；若良性非法值响应与单引号探针**同构**（状态码+错误页指纹一致），判定为输入校验而非 SQL 报错 → 安全跳过。判定保守：两类响应有任一差异即保留完整检测。
- **验收**：fp_strict 205 → ~7 请求；新增单测：良性非法值同构跳过 / 异构保留；fp_noecho/fp_json 现有 5 请求表现不变。

### 8. 布尔盲注二分提取的字节级优化（Extractor）
- **问题**：`engine/Extractor.js`（1241 行）布尔盲注逐字节二分，每字节最多 7-8 请求；100 字符版本号 ≈ 700 请求。
- **修改点**：启用字符集感知——版本号/表名类提取按已知字符集（数字+点 / 十六进制+下划线）缩半区间；对 32 位 hash 类目标用位测试（`ORD(SUBSTR(...))&bit`）每字节固定 7 次封顶。
- **验收**：union_extract fixture 请求数不增；新增二分字符集单测；提取正确率不变（golden 对比）。

### 9. SQLite time 向量误触发全表扫描风险
- **问题**：`TIME_VECTORS` SQLite 用 `LIKE('ABCDEFG',UPPER(HEX(RANDOMBLOB(...))))` 延迟，参数 5000000 在低端机器上可能 >10s；且该向量在未知库探测阶段会打到所有未知目标。
- **修改点**：`engine/payloads/index.js`：SQLite 向量时长减半并夹上限（如 {SLEEP}0000000 → min({SLEEP},3)*1000000/2）；`DBFingerprinter` 粗筛阶段对 SQLite 向量加单次超时熔断（超时即跳过该库）。
- **验收**：mock 慢目标场景总时长可控；无新增漏检。

## P2 工程与安全

### 10. Payload 池的"真实 DBMS 合法性"回归防线（本轮教训固化）
- **背景**：本轮真实 MySQL 暴露 mock 正则匹配放行非法 payload（裸 SLEEP 1064）的问题。这是体系性风险——任何新加模板都可能再犯。
- **修改点**：新增 e2e `e2e/real-mysql-lab/payload-validate.e2e.js`：遍历 `PAYLOADS.MySQL.stacked/time` 全部模板，经 mysql2 真连执行（空库安全模板），断言无 1064 语法错误（允许语义类错误如表不存在）。CI 可选跑（需 MySQL 实例时跳过）。
- **验收**：当前模板全过；人为注入一条坏模板测试能红。

### 11. 报告脱敏补口（cookie 值进报告）
- **问题**：`scanRunner` 事件已脱敏（`publicTarget`），但 `report.points` 内 `originalValue` 若来自 Cookie 值（如 session token），导出 JSON/HTML 报告时原样带出。
- **修改点**：`services/ReportGenerator.js` 导出路径增加 cookie 参数值打码（保留首尾 2 字符）。
- **验收**：单测——cookie 注入点的报告导出中 token 值已脱敏；功能不受影响。

### 12. UI 扫描进度的时间盲注可视化
- **现状**：`result.trace` 已带 baseline μ/σ/阈值等结构化轨迹（TimeBlindDetector），前端 `src/pages/ScanPage.tsx` 未消费。
- **修改点**：ScanPage 检测中状态增加"时间盲注标定进度"小面板（基线 μ/σ、当前阈值、稳定率），数据源 `scan_progress` 事件里的 trace 字段。
- **验收**：真实扫描时 UI 实时显示标定参数；不影响现有事件流。

### 13. CLI 参数与 REST 白名单一致性守卫
- **问题**：`api/scanRoutes.js` KNOWN_CFG_KEYS 白名单与新配置键需手工同步（本次 `prefilterSinglePoint` 就是手动加的），漂移风险。
- **修改点**：新增测试：遍历 `config/defaults.js` 顶层键，断言白名单包含全部用户可配键（允许显式 internal 豁免清单）。
- **验收**：该守卫测试进 CI；故意漏一个键测试变红。
