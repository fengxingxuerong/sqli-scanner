## 批次 1 · CI #131 双红收口（commit cc31d73 / 远端 5582912）

### 取证路径（artifact → 速率账 → 源码）

1. `e2e-self-contained` 与 `acceptance` 两个红 job 的 artifact（run-all 日志 / 验收报告 /
   batch-lab 失败现场）显示**同根**：batch-lab C1 限速判据失败 ——
   3 目标、上限 6 req/s，实测 **19.53 req/s**。
2. 速率账：C1/C2 请求总数同为 237；CI 上 C1 用时 12.5s ⇒ 237 ≈ 3 × (6 × 12.5 + 突发)。
   **19.5 ≈ 3 个独立的 6 req/s 桶**；共享桶生效应为 ≥39.5s。
3. 源码定位：`bin/cli/config.js` 的 `buildConfig()` 是显式键清单，`rateGroup` 没在表里
   ⇒ CLI 批量生成的组 id 到不了 `target.config` ⇒ `getScanClient` 拿到 undefined
   ⇒ 每目标各建 per-scan 桶。REST 路径（scalarsCore 白名单）一直是对的。

### 为什么本机一直是绿的（又一个「单机绿 ≠ 判据验过」）

本机 Windows 的引擎逐请求 CPU 开销把自然发包率压在 7.5 req/s 判据之下，桶是否共享根本
不可观测；CI 的快机器才让缺陷显形。与 09-09「系统代理假阴性」同款教训：
**判据只有在它声称管辖的条件成立时才真正被验证过**。

### 修复与加固（三层）

| 层 | 改动 |
|---|---|
| 根因 | `buildConfig` 透传 `rateGroup`（值由 cli.js 内部生成，形态与 REST 收紧同口径） |
| 解析加固 | `_resolveRateBucket`：rateKey 查不到 ⇒ 同 key **惰性重建**，绝不回退 per-scan/rate 桶（回退 = 总量保证在异常路径静默失效）。forScan 视图补注 `ratePerSec` —— 单测抓出首版「重建成不限速桶」缺陷（effectiveRate undefined ⇒ createBucket 归一为 0）后补的 |
| 生命周期 | 组桶引用计数：forScan 注册（scanId→rateKey + 计数），退役 `releaseGroupBucket`，最后一个成员退役才删桶。收掉 REST 长驻进程每批泄漏一个 TokenBucket 的无界增长 |

### 守卫缺口（本批最值钱的教训）

`rateGroup.wiring.test.js` ⑤ 只钉了「CLI 生成了组 id 变量」，没钉「组 id 进了 target.config」
—— **登记 ≠ 有入口** 的又一次兑现。新增 ⑤b：真调 `buildConfig` 断言透传与缺省不造键
（行为判据，不是源码文本）。缺陷注入复验：注释掉透传行 ⇒ ⑤b 红（杀）。

### CI 卫生（顺带）

⇒ 验收报告每次自陈「工作区 dirty，不对应任何提交」，版本凭证恒失效。步骤后
`git checkout --` 还原（`if: always()`）。

## 批次 3 · WAF 链侧能力：搜索器补「减标点补位 + 三链组合 + 有序去重」

评价文档定性「提打穿链数必须动链侧，不是再写第 229 个 tamper」。本批在 A2 架构内修生成器
的三个质量缺口：

1. **dash2hash 进不了候选池**（covers=0 被 `.filter(covers>0)` 挡住）—— CRS 标点预算方向
   唯一实证有效项从生成器里整体消失。修法：消除者/减标点补位分池，补位只作第二三槽位、
   不占定向名额、两序都生成。
2. **被拦词族 ≥3 时双链覆盖不满** —— 每类别取最优消除者再跨类别组三链
   （不能用 pool 前 3 名两两配：quote 被拦时前几名可能全是 LITERAL 类 ⇒ 三链恒空）。
3. **去重键用排序集合** —— 变换复合不可交换，两个顺序被折叠成一条
   （`push` 与 `mergeCandidateChains` 两处；后者此前连静态表自己的两种实证顺序都吃掉一半）。

验证：39/39 单测（+4 新用例，注入复验杀 3）；`waf-bypass-search` e2e ✅（A=2/B=0/预算 6:6）；
`waf-real` PL1 对外口径零变化；`tamper-matrix` exit 0。

**回归排查留证（waf-auto PL1）**：本机跑 `CRS_PL=1 npm run waf-auto` 得自动技术位 0
（CI #133 同套件=8）。做了对照实验——把 searcher 换回批次 C 前版本重跑：**同样 0**
⇒ 不是批次 C 引入的回归，是本机实验室（本地 MySQL 8.0.28 + 本机扫描动力学）与 CI
（8.0.46 + 服务化初始化）的既有差异。批次 C 改的只有「第 3 个验证名额（生成链）」的内容，
静态前两名的选取与排序零改动；CI #134 的 acceptance 将给出批次 C 在 CI 侧的实证结论。
