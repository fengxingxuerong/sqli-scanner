## 一、这一批吸收的是什么

不是"再加几个插件"，而是**一条外部判据**。

本仓关于 tamper 的两条既有门都是**自报的**：

| 既有门 | 它证明的事 | 它证明不了的事 |
|---|---|---|
| `tamper:parity` | 官方有的插件，本仓有**同名**的 | 同名是不是同行为 |
| `tamper.doctest.test.js` | 本仓 transform 符合**本仓自己写的**期望 | 期望本身是不是抄错了 |

⇒ 把 `A→B` 翻译成 `A→C`，并顺手把期望写成 `C`，两道门能同时绿。
这正是本仓反复在治的那类缺陷（"声明与真值分处两地"）。

上游 docstring 里的 `>>> tamper(输入) / 期望输出` 是**第三方出的卷子**：同一条输入、
同一个期望，由上游作者为其真实行为背书。本批把它做成门禁：

```bash
npm run tamper:examples            # 离线校验（快照已入库，CI 无网络也能跑）
npm run tamper:examples:refresh    # 从 tag 1.10.10 重新抽官方示例
```

新文件：`scripts/verify-tamper-upstream-examples.mjs`
入库快照：`server/src/core/tamper/upstream-sqlmap-doctests.json`（79 个插件 / 126 条官方示例）
豁免账：`server/src/core/tamper/tamper-upstream-examples-baseline.json`（25 条，逐条写原因）

判据形态说明（避免"看起来严其实空"）：
- **字面比对**上游示例；插件两次调用输出不同 ⇒ 判为随机性，**逐条点名跳过**（本轮 10 条），不静默；
- 上游已无该示例 / 本仓已改成与上游一致 ⇒ 豁免账里的该条**被点名失效**并提示 `--prune-baseline`
  （已用注入法验证：塞一条 `castprefix#0` 假豁免 ⇒ 门如实点名）；
- 本仓无同名插件 ⇒ 点名（本轮 0 条）。

## 三、修掉的 4 条（其中 1 条是"测试把缺陷钉成了期望"）

| 插件 | 上游行为 | 本仓此前行为 | 定性 |
|---|---|---|---|
| `equaltorlike` | `id=1` → `id RLIKE 1` | `id=1` → **`idRLIKE1`** | 🔴 **产出非法 SQL**：三个 token 融成一个标识符，比较整个消失。兄弟件 `equaltolike` 早在 `[T4]` 就补了空格，本件漏改（同型缺陷只修了一半）。更坏的是静态规则型绕过矩阵会把 `idRLIKE1` 记成"绕过成功" ⇒ **废插件在报表里看起来有效** |
| `between` | `>` 与 `=` 两条分支 | 只有 `>`；且不消费两侧空白 ⇒ `A > B` 叠出双空格 | 🟠 覆盖缺口 + 形态漂移。`x = y ⟺ x BETWEEN y AND y` 严格等价、无边界损失，此前整条缺失 |
| `least` | `a > b` → `LEAST(a,b+1)=b+1` | 只有本仓自加的 `a < b` 分支 | 🟠 覆盖缺口（既有 `<` 分支保留，不回退） |
| `informationschemacomment` | 保留原大小写 | 替换串写死小写 ⇒ `INFORMATION_SCHEMA` 被改成 `information_schema` | 🟠 MySQL 上看不出来，**Oracle / PostgreSQL 的引用标识符区分大小写** ⇒ 静默换了一个对象名 |

**元缺陷（比单条插件更值钱）**：`server/tests/tamper.test.js:434` 原本断言
`transform('1=1') === '1RLIKE1'` —— 自写测试把非法 SQL 钉成了期望。已改为 `'1 RLIKE 1'` 并就地留痕。
⇒ 自写 doctest + 自写测试同源，是"全绿而行为坏"的标准成因；本批的外部卷子正是为拆这个闭环。

## 四、新判据：`server/tests/tamper.tokenBoundary.test.js`（5 条）

## 十二、D9 落地：5 条 MySQL 8 版本门条目 + 补丁级门

路线定了就做，全部结论有实测出处：

| 条目 | 形态 | 声称下限 | 真库 8.0.28 差分 |
|---|---|---|---|
| `mysql-bool-cte-80` | 递归 CTE 标量子查询 | 8.0.0 | ✅ 真=1 行 / 假=0 行 |
| `mysql-bool-window-80` | `ROW_NUMBER() OVER (ORDER BY NOW())` | 8.0.0 | ✅ 同上 |
| `mysql-bool-lateral-8014` | LATERAL 派生表 | 8.0.14 | ✅ 同上 |
| `mysql-bool-valuesrow-8019` | `VALUES ROW()` 表值构造器 | 8.0.19 | ✅ 同上 |
| `mysql-bool-jsonvalue-8021` | `JSON_VALUE()` | 8.0.21 | ✅ 同上 |

- **地基先行**：`versionAtLeast` 旧实现只比到 `major.minor` ⇒ `8.0.21` 会被读成 `8.0`，条目会投到
  8.0.0-8.0.20 拿运行时错误。现支持补丁级（`patch` 缺省时从 `raw` 第三段现算，不动 8 个解析返回点），
  schema 侧把 `minVersion: 8.019` 这种"一位小数编码"的歧义写法**当场拒**。
- **与执行同源**：靶场 `e2e/real-mysql-lab/versionedForms.e2e.mjs` 不抄 SQL，而是从注册表取条目、
  用引擎自己的 `fillPayload` 渲染后在真库跑 ⇒ 测的就是发出去的那串；已入库条目失败判红(exit 1)，
  候选区失败不判红（研究区）。连不上 MySQL 一律 exit 2（SKIP 口径，与同目录 `payload-validate` 一致）。
- **两条被钉住的坑**：① 窗口里 `ORDER BY 1` 报 `ER_WINDOW_ILLEGAL_ORDER_BY`（裸数字被当列序号）
  ⇒ 靶场候选区留着当反向对照；② "能不能扩到引号上下文"实测**不能**（4 条无差分、JSON_VALUE 直接 1064）
  ⇒ 条目只声明 `boundary: [""]`，且 `payloadVersion.patch.test.js` ⑤ 钉住"声明边界 == 实测边界"，
  扩上下文必须先补真库差分，不许"顺手多声明一个边界"。
- 投放矩阵断言做成**每条都必须在某些版本退场**（8.0.28 五 / 8.0.19 四 / 8.0.14 三 / 8.0.0 二 / 5.7 零），
  否则"写了 minVersion 形同没写"这类空门就又混进去了 —— 这正是 D8 那条入口断链的同一族。
- 指纹基线 681 → **686**，两个 SHA 抄测试自己打印的 actual（不自己算）。
- ⚠️ **仍未知**：这 5 条形态在**真机 CRS** 下的打穿率（本仓唯一真机口径是 CI 的 modsec-live，
  本地跑不了）⇒ 与 D7 §六 T-6 同一证据要求，别把"语法可用"读成"能过 WAF"。

- **A3（抖动下逐字符多数投票）未开工** —— 全仓 `majority|vote|reconfirm` 0 命中（sqlmap 1.10 的
  `kb.jitterSeen` ⇒ "escalates to a majority vote"；ghauri 也有 verify extracted characters）。
- 上游 `--timeless`（HTTP/2 完成顺序时序 oracle，USENIX Sec 2020）只做了可行性勘查，未实现；
  本仓 h2 目前只服务爬虫/取页（`crawler.js:169`、`TargetParser.js:385`、`core/http/transport.js:92`），
  检测与时间通道仍在 h1。
- **T-1…T-10 全部未做**（尤其 T-6 版本注释族与 T-4 双反斜杠族，本地口径判不了，要 modsec-live 真机）。


## 十三、A2 落地：base64url 编码态载体 + 交付面标注（含一次"通过得太便宜"的自我否决）

### 真缺口核对（撤回假结论之后剩下的）

| 形态 | 此前 | 现在 |
|---|---|---|
| 标准 base64（`MQ==`）/ `0x` hex | ✅ 已实现（paramEncoding，2026-09-11） | 不变 |
| **base64url 无补齐**（`dXNlcg`、含 `-`/`_` 的 `fn5-`） | ❌ 漏（标准分支要求长度是 4 的倍数） | ✅ 识别 + 按同规则重编码 |
| JWT 三段（`h.p.s`） | ❌ 无 | ❌ **仍不做**，理由见下 |

base64url 分支刻意排在标准 base64 **之后**且要求串内无 `+` `/`：两族只差在 62/63 两个字符，
错标成 base64url 会让该点所有请求带上 `-`/`_`，严格解码的服务端直接解坏 ⇒
**一个正常可注入点被打不动**（比漏识别贵，与 `paramEncoding.js` 头注释同一口径）。
`字母表重叠护栏` 那条单测就是钉这件事（`U0VDUkVULVRPS0VO` 必须判 base64，不许被抢）。

### 一次自我否决：靶场第一版"通过得太便宜"

`/b64url` 路由首版写的是"解不出可打印明文就按原值拼 SQL"。跑出 **11/11 PASS**，
但我去报告里找 `base64url` 标记时发现**一次都没有** ⇒ 通过的是**回退分支**：
原始 payload 里的引号本来就能 breakout，特性根本没参与。改成**严格解码**（不留原值后路）后：

| 运行 | 结果 |
|---|---|
| 特性开（base64url 识别在） | `[PASS] b64url 检出=[union,boolean]`，11/11 |
| 特性摘（`paramEncoding` 那条分支短路） | `[FAIL] b64url … miss=[boolean]`，10/11（其余 10 场景不受影响） |
| 还原再跑 | 11/11 PASS |

⇒ 这才叫**能区分的测试**；第一版那种"绿"是靶场宽松造成的假证据。
教训与仓内纪律同源：**新靶点必须先问"特性摘掉它会不会红"**。

### 交付面（引擎做对 ≠ 说清）

`poc.payload` 是**解码后的语义形态**，而 `url/curl/raw` 是重编码后的**线上形态**。
本轮在 `pocBuilder.buildPocRequest` 里给带 `point.encoding` 的点补了一句 note
（`参数值以 base64url 传输：payload 是解码后的语义形态，url/curl/raw 已按同规则重新编码，复现请直接用 curl/raw`）。
变异自证：摘掉这条 note ⇒ `poc.encodedCarrier.test.js` ①③ 红、② 仍绿。

### 仍然不做的两条（写清理由，不是遗漏）

- **JWT 分段注入**：现有编码模型是"整个参数值 = 语义值的编码"，而 JWT 的可注入面在
  **payload 段内部的某个叶子**——把 SQL 拼到解出来的 JSON 文本尾部产出的是非法 JSON，
  服务端 JSON 解析先炸，与"宁可不发现也不发畸形报文"冲突。要做需要复用 JSON 叶子点位机制
  + 签名语义（多数实现验签后根本不用解码值），是独立一批的设计量。
- **长度下限 `s.length < 4`**：`MQ`（base64url 的 `1`）因此不识别。把 floor 降到 2 会把
  `a-`/`MT`/`1_` 这类正常短值卷进误标面，而误标代价是整点打不动。用单测把这个取舍钉住
  （`刻意保守的下限留痕`），要放宽得先拿出"反例集不被误标"的证据。
