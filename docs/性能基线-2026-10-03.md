# 性能端到端基线（2026-10-03）

> 回应 `docs/项目评价-2026-10-03.md` §三.H 的缺口：「只有单点下界（perf:budget 96 请求），
> 没有**整站扫描耗时**基线」。本文件建立第一个整站口径的基线，全部数字来自
> `docs/sqlmap-benchmark/results-level1-runs3.json`（23 关 × 3 轮，同机同批实跑，
> 复现命令见文末）。

## 基线数字（2026-10-03，本机 Windows / Node 24 / SQLite sqli-labs 靶场）

| 口径 | 我方 | sqlmap 1.10.7（--level=1 对照） |
|---|---|---|
| 整站扫描（23 关全检出）总耗时 | **2.675s**（每关中位耗时之和） | 30.3s（命中 14 关的耗时之和；未检出的 9 关另计） |
| 单关中位耗时 | 123ms（最慢一关 170ms） | 2.2s（中位） |
| 请求量 | 见 `npm run perf:budget`（最小配置 + 安全点 = 96 请求/点，逐通道分解见 README「性能」章节） | 未计数（sqlmap 侧无该口径） |

- 我方 23/23 关全部 3/3 轮稳定命中 —— 耗时数字不是「捡了快的那轮」：多轮中位下
  每关 ~92-170ms，整站 23 关连续扫完 **2.7 秒**。
- 对照组同口径 30.3s（且只覆盖 14 关）⇒ 整站吞吐差约 **11 倍**（该对照是 --level=1
  浅配置；这不是「sqlmap 慢」的普适结论，是同档位同靶点的实测）。

## 口径纪律（防这份基线被误用）

1. **机器相对量，不是绝对承诺**：本基线产生于一台具体机器。换机器/换负载，绝对值会漂；
   可跨环境比较的是**同机对照倍率**（11×）与**请求量**（perf:budget 的 96 请求/点，
   请求量与机器无关）。
2. **覆盖边界**：23 关是 sqli-labs 检测型场景（无拖库/无 WAF 前置）。WAF 场景的优化
   验收纪律已立（README「性能」章节）：凡涉及 WAF 的耗时结论必须带 tamper on/off 对照。
3. **未采样通道**：拖库（extractScope dump）、时间盲注重试、爬虫/浏览器发现的请求量
   不在 96 请求预算内，各有独立触发条件 —— 声称「整站请求量」时不得引用 96 这个数。

## 复现

```bash
node e2e/sqlmap-benchmark/run.mjs --runs=3     # 多轮中位基准（本文数字来源）
npm run perf:budget                             # 单点请求预算（stub 计数，无网络）
```
