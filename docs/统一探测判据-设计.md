# 统一探测判据：设计（把「二分探测」的判据收敛到一处）

> 状态：**设计稿，未实施**　编写：2026-09-17 19:53
> 起因：客户端提取链三层缺陷逐层挖出来后，发现**深层病根是同一个**。

---

## 1. 病根：同一个模式出现了三次

| # | 位置 | 二分求什么 | 上限 | 实测表现 |
|---|---|---|---|---|
| 1 | `columnGuess.js` | 列数（`ORDER BY n`） | 50 | 恒 200 目标上收敛到 50 → UNION 提取必败 |
| 2 | `blindExtractor._extendLength` | 字段长度（`LENGTH()`） | **65,531** | 恒 200 目标上扩展到上限 → "提取 alice" 变成"提取 6.5 万字符" → 超时 |
| 3 | `_timeBinarySearch`（时间通道） | 长度/字符 | —— | **未验证，疑似同类**（下一步查） |

**共同形态**：

```
二分判据只有「真/假」两态，而真/假的来源是「响应差异」
  → 目标恒 200 + 错误页回显时，差异被抹平（实测：错误页 209 vs 正常页 224，远超阈值 106）
  → 二分失去方向 → 一路判「真」→ 顶到上限 → 下游拿着荒谬的值继续跑
```

**为什么危险**：三处的「顶到上限」**都不会报错**，而是**静默地拿着错误值继续**——
列数 50 会构造出必然失败的 UNION；长度 65531 会让提取跑上百倍请求直到超时。

---

## 2. 设计目标

1. **判据有第三态**：不只「真/假」，还要能表达「**这个判据在本目标上不可信**」；
2. **只在必要时才启用备份判据**（保证既有目标零额外请求、既有测试零回归）；
3. **统一入口**：新增探测点时不再各写一份二分，避免第四次出现同样的病；
4. **上限即可疑信号**：收敛到上限本身就该触发自检，而不是被当作正常结果返回。

---

## 3. 统一 helper 设计

### 3.1 接口

```js
/**
 * 二分探测（列数/长度/字符/任意单调量）
 * @param {(n:number)=>Promise<any>} probe        发探测请求
 * @param {object} o
 * @param {number} o.lo
 * @param {number} o.hi
 * @param {(res:any)=>boolean} o.judge            主判据（原逻辑：真=偏大 / 假=偏小）
 * @param {(res:any)=>string}  o.shape            响应骨架提取（用于备份判据）
 * @param {number} [o.maxReasonable]              合理上限；超过即判「探测不可信」
 * @returns {Promise<{n:number, reliable:boolean, capped:boolean}>}
 */
export async function binaryProbe(probe, o)
```

### 3.2 两段式（沿用 M2 已验证的结构）

```
第 1 段：只用 judge 跑完整二分（既有目标行为完全不变）
         → 若结果 < hi（没顶到上限）→ 直接返回，零额外请求

第 2 段：仅当顶到上限时（capped），才做形态自检：
         · 取 probe(lo) 与 probe(hi) 两个端点响应的骨架
         · 若两者骨架可区分 → 用「与 hi 端同形即判偏大」的备份判据重跑
         · 若不可区分 → 返回 { capped:true, reliable:false }
```

### 3.3 调用方对 `capped/reliable` 的处置（关键，不能只是记个日志）

| 调用方 | capped 时的正确处置 |
|---|---|
| 列数 | **返回 null 而非 50**，让 UNION 路径放弃（而不是构造必然失败的 payload） |
| 长度 | **判定长度探测失败**，放弃该字段（而不是逐字节提取 65531 个） |
| 任意 | 报告里标注「该字段/该点未确认」，与项目既有的 `summary.constraints` 一致 |

> 这一条比"加判据"更重要：**今天三次事故里，判据失效只是起因，拿错误值继续跑才是伤害**。

## 6. 诚实的边界

- **本设计只解决"判据失效导致的顶到上限"**，不解决"判据本身不够好"
  （例如目标刻意做成真假无差异时，任何判据都无能为力——那时正确行为是**报"未确认"**）；
- 阶段 2 的「长度上限 4096」是**经验值**，需在真实目标上抽查；
- **阶段 3（时间通道）未验证**，标记为待查，不预设结论。

## 6.6 阶段 2 首次尝试：失败根因 = **判据方向反了**（2026-09-17 20:05，未修）

把 `_binarySearch` 改为调用 `binaryProbe` 后，**21 个提取测试失败**。读
`tests/extractor.lenExt.test.js` 的 mock 后定位到一句话根因：

```js
// _binarySearch 原版：test('>mid') 为真 ⇒ 真实值 > mid ⇒ mid 偏小 ⇒ 往上
if (ok) { found = mid; lo = mid + 1; }

// binaryProbe 的 judge：返回 true 表示「值偏大」⇒ 收缩上界
if (over) b = mid - 1; else { ans = mid; a = mid + 1; }
```

**两者的方向语义相反** —— `_binarySearch` 的 `truthy(x > mid)` 意味着「mid 偏小」，
而 helper 的 `judge` 期待「结果偏大」。直接套用等于**把二分倒着跑**。

**修法**：
- **推荐**：给 `binaryProbe` 增加 `direction: 'gt' | 'lt'`（或在文档里把判据语义钉死为
  「**该 mid 是否偏小**」），让两种调用各自表达清楚：
  · `columnGuess`：`ORDER BY n` 失败 ⇒ **mid 偏大** → `direction: 'gt'`
  · `_binarySearch`：`x > mid` 为真 ⇒ **mid 偏小** → `direction: 'lt'`
- 临时方案：调用处反转 `judge`，但可读性会变差。

**一个有利条件（已确认）**：这些 mock 的响应是 `'OK'`（2 字节）/ `''`，
而 `endShape` 有 `hiShape.length < 8` 的门槛 → **备份判据会自动禁用** →
两段式对这些 mock **不会多发请求**。所以**修好方向后，这 21 个用例理论上应直接通过**
（等价于原逻辑），不需要改动测试。

**另一条经验（补充到第 7 节）**：迁移到新抽象之前，**必须先把目标测试的 mock 语义读出来**
—— 本次就是靠 `extractor.lenExt.test.js` 里的 `/LENGTH\(\(.*?\)+\s*>\s*(\d+)/` 与
`? 'OK' : ''` 两行，才看清方向问题的。

## 7. 一句话

> **同一个病根出现三次，说明它不是 bug，是缺少一处该有的抽象。**
> 列数、长度、字符都是"二分探测"，就该共用同一套「判据 + 备份判据 + 上限自检 + 错误值处置」。

## 8. 迁移前必做：先读 mock 语义（本次血的教训）

阶段 1（列数）一次成功，阶段 2（长度）一次失败 —— 差别只在**动手前有没有读测试的 mock**。

| 阶段 | 动手前做了什么 | 结果 |
|---|---|---|
| 阶段 1 列数 | 先把 8 个 mock 的 n 边界与断言列成表 | **一次通过**（10/10） |
| 阶段 2 长度（首次） | 直接套用列数的成功经验 | **21 个失败** |

**具体教训**：`_binarySearch` 与 `columnGuess` 的**判据方向相反**
（前者"判据为真 ⇒ mid 偏小 ⇒ 往上"，后者"判据为真 ⇒ 结果偏大 ⇒ 往下"）。
这个差异**只有读 mock 才能看出来** —— 单看两个函数的代码，都会被"二分"这个外壳骗过去。

**固化为流程**：迁移任何二分探测到 `binaryProbe` 之前，先回答三个问题：
1. 判据为「真」时，**mid 是偏大还是偏小**？（决定 `direction`）
2. mock 的真/假响应**长什么样**？（决定 `shape` 的骨架门槛是否够用 —— 本次 `'OK'` 只有 2 字节，
   低于 `endShape` 的 8 字节门槛，所以备份判据自动禁用，等价于原逻辑）
3. 哪些断言是**请求数**断言？（新判据若多发请求会打乱它们）
