## 官方 AI 报告网关套件（ai-gateway / D228）实测：FAIL（如实，非 SKIP）

单网关、全程无并发、无其他请求占用；同一 key 的三角色串行流水线：

| 网关 | 参数 | 结果 |
|---|---|---|
| B 192.168.151.151:18080 | TIMEOUT=180000 / MAX_TOKENS=8192 | analyst 60s 超时 → writer → reviewer 429 冷却 60s，全挂 |
| B | TIMEOUT=300000 / MAX_TOKENS=2048 | 首轮 analyst 即 429，三轮降级全挂 |
| A 127.0.0.1:8080 | TIMEOUT=300000 / MAX_TOKENS=2048 | analyst 100s 超时 → 降级连环 429，全挂 |

根因（读 server/src/services/ReportAI.js 坐实，不是推断）：
- 三角色串行；callLLM 每步硬超时 = timeoutMs/3；MAX_TOKENS 默认 8192
  （AI_REPORT_MAX_TOKENS 可覆盖），推理模型生成长输出 >60s。
- 429 时 markKeyFail 冷却 60s；run.mjs 把 KEY_1/2/3 全设成同一个 key，
  所以「跨角色降级」等于原地等待，连续请求又撞 "user/model concurrency limit exceeded"。
- 网关侧硬约束：glm-5.3（非 flash）A=429 model concurrency limit exceeded、
  B=502 upstream exceed quota limit；**只有 glm-5.3-flash 可用**。
  短请求串行 + A/B 轮换则全部 200（见上 14 场景）。

边界：本轮只做实测，未改 ReportAI、未放宽任何验收断言。
要跑通套件需 ① ReportAI 支持多网关/多 key 真分担（而非同 key 降级）
② 按推理模型调 MAX_TOKENS 与 per-step 超时 ③ 429 退避改成换网关而非 60s 冷却。
