### ⚠️ P1-A：内部计数空转 + validity 误报（**严重度已更正**）

> **重要更正（18:39）**：本节最初被定为「P0、对目标有实际危害（19,000 req/s）」。
> 用**外部可观测事实**复核后**推翻**了该结论 —— 见下方验证。

**外部验证（MySQL `Questions` 计数器差值）**：
```
扫描前 Questions = 22766
扫描后 Questions = 22969
差值（真实到达靶场的 SQL 查询数）= 203      ← 而 --max-requests 设的是 200
工具自报 counts.total = 327875
```

**读法**：
- **真实到达目标只有 203 次**（≈ 上限 200 + 少量探测开销）→ **`--max-requests` 实际是生效的**；
- `counts.total = 327875` 是**工具内部计数**，**不是真实发包数**；
- 上限检查在「发送之前」就 `throw`（`httpClient.js:1150` `if (err instanceof AppError) throw err;`），
  所以**目标没有被洪泛**。

**由此更正两处结论**：
| 原结论 | 更正后 |
|---|---|
| 🔴 P0「对目标有实际危害，19000 req/s」 | ❌ **错误** —— 真实请求 203 次，**不伤目标** |
| 「`--max-requests` 未生效」 | ❌ **错误** —— 上限生效了 |

**真实存在的问题（降级为 P1，但仍需修）**：
1. **内部空转**：上层循环吞掉上限错误后持续重试，空转 **327,875 次**、烧掉 **33 秒 CPU**；
2. **`validity.status` 误报为 `unreachable`** ✗ —— 而目标**完全可达**（真实响应 203 次全部成功
   抵达靶场）。这是**报告正确性问题**：用户会误以为目标挂了，而实际是工具自己空转；
3. `failStreak=327672` 同样被内部空转污染，使「有效性判定」失去意义。

### 结论修正

M3 的"7 分钟无产出"**不是慢，也不是死循环**，而是：
**提取阶段进入失败重试风暴 → 32 万次请求 → 最终由 validity-guard 熔断收场**。

**触发条件**：目标恒 200 + 错误页回显 SQL（列数探测失效，猜列 50）→ UNION 提取按 50 列构造
→ 请求全部失败 → **失败未被当作"该停"的信号**。

**优化方案（可落地，按优先级）**：
1. **把 `--max-requests` 接到提取/重试路径**（当前只有部分阶段接）—— 硬上限必须先落地
2. **连续失败退避**：同一注入点连续 N 次失败 → 指数退避 + 最终放弃该点（而不是全速重试）
3. **熔断阈值大幅下调**：validity-guard 的连续失败阈值应从「数十万次」降到「几十次」量级
4. 修复 M2（列数探测）后，该场景的失败根源消失，但 **1–3 是独立的安全网，必须做**

### P0-A 根因定位（12:31，已锁定到具体代码行）

上限检查**存在**，在 `server/src/core/httpClient.js:1017–1027`：

```js
if (opts.maxReq && opts.maxReq > 0 && opts.scanId) {      // ← 三个条件必须同时成立
  const count = this._requestCounts.get(opts.scanId) || 0;
  if (count >= opts.maxReq) {
    throw new AppError(ErrorCode.HTTP_ERROR, `请求上限已达（maxReq=${opts.maxReq}），拒绝新请求`);
  }
  this._requestCounts.set(opts.scanId, count + 1);
  this._evokeRequestCounts();   // 兜底淘汰
}
```

**注意它的注释**（说明作者当时就知道风险）：
> 仅对归属明确（带 scanId）的请求计数：无 scanId 的请求无法在扫描结束时回收计数，
> 用统一 key 会导致 ① Map 无界增长 ② 达到上限后全局永久拒绝新请求（不可恢复）。

**所以设计上就存在一个"两端都不好"的取舍**：带 scanId → 可能漏传导致不生效；
不带 → 全局永久拒绝。当前实测说明**走到了"漏传导致不生效"这一侧**。

**诊断结果（12:41）——H1、H2 双双被推翻，真因更糟**：

```js
// 临时诊断（打印走到检查的序号 + 当时的 count），--max-requests 200
[MAXREQ-DBG] seen=195  maxReq=200 scanId="jrb8QPOoGu6E" count=194
[MAXREQ-DBG] seen=200  maxReq=200 scanId="jrb8QPOoGu6E" count=199
[MAXREQ-DBG] seen=201  maxReq=200 scanId="jrb8QPOoGu6E" count=200   ← 此处 count>=maxReq，throw 已触发
[MAXREQ-DBG] seen=205  maxReq=200 scanId="jrb8QPOoGu6E" count=200   ← count 不再增长，但 seen 继续涨
[MAXREQ-DBG] 走该检查的请求总数 = 327875（与报告 counts.total 完全一致）
```

**读法**：
- `maxReq` / `scanId` / `count` **全部正常**（H1、H2 不成立）；
- **所有 327,875 次请求都走到了这个检查**（`seen` 与总数一致）→ 不是"绕过检查"；
- **`count` 卡在 200 不再增长** → 说明**每一次调用都命中 `count >= maxReq`，每一次都 `throw`**；
- **但 `seen` 仍一路涨到 32 万** → 说明 **`throw` 被上层吞掉后循环继续**。

### 🔴 P0-A 精确机制

```
count 达到 maxReq
  → 每次调用都 throw AppError('请求上限已达')
  → 该错误被归为「可重试」→ 在重试/调用循环里被 catch 吞掉
  → 循环继续 → 再次命中同一条件 → 再 throw → 再被吞
  → 死循环（32 万次），直到 validity-guard 兜底熔断
```

**一句话**：`--max-requests` 的上限错误**被当成"可重试的临时故障"**，
于是它不但没能终止扫描，反而变成了**无限重试的燃料**。
现有 `NON_RETRYABLE_CODES` 机制（`httpClient.js:198`）**没有覆盖这个错误码**。

### 修法（明确、可落地）

1. **把「请求上限已达」归入不可重试**（`NON_RETRYABLE_CODES`）—— 命中即立刻向上抛，不再重试；
2. **同时置终止标志**：`this.maxReqExceeded = true`（或触发扫描级 `AbortController.abort()`），
   让**上层所有循环**都能检测到"该停了"，而不是依赖每次调用都抛错；
3. **回归验证**：同一条命令重跑，`counts.total` 必须 ≤ 200（当前 327,875）。

**为什么本轮没动手**：改动落在**核心发包路径**（httpClient / egressOpts / Extractor / Detector
四处协作），必须配全量回归（真机 7 库 + 黑盒靶场 + 请求数断言），
不适合在会话尾部仓促修改。**已定位到行，下次可直接进入修复。**

**另外记一条**：`server/src/engine/egressOpts.js`（271 行）里**既没有 `EGRESS_KEYS` 也没有 `scanId`**
—— 与文档/记忆中的描述不符，说明该文件的形态已变化（或我记错了位置）。
**下次先读它再动手**，不要按旧印象改。

**这一项为什么重要**：
它是**检出率指标上完全看不出来**的缺陷类型 —— 黑盒靶场 9/13、误报 0/7 依然成立，
但「拖库」这个 sqlmap 最核心的功能在真实目标形态（200 + 友好错误页）上直接不可用。
**这正是本计划把 M3 排在第一位的理由。**

```bash
  --union-cols 3 --format json -o out/uc.json
→ 仍然 TIMEOUT（180s / 8971 请求 / 无报告）
```
**结论：列数不是原因** —— 固定为正确的 3 列后，请求量与耗时**基本不变**。

**问题定量**：
| 项 | 数值 |
|---|---|
| 数据规模 | 5 行 × 6 列 = **30 个值** |
| 实测请求数 | 8971 ≈ **300 请求/值** |
| 正常盲注提取预期 | ~10 字符 × 8 轮 ≈ **80 请求/值** |
| 差距 | **约 4 倍** |

**候选原因（下一步逐个排除）**：
1. **动态块排除**（`autoDynamicBlock`）—— 每个判定要多轮采样才能判「真/假」；
2. **整值复验**（`extractVerify`）—— 提取完成后对整值再验一遍；
3. **字符集/长度探测** —— 每个值开工前的前置探测；
4. **失败重试** —— `_send` 失败默认重试，逐次放大。

**下一步的正确切入点**：在 `blindExtractor` 里打印**每个值实际消耗的请求数**，
一眼就能看出是"某个固定环节开销大"还是"随长度线性膨胀"。

### ✅ 已定位：**长度探测失效 → 要去提取 65,531 个字符**（19:46 实测）

按上述切入点加了批次级诊断（打印每批请求数 + **剩余待收敛位置数**），一次就抓到了真凶：

```
批#1    本批请求=5  累计=5     剩余位置=65531  phase=cls-digits pos=1
批#50   本批请求=5  累计=250   剩余位置=65531  phase=cls-digits pos=197
批#600  本批请求=5  累计=3000  剩余位置=65531  phase=cls-digits pos=2397
```

**`剩余位置=65531`** —— 提取器认为这个字段有 **65,531 个字符**要逐字节提取。

| 观测 | 读法 |
|---|---|
| 每批只发 5 个请求 | 并发策略本身没问题（K=4 + 1 个 false 基准） |
| **剩余位置恒为 65531** | **长度探测没有收敛**，直接返回了上限值 |
| `phase` 长期停在 `cls-digits` | 连"是不是数字"都没判出结果 → **真/假判定在该目标上失效** |

**根因**：**长度探测（二分求 `LENGTH()`）与列数探测是同一族问题** ——
目标恒 200 + 错误页回显时，二分所需的"真/假"信号失真 → **不收敛 → 返回上限**。
于是"提取一个 5 字符的 `alice`"变成了"提取 65531 个字符"，请求量自然爆炸。

**这解释了之前所有现象**：
- 每值 ~300 请求 ≠ 效率低，而是**根本没跑完**（180s 只够 9000 请求，30 个值都还停在开头）；
- 固定列数（`--union-cols 3`）无效 —— 因为卡的是**长度**，不是列数；
- M2 修好后提取链**毫无变化** —— 因为真正卡住的是长度探测这另一条链路。

**修法方向（与 M2 同构）**：给长度探测也加**形态判据**（用 `e2e/blackbox-lab` 的
`responseSkeleton` 思路），并在"顶到上限"时做自检；同时**给长度设一个合理上限**
（字段长度超过阈值即判定探测失败，而不是拿着 65531 去逐个提取）。

## 五、P1-A 已修复（2026-09-17 18:46）—— 内部空转与 validity 误报

**定位手段**：在 `httpClient` 的上限分支打印**调用栈**，一次拿到完整链路：

```
HttpClient.request (httpClient.js:1028)
  <- scanRunner.js:130
  <- Extractor._send (Extractor.js:95)
  <- worker (blindExtractor.js:276)        <- 盲注并发 worker
  <- _sendBatch (280) / extractBoolean (158)
  <- scan/extract.js:53 -> scanHelpers.js:154
```

**根因**：`Extractor._send` 把所有异常统一 `return null`（原注释「不改变静默降级语义」），
于是「请求上限已达」被当成「这一次失败」；`_sendBatch` 的 worker 继续全速调用，
每次都在发送前被拒又立刻重试 -> 空转 327,875 次。

**改动（2 处，约 12 行）**：

| 文件 | 改动 |
|---|---|
| `server/src/engine/Extractor.js` | `_send` 的 catch 识别「请求上限已达」-> 置 `this._limitHit = true` |
| `server/src/engine/blindExtractor.js` | `_sendBatch` 的 worker 循环开头加 `if (ex._limitHit) break;` |

**验证结果**：

| 指标 | 修复前 | 修复后 |
|---|---|---|

**最后一行是关键**：真实请求数**未变** —— 本次修复**只消除内部空转与误判，
