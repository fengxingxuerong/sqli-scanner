# nuclei 式模板生态 · 可行性调研（2026-10-25，W43 对标排队项收口）

> 立项背景：`docs/竞品对标-2026W43.md` 吸收矩阵把「nuclei 式模板化规则生态」列为排队项，
> 待办措辞是「先做 payload 池外置化可行性调研，再谈 DSL」。
> **本调研的核心发现：外置化的最小形态在本仓已经存在且已文档化**——本文回答的
> 真正问题是「剩下的差距值不值得追、怎么追才不倒退」。

## 一、nuclei 模板生态的四个组成部分（拆开看）

| 组成 | nuclei 的形态 | 本仓对应物（实测） |
|---|---|---|
| ① 模板数据 | YAML DSL：请求构造 + **自带检测判据**（matcher/extractor，响应侧模式匹配） | `registry.json` 681 条 + 主库 1769：`template/falseTemplate` 占位符 + `dbms/technique/level/risk/clause/boundary/where` 元数据——**数据已外置化（JSON），但判据不在模板里**（见 §三） |
| ② 外部加载 | `-t <dir/file>` 任意本地模板 | **`--payload-file <file.json>` 已有**：追加式、同 schema、id 冲突即拒、高危池硬门同样管辖、校验失败硬失败（`customPayloads.js`，README「自定义检测条目」节 + 专文 docs/自定义检测条目.md） |
| ③ 选择面 | `-tags/-severity/-author` 元数据过滤 | `--technique/--level/--risk/-p/--param-filter` + dbms 自动适配（等价表达力，维度不同） |
| ④ 分发生态 | nuclei-templates 仓库（社区贡献、版本化、CI 验证、订阅更新） | 无（内置库由本仓门禁+验收守护） |

## 二、已完成的（不用再做）

- **②外部加载 + ③选择面**：`--payload-file` 就是「payload 池外置化」的最小可行形态，
  且设计比朴素做法更稳：只追加不覆盖（外部文件不能改基线能力）、缺字段按最保守值补全
  （外部文件不能顶开 level 闸门）、`isDestructivePayload()` 按模板串内容比对（不靠 id
  命名——改名绕不过高危门）。**结论：排队项的「外置化调研」可以关闭。**
- 模板的**版本化**也已有雏形：`registry.versioned.json`（按 DBMS 版本分支，如 MySQL
  5.7.8+ 的 JSON 报错通道），这是 nuclei 模板没有的维度（它不感知目标库版本）。

## 三、真正的差距是「检测模型」，不是格式

nuclei 模板自带检测判据（matcher 对响应做模式匹配），本仓模板只带**注入构造**，
检测判据在通道引擎里（布尔差分/报错签名/UNION 列对位/时序基线——全是**校准过的
差分判定**，不靠单响应模式匹配）。这不是落后，是**对 SQLi 更强的模型**：

- SQLi 的响应没有稳定可匹配的「漏洞特征串」（同一条 payload 在不同数据/模板/WAF 下
  响应形态完全不同）——nuclei 式 matcher 在 SQLi 上天然高误报，这正是 nuclei 的 SQLi
  模板数量少且社区质量参差的原因；
- 本仓验收体系（26 套件、五个外部裁判、误报=0 口径）全部建立在差分判定之上；
  引入 matcher 式模板等于在引擎外再开一条**判定旁路**，每一条都要重新回答
  「误报率证据在哪」——与本仓 claims 纪律正面冲突。

**结论：不做「兼容 nuclei 模板格式」的方向。** 若为了生态互通硬吃 YAML+matcher，
等于用别人未校准的判定逻辑稀释本仓校准过的判定逻辑。

## 四、值得做的是「④分发生态」的一个受控子集（建议，未立项）

若确有「团队间共享 payload 包」的需求（国产中间件/WAF 放行形态/国产库语法——
内置库覆盖不到的长尾），建议形态是**受控配方包**而非开放订阅：

1. 一个 payload 包 = 一个 git 仓库/目录：若干与 `registry.json` 同 schema 的 JSON
   + **每条至少附一个可复现的靶场证据**（对齐台账纪律：有 refute_cmd 才能进）；
2. 加载沿用 `--payload-file` 的全部硬约束（追加式/高危门/硬校验），外加包级清单
   （来源、版本、审计者）；
3. **不做**自动订阅/自动更新（供应链面：外部模板 = 外部注入构造的投放渠道，
   自动拉取等于把投放权交给第三方——本仓授权红线不允许）。

价值判断：这个子集解决的是真实但小众的需求（团队内共享长尾 payload），优先级低于
已知待办（桌面交付件首跑 / 云 WAF 样本采集 / 远端推送）。**建议维持排队、不立项**，
待出现第一个真实用户诉求再启动。

## 五、结论一览

| 排队项子问题 | 状态 |
|---|---|
| payload 池外置化 | ✅ 已存在（`--payload-file`，本调研实证后关闭） |
| YAML DSL 化 | ❌ 不做（JSON 已是数据化；换格式无增益） |
| nuclei 模板兼容 | ❌ 不做（检测模型不同：matcher 旁路会稀释差分判定，误报证据无法对齐） |
