# 检测技术取舍说明：Inline Queries（sqlmap `Q`）与 OOB 替代决策

> 版本：P2 收尾补充（2026-08-03）
> 适用范围：`sqli-scanner` 当前检测技术矩阵（U/E/B/T/S + OOB + second_order + 非SQL注入 opt-in）
> 目的：把"为什么没有实现 inline queries、以及用 OOB 作为无回显盲注兜底"这件事**作为有意识的设计取舍**固化下来，避免被误读为能力缺口；同时形成可面试复述素材。

---

## 1. 什么是 sqlmap 的 `Q`（Inline Queries）技术

sqlmap 的 `--technique` 取值字母：

| 字母 | 技术 | 一句话 |
|------|------|--------|
| B | Boolean-based blind | 真假响应差异推断 |
| E | Error-based | 报错回显数据 |
| U | UNION query-based | 联合查询直接回显 |
| S | Stacked queries | 堆叠语句 |
| T | Time-based blind | 时延推断 |
| **Q** | **Inline queries** | **内联子查询就地提取** |

`Q`（Inline queries，内联查询）是 sqlmap 在 **UNION 不适用** 时用于**就地提取单值**的盲注分支：

- 原理：在原始 SQL 的**输出位置直接嵌入一个标量子查询** `SELECT (SELECT ... FROM ...)`，让被提取的值"内联"出现在原响应中。
- 典型适用场景：Oracle、PostgreSQL 等——原始查询只返回单列/单行、列数/类型不匹配导致 UNION 无法拼接，但 WHERE 子句可控，可在原 SELECT 列表里直接挂一个标量子查询。
- 本质：**一种"不需要 UNION 的数据提取通道"**，等价于"把布尔盲注的每次二值提问，换成一次性把值拼进响应"——提取粒度介于 UNION（整行）与布尔/时间（逐位）之间。

> 关键点：`Q` 与 `U`（UNION）是**并列的两种"直接回显"提取通道**；它**不是**独立的"检测是否存在注入"的方法，而是**注入已确认后的数据提取手段**。

## 3. 为什么本工具**有意不实现** `Q`（取舍论证）

结论先行：**`Q` 在本工具的能力版图里属于"被已有能力覆盖 + 收益边际"的区间，故作为有意识取舍搁置，而非能力短板。2026-08-03 已补齐 `Q` 的**检测半 + 轻量提值**（InlineQueryDetector + Extractor.extractInline），但**完整内联拖库**（重建原始 SQL 模板逐表拖）仍取舍搁置，因单参数注入模型不支持模板重建。**

### 3.1 已有能力已覆盖 `Q` 的提取场景

| `Q` 能做的 | 本工具对应覆盖 |
|------------|----------------|
| Oracle/PG 无 UNION 时就地提值 | **字节级盲注提取**（Extractor：`boolean`/`time` 双通道，字节 0–255 + `TextDecoder('utf-8')）已 DBMS 无关地覆盖"无法 UNION 时的提取" |
| 单值内联回显 | 盲注提取逐字节还原，对任意 DBMS 通用，不依赖能否挂标量子查询 |
| 无回显环境 | **OOB 带外**（MySQL LOAD_FILE/UNC、Oracle UTL_HTTP、PG/MSSQL 对应原语）已作为无回显盲注兜底 |

即：`U` 覆盖"能 UNION 就直接整行回显"；`B`/`T` 覆盖"不能 UNION 就用盲注逐位提"；`oob` 覆盖"连响应都看不到就用带外"。`Q` 能触达的"Oracle/PG 单列无 UNION"场景，**已被 `B`/`T` 盲注提取完整覆盖**，增量收益有限。

### 3.2 `Q` 的局限使它优先级靠后

- **DBMS 窄**：真正"必须有 Q 才方便"的主要是 Oracle/PG 的特定单列场景；MySQL/SQL Server 有 UNION 即可，Q 几乎用不上。
- **脆弱**：内联标量子查询要求**原查询恰好是单列 SELECT 且可挂子查询**，姿态约束强，实战触发率低。
- **与盲注提取同质**：本质上仍是"把值放进响应"，和 `B`/`T` 提取做的是同一件事，只是省了逐位轮询——但本工具盲注提取已稳定（非 ASCII/emoji 已验证），省轮询的体验收益不构成本质差异。

### 3.3 OOB 作为"无回显兜底"的取舍理由

无回显（响应被吞/差分不可见）是盲注的**真正硬骨头**，`B`/`T` 都失效。此时：

- **方案 A：补 `Q`** —— 仍依赖响应回显，对"无回显"**无效**，解决不了真正痛点。
- **方案 B：做 OOB 带外** —— 通过 DNS/HTTP 回连把数据送出响应信道，**直接命中无回显场景**，是 `B`/`T` 失效时的正确兜底。

→ 本工具选 **B（OOB）** 而非在 `Q` 上投入，是因为 OOB 解决了 `Q` 解决不了的问题，且 `Q` 的提取场景已被盲注覆盖。**资源应投向"能力空白"而非"能力重叠"。**

## 4. 取舍代价与诚实声明（能力边界）

不实现 `Q` 的**真实代价**：

1. **Oracle/PG 单列无 UNION 场景**：本工具走 `B`/`T` 盲注提取，**可用但比 `Q` 多轮询**（逐字节 vs 一次性内联）。这是"慢一点"而非"做不到"。
2. **UI 标签诚实性（已解决）**：前端 `SQLMAP_TECHNIQUES` 的 `Q` 标签现已对应真实检测器 `InlineQueryDetector`（后端 technique=`inline`）。它作为 **opt-in** 技术透传——仅当用户在 `ScanConfig.techniques` 显式勾选 `inline` 时才运行（默认 techniques 不含），既激活了标签又不向无回显点目标产生误报噪音。

> 这条代价是**真实的、已记录的**，不是被隐藏的缺口。面试时可直接说明："Q 我们评估过，结论是盲区已被盲注提取+OOB 覆盖，故暂不实现，代价是 Oracle/PG 单列场景多轮询。"

| sqlmap 技术 | sqlmap 支持 | 本工具 | 备注 |
|-------------|-------------|--------|------|
| B 布尔盲注 | ✅ | ✅ | 已实现 |
| E 报错注入 | ✅ | ✅ | 已实现 |
| U 联合查询 | ✅ | ✅ | 已实现 |
| S 堆叠注入 | ✅ | ✅ | opt-in |
| T 时间盲注 | ✅ | ✅ | 已实现 |
| Q 内联查询 | ✅ | ✅（检测半 + 轻量提值） | 完整内联拖库（模板重建）暂未做；盲区已被 B/T 提取 + OOB 覆盖 |
| OOB 带外 | ✅（需 `--dns`/`--os`） | ✅ | opt-in，需接收端 |
| Second-order | ✅ | ✅ | 独立补充趟 |

**对标结论**：6 类主技术中 5 类对齐，唯一缺口 `Q` 为有意识取舍（盲区已被覆盖）；额外超出 sqlmap 默认范畴的是**非 SQL 注入统一归 `nosql` 补充趟**（NoSQL/GraphQL/SSTI），这是 sqlmap 主线不覆盖的维度。

## 6. 路线图（`Q` 实现状态，2026-08-03 更新）

已实现（检测半 + 轻量提值）：
1. ✅ 新建 `InlineQueryDetector`（technique=`inline`），仅当用户显式勾选 `inline` 时运行；检测逻辑：注入标量子查询 `SELECT '__S__INL__E__'` 并比对"测试请求回显标记 / 基线不含标记"确认内联通道可用。
2. ✅ `Extractor` 新增 `extractInline` / `extractInlineProof`：复用 WRAP 包裹与 `__S__/__E__` 解析，把任意 SQL 表达式（如 `VERSION()`）经内联子查询回显带出，作为轻量提值证明。
3. ✅ 前端 `TECHNIQUE_LABEL` 新增 `inline: '内联查询(Q)'`、`SQLMAP_TECHNIQUES` 的 `Q` 已激活可选并透传 `ScanConfig.techniques`。
4. ✅ 补 `server/tests/inlineQuery.test.js`（5 项：回显命中 / 无回显点不误报 / 基线含标记不误报 / 默认不投 / 勾选入报告）。

仍取舍搁置（完整内联拖库）：
- **完整内联拖库**（重建原始 SQL 模板、逐库逐表经内联子查询拖数据）**暂未实现**：本工具是单参数注入模型，无法重建目标原始 SQL 模板，故不提供"一键内联拖库"。此场景已被 UNION 整行回显 + 字节级盲注（`B`/`T`）+ OOB 兜底完整覆盖。

> 优先级评价：检测半 + 轻量提值已补齐，剩余"完整内联拖库"属于**体验优化**而非**能力补齐**，低于"非 SQL 注入实战化""扩库提取深度"等空白项。
