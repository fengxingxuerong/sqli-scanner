# 检测器统一契约（D257）

> 起点：`docs/架构对标-GitHub-SQLi-项目-2026-11-06.md` §6 第二条
> 「执行器 / 匹配算子接口化（nuclei `Executer` + `Operators`）」，
> 以及 §10.1 对 commix `MODULES` 注册表的判断：**不必先把载荷彻底数据化，
> 也能拿到「加能力不改引擎」的收益 —— 先把检测器注册与判定契约收敛成一张表**。
>
> 本文只描述**本次落地的契约与判据**，不声明检出率/覆盖率变化。

## 1. 修前状态：13 个检测器只有一个口头约定

`Detector.detect(ctx)` 返回一个「看起来像 `DetectionResult`」的对象，是全部检测器
唯一的共同点。实际后果（都是本次读码/实测确认，不是推测）：

| 形态 | 事实 |
|---|---|
| 字段形状无校验 | `vulnerable` 为 `undefined`、`payloads` 不是数组、`pointId` 串台，都能一路走到报告层 |
| 「没测成」与「测过且无洞」同形 | `InlineQueryDetector` 两条网络失败路径把「未结论」写进 `evidence`，却没置 `inconclusive` ⇒ 该点被记成已测阴性，也不进 `summary.unverifiedSurfaces` |
| 调度层与编排总图两份真源 | `detect.js` 手写 `FAST = ['union','error','boolean','inline']` / `SLOW = [...]`；`strategyOrder.js` 是另一份。新加一个 `phase:'primary'` 的检测器会**实例化但永远不被调度**（本仓 D95 已出过「有入口从不执行」的同形态） |
| 「靠什么判、能提取什么」只在注释里 | 新检测器没有可核声明；报告读者无法机器化回答「这条命中属于哪类证据」 |

## 2. 落地的三件套

新增 `server/src/engine/detectorSupport/detectorContract.js`：

### 2.1 算子声明（Operators）

```js
MATCH_KINDS   = signature | echo | bool-diff | timing | oob | stored | marker | unspecified
EXTRACT_KINDS = dbms | echo-columns | error-context | nosql-kind
```

`defineDetectorContract({ technique, match, extract, note })` 在**构造期**校验并冻结：
未知类别、空 `match`、缺 `technique` 一律抛 `AppError(6012)`，不等扫描时才炸。

13 个检测器的声明（`new XxxDetector().contract` 可直接读）：

| 检测器 | technique | match | extract |
|---|---|---|---|
| UnionDetector | union | echo | dbms, echo-columns |
| ErrorDetector | error | signature | dbms, error-context |
| BooleanBlindDetector | boolean | bool-diff | dbms |
| TimeBlindDetector | time | timing | dbms |
| StackedDetector | stacked | timing | dbms |
| OobDetector | oob | oob | dbms |
| InlineQueryDetector | inline | echo | — |
| SecondOrderDetector | second_order | stored | dbms |
| NoSqlInjectionDetector | nosql | bool-diff, marker | nosql-kind |
| LdapXpathInjectionDetector | nosql | 继承上者（bool-diff, marker） | nosql-kind |
| XmlParamNameDetector | boolean | bool-diff | — |
| OrderByKeyDetector | boolean | bool-diff | — |
| KeyBoolDetector | boolean | bool-diff | — |

### 2.2 结果不变量（Executer 的出口判据）

`assertDetectionResult(result, { technique, pointId })` 强制：

1. `pointId` / `technique` 必须与执行上下文一致（防复制粘贴串台）；
2. `vulnerable` 布尔、`evidence` 字符串、`payloads` 数组；
3. **命中 ⇒ 证据非空 + 至少一条载荷**（否则报告出现「有洞但无证据」）；
4. **未结论 ⇒ 与命中互斥 + 原因非空**（否则调度层无法记入未验证面）。

### 2.3 统一执行器（Executer）

`Detector.prototype.run(ctx)` → `executeDetector()`：

```
detect(ctx) → assertDetectionResult() → { technique, result, vulnerable, unverified, reason }
```

调度层不再各自解释 `result`：`detect.js` 主循环、XML 元素名 / ORDER BY 键名 /
多键拼接三条补充探针、二阶与非 SQL 补充趟全部改走 `runDetector()` ——
生产检测器（继承 `Detector`，带 `run`）经 `run()` 做契约校验；只有 `detect` 的
鸭子类型对象（调度测试里的替身）退回 `detect()`，不绑死测试桩。
生产侧由守卫钉住「编排总图里每个类都 `instanceof Detector`」，不靠退路放水。

三条补充探针原先各写一份「inconclusive ⇒ addNetworkErrorPoint + netErr +
unverifiedReason」，本次收敛为 `applyOutcomeToPoint()` 单源（主循环那份因复杂度
基线保持内联，语义由 `run()` 保证一致）。

## 3. 调度层：从编排总图派生

`strategyOrder.js` 每条一阶检测器补 `layer: 'fast' | 'slow'`，导出
`FAST_TECHNIQUES` / `SLOW_TECHNIQUES`；`detect.js` 只引用派生值，不再写第二份数组。
守卫测试同时钉住：

- 派生值与历史常量**逐字等价**（union/error/boolean/inline；time/stacked/oob）；
- 两层不重叠；
- 一阶实例集合 == 两层并集（多一个=白跑，少一个=漏跑）；
- 补充趟不得填 `layer`。

## 4. 本次抓到的真实缺陷：Inline 的「未结论」被记成阴性

`InlineQueryDetector` 三条失败路径：

| 路径 | 修前 | 修后 |
|---|---|---|
| 基线/测试响应不可用（重发仍失败） | 只写 evidence「未结论」 | `inconclusive=true` + 原因 |
| 反射门控探针不可用（重发仍失败） | 只写 evidence「未结论」 | `inconclusive=true` + 原因 |
| `catch` 到网络层异常 | 按「该点无内联通道」处理 | 网络层异常 ⇒ 未结论；非网络异常仍按无通道 |

为什么这条重要：报告口径里 `verdict=no_vulnerability_detected` 只在「测过且无洞」
时成立；未结论点会进 `summary.unverifiedSurfaces` 并把整轮结论降级。修前这些点
**既不报洞、也不报未验证**，是标准的假阴性记账。

## 6. 诚实边界

- **算子声明 ≠ 判定算法强度**。它只保证「每个检测器说清了自己靠哪类证据下结论」，
  不保证该类证据足够强；检出率仍以靶场实测为准。
- `extract` 声明目前由守卫与文档消费，**报告层尚未按算子渲染**（例如还没有
  「按 match 类别分组统计命中」的报表）；它是为后续消费方准备的稳定接口，
  不是已生效的展示能力。
- `NoSqlInjectionDetector.detect` 的 `catch` 仍把异常折成「未命中」（opt-in 补充趟，
  改动会影响非 SQL 通道的记账口径，未在本批一并改）；`KeyBoolDetector._bodyOf`
  同样把网络失败折成 `null`。两者都在**补充面**，不影响一阶 `fullyTestedPoints`，
  但引用其阴性结论时仍应知道这一边界。
- 主循环 `runLayer` 的 `inconclusive` 处理仍保留内联形态：该箭头函数在
  `docs/_complexity-baseline.json` 里是 162 行 / 圈复杂度 76 的存量条目，搬移会
  触发复杂度门禁（只许持平或下降 + 行号重映射需特征完全一致）。语义由 `run()`
  保证一致，形态差异不影响结论。
- `assertDetectionResult` 是**结构**判据，不校验 `evidence` 内容是否与 `payloads`
  对应 —— 那属判定质量，归靶场与结论台账管。
