## 三、三条结论

1. **「放行」必须被推翻成主口径。** 同一个 job、同一批样本，放行 8 个插件 vs 打穿 1 个 ——
   差 **8 倍**。首轮若把放行数当绕过能力引用，会系统性高估到这个量级。
   本轮起，对拍报告主口径改为「打穿」，放行列降为辅助。
2. **PL1 与 PL3 在本批样本上仍然一致**（1 vs 1、8 vs 8）。与首轮「PL 提升对已绕过关键词的样本
   边际影响很小」的观察同向。⚠️ 但**不能**据此说「PL3 好过」：裸注入在 PL3 照样被拦（自检已证）。
3. **靶站真库化没有引入假失败**：MySQL 起不来时靶站会降级成 echo，而 CI 里设了
   `MODSEC_REQUIRE_DB=1` → 降级 = **exit 1**（可见的失败），不会出一份看着正常的「放行率」
   报告冒充绕过能力。这条路径已用桩驱动实测（降级标注 / REQUIRE_DB 硬失败 / WAF 不在位硬失败，
   三条全对）。

## 四、诚实边界（引用前必须读）

1. **不能对外声明「真实 WAF 下的绕过率」。** 上界只有 1 条样本，任何百分比都建立在
   单条样本上，不具统计意义。可以说的是：*在唯一具备可打穿上界的样本上，`unionvaluesrow`
   做到了「过 PL1/PL3 的 CRS + 真 MySQL 取数」。*
2. **本轮数字与首轮（09-27）的 74 / 72 不可直接比较。** 首轮口径是「放行」（且靶站为 echo），
   本轮是「打穿」。
   ⚠️ **并且存在一处未解释的差异，已登记待查**：首轮 PL1 报「74 个插件至少放行 1 条样本」，
   本轮同口径（放行）只有 **8** 个 —— 同镜像同配置下差 9 倍。首轮脚本版本已不在仓库中
   （本轮重写了统计与靶站），无法直接对拍，故**不作解释、只登记**。
   → 待查：复跑首轮那份实现（或从 git 历史取出）做同配置对照。
3. **放行 ≠ 打穿，打穿 ≠ 能利用。** 打穿只到「取到数据」这一步；能不能提权、读写文件、
   拿 shell 是另一条链（那部分见 README「利用能力实测口径」）。
4. **靶站是我们自己写的注入点**（原样拼接），不是真实业务系统。它证明的是「这条链的载荷在真
   MySQL 上语义成立」，不是「真实站点能打穿」。
5. 安全对照 4 条 0 误拦，只说明「这 4 条没触发 CRS 误报」，不能推广成「零误报」。
6. CRS 版本仍是 **4.29.0**，与自实现 `crs-engine` 的 **4.1.0** 不同代 —— 真机 vs 自实现的
   分歧里仍混着「版本差」，不能全算在引擎实现头上。

## 六、第三轮（同日）：扩样本集 —— 样本自带上下文

### 起因：上界 1/8 的根因不是 WAF 强，是**样本与靶站形态不匹配**

上一节的「上界 1/8」被记为测量分辨率问题，本轮定位到具体成因：

- 靶站只有一处注入点 `WHERE id = ${raw}`（**数值、无引号**）；
- 而样本集里多数是**字符串上下文**写法（`1' UNION …-- -`、`keyboard%' AND 1=1-- -`）。
  拼进 `WHERE id = 1' UNION …` 之后不是注入，是**语法错误** —— 只能算「抵达 SQL 层」，
  取不到任何数据。
- 于是 8 条里只有恰好是 4 列 + 数值上下文的那一条能取数 ⇒ 分母恒为 1。

这不是 WAF 的能力结论，是**我们的尺子坏了**。修法不是放宽判据，是让样本回到它该在的上下文里。

### 改动

| 文件 | 改动 |
|---|---|
| `e2e/waf-real/samples.mjs` | 新增 `CONTEXTS`（**拼接模板的单一来源**：靶站与对拍脚本共用）。样本从裸字符串升级为 `{ ctx, payload, exfil?, note }`，三种上下文：`num`（`WHERE id = ${raw}`，数值无引号）/ `str`（`WHERE name = '${raw}'`，字符串带引号）/ `in`（`WHERE id IN (${raw})`，括号）。样本数 8 → **15**（union 取数 / 报错取数 / 布尔 / 时间四类齐），取数样本统一带 `__S__…__E__` 或 `SQLISCANNER<n>` 标记，并新增 `exfil: true` 声明 |

## 八、第四轮（2026-09-29）：真实框架形态 —— 注入点 3 → 5

第三轮把「样本 × 靶站形态」的错配修掉了，但三种形态全落在 WHERE 的等值/枚举上 ——
结论只代表那一类靶点。本轮补上真实业务里同样高频、逃逸前提却完全不同的两处：
**搜索页 `LIKE '%q%'`** 与 **列表页排序 `ORDER BY ${sort}`**。

### 8.2 新形态逐条判定（这是本轮唯一的新信息）

| # | 形态 | 样本 | 直连判定 | 说明 |
|---|---|---|---|---|
| 16 | `like` | `1%' UNION SELECT 1,CONCAT('__S__',version(),'__E__'),3,4-- -` | **pwn_result** | 闭合 `%'` 后 union，尾部 `%'` 用注释吃掉 |
| 17 | `like` | `1%' AND extractvalue(...)` | **pwn_error** | 报错取数 |
| 18 | `orderby` | `extractvalue(1,concat(0x7e,(SELECT CONCAT('__S__',version(),'__E__'))))` | **pwn_error** | **ORDER BY 位置能被报错取数打穿** |
| 19 | `orderby` | `IF(1=1,1,2)` | reached_sql | 布尔样本，设计上就不取数（只测放行） |

- **`ORDER BY` 不是「安全位置」**：排序参数在真实列表页里几乎人人写过，实测它在真 MySQL 上
  能被 `extractvalue` 报错取数打穿 —— 这类位置不该被当成「没有 WHERE 就没风险」。
- **`LIKE` 位置两条都打穿**：需要先闭合 `%'`、尾部还有个 `%'` 要注释掉，逃逸前提与等值形态
  确实不同，值得单独作为一种形态存在。

### 8.3 一条不能漏读的结论：形态变多 ≠ 绕过链变多

- 上界从 7 抬到 **10**、靶点从 3 类扩到 **5 类** ⇒ **测量的代表性与分母变好了**；
- 但真机**打穿插件仍然只有 1 个**（`unionvaluesrow`，2/19；其直连上界 10/19 ⇒ 按可打穿样本计
  **2/10**）⇒ **没有发现任何新的打穿链**。
- 也就是说：这一轮改善的是「尺子」，不是「能力结论」。把两者混着说会得出
  「加了形态所以更能绕过」的错误印象 —— 事实是更能**测**，不是更能**打**。
