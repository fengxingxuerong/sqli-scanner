## 三、三条结论

1. **「放行」必须被推翻成主口径。** 同一个 job、同一批样本，放行 8 个插件 vs 打穿 1 个 ——
   差 **8 倍**。首轮若把放行数当绕过能力引用，会系统性高估到这个量级。
   本轮起，对拍报告主口径改为「打穿」，放行列降为辅助。
2. **PL1 与 PL3 在本批样本上仍然一致**（1 vs 1、8 vs 8）。与首轮「PL 提升对已绕过关键词的样本
   边际影响很小」的观察同向。⚠️ 但**不能**据此说「PL3 好过」：裸注入在 PL3 照样被拦（自检已证）。
3. **靶站真库化没有引入假失败**：MySQL 起不来时靶站会降级成 echo，而 CI 里设了
   `MODSEC_REQUIRE_DB=1` → 降级 = **exit 1**（可见的失败），不会出一份看着正常的「放行率」
   报告冒充绕过能力。这条路径已用桩驱动实测（降级标注 / REQUIRE_DB 硬失败 / WAF 不在位硬失败，
   三条全对）。

## 四、诚实边界（引用前必须读）

1. **不能对外声明「真实 WAF 下的绕过率」。** 上界只有 1 条样本，任何百分比都建立在
   单条样本上，不具统计意义。可以说的是：*在唯一具备可打穿上界的样本上，`unionvaluesrow`
   做到了「过 PL1/PL3 的 CRS + 真 MySQL 取数」。*
2. **本轮数字与首轮（09-27）的 74 / 72 不可直接比较。** 首轮口径是「放行」（且靶站为 echo），
   本轮是「打穿」。
   ⚠️ **并且存在一处未解释的差异，已登记待查**：首轮 PL1 报「74 个插件至少放行 1 条样本」，
   本轮同口径（放行）只有 **8** 个 —— 同镜像同配置下差 9 倍。首轮脚本版本已不在仓库中
   （本轮重写了统计与靶站），无法直接对拍，故**不作解释、只登记**。
   → 待查：复跑首轮那份实现（或从 git 历史取出）做同配置对照。
3. **放行 ≠ 打穿，打穿 ≠ 能利用。** 打穿只到「取到数据」这一步；能不能提权、读写文件、
   拿 shell 是另一条链（那部分见 README「利用能力实测口径」）。
4. **靶站是我们自己写的注入点**（原样拼接），不是真实业务系统。它证明的是「这条链的载荷在真
   MySQL 上语义成立」，不是「真实站点能打穿」。
5. 安全对照 4 条 0 误拦，只说明「这 4 条没触发 CRS 误报」，不能推广成「零误报」。
6. CRS 版本仍是 **4.29.0**，与自实现 `crs-engine` 的 **4.1.0** 不同代 —— 真机 vs 自实现的
   分歧里仍混着「版本差」，不能全算在引擎实现头上。
