### 沙箱抓到的发布阻断缺陷（已修，提交 `8d0a85b`）

- **启用 token 后 Web UI 打不开**：`GET /` 返回 `401 需要有效的 API Token`。
  根因：token 中间件只放行 `PUBLIC_READONLY` 精确集合，而 A2 之前默认无 token，这条路径从未被执行到
  ——**只在 Docker/单端口 + 配了 token 的组合下 100% 命中**，开发模式与单测都测不到。
- 修法：按路由段区分——GET 且首段不属于 `{api, sqlmap, scan, exploit}` 视为前端外壳放行；
  其余（含不带 `/api` 前缀的 `/scan/*`、`/exploit/*`、`/sqlmap/*`）仍必须带 token。
- 反向验证：`/scan/aaaaaaaaaa`、`/scan/aaaaaaaaaa/report`、`/api/scan/aaaaaaaaaa` 无 token 均 401。
- 同步新增 CI job `release-smoke`（只依赖 PGlite，不需 MySQL），并把两条断言加进 `security-guardrails`（现 20 项）。
- `v1.1.0` 标签已移到含本修复的提交 `8d0a85b`。

**教训**：A1（CSP 白屏）与本条（token 拦前端）是同一类缺陷——**只在"生产配置组合"下现形**。
此前所有门禁都用开发便利配置，因此需要常驻的"生产配置冒烟"，而不是再加更多单测。

> **↑ 这行"11 PASS / 0 SKIP"是假绿，见 §7.5**：当时 `acceptance.mjs` 把「只输出 SKIP、一行断言都没跑」
> 的 fileRead / fileWrite 算进 PASS 并计入汇总。同一环境改成四态分列后复跑，实测是
> **8 PASS / 0 BLOCKED / 0 FAIL / 3 SKIP**。

### 7.3 两个靶场的定性（按"每边 ≥3 次"的口径，不做单样本归因）

- **concurrent-isolation：确定性失败，且早于本批。** HEAD 连跑 3 次 = 3 失败；把本批改动的引擎/CLI 文件整体回退到改动前再连跑 3 次 = 仍 3 失败，失败行逐字相同：
  `[pg-shell] dbms=PostgreSQL ✓ union OK`，而 `[my-num]` / `[my-str]` 两条 `dbms=null techs=[] union=MISS`。
  为什么一直没被抓到：它 `deps:['pg','sandbox']` → CI 无 PG → 直接 SKIP；且第 32 行**硬编码 `port: 3306`**、不读 `MYSQL_PORT`，与"走隔离沙箱"的声明自相矛盾（这很可能就是根因，见 TODO）。
- **udf-lab：抖动，非回归。** 本批 HEAD 4 次 = 2 通过 / 2 失败；回退本批文件后 5 次 = 2 通过 / 3 失败；关掉宿主 3306 再 3 次 = 1 通过 / 2 失败。失败点固定在 `[step4] sys_eval('cmd /c echo M')` 捕获为空，而同一次运行 `sys_eval('whoami')` 正常 → DLL 与注册都没问题，是 cmd 输出捕获偶发为空。step6 的提示把它归因为"Windows 本地化 GBK 输出"，而 marker 是纯 ASCII —— **这条归因文案本身会误导排查**，待改。
- 服务端单测：本机今日共 6 次，5 次全绿、1 次 1 条失败（现场已随上文改动保留，下次可直接看到用例名）。

### 7.4 对发布结论的影响

§3 的 P0 没有一条被本节消掉，反而多了一条更硬的：**在接上远端、让 CI 真跑绿一次之前，本项目的"全部门禁通过"只有"作者单机单次"这一种证据**。此外 `run-all` 目前带着一个确定性红套件，合入前要么修掉 concurrent-isolation，要么让它显式 BLOCKED（别以 SKIP 混过）。

### 7.5 同日再补（2026-09-19 下午，本批）：三条假绿掐掉，一处归因自我撤回

上面 §7.1 立了"门禁可信度"这条线，本批把它执行到底，并顺带暴露我自己的一个错误结论。

| 项 | 修前 | 修后（实测） |
|---|---|---|
| acceptance 的 SKIP | `pass: passed \|\| skipped` → 未执行断言的套件计入「11 PASS」 | 四态分列：本机默认环境 **8 PASS / 0 BLOCKED / 0 FAIL / 3 SKIP**（退出码 0） |
| eslint 覆盖范围 | 9 条目录/文件级 ignore，**含门禁总控 `acceptance.mjs` 自己** | 全部纳回，25 条 `no-unused-vars` 清零；`eslint .` 0 error / 6 warning / 退出码 0 |
| WAF 对外数字 | README 抄的是 `10/5`（量纲混在一个分数里）+ 自动档 11；`waf-auto-check` 里还写死「基线 = 10」 | 复测 **on=8 / auto=8**（两次独立运行一致）；输出改为「技术位合计 8（5 个注入场景）」，基线改为从 `waf-real-report.json` 现读 |
| 定库判据 | H2 用跨库通用的 `version()` | 改 exclusive 的 `H2VERSION()` 并前置；真引擎 A/B：`dbms=null` → `dbms=H2`，真 MySQL 三点仍 `dbms=MySQL` |

**自我撤回**：本批先前写「H2 的 `version()` 回显会命中 MySQL 的裸版本号 sig → 真 H2 被定成 MySQL」，
并把它当成 multi-engine-lab 的实测结论。真跑 A/B 后是 **定库失败（`dbms=null`）**，那条误判路径在这台
真 H2 上根本不可达（H2 没有 `version()` 标量函数，MySQL 系 WRAP 的 `CAST(x AS CHAR)` 直接报错）。
症状从"误判"降级为"识别不出"，修复的收益不变，但**结论的来源必须写清是实测还是推理**（TODO §A 已改写）。

**WAF 那 2 格丢在哪，第一次有了规则级证据**（逐条手工发探针，规则原文可复核）：
CRS 942361 的判据是 `^[\W\d]+\s*?(?:alter|union)\b` —— 打的是**参数值起始形状**，不是 `UNION`/`SELECT`
的相邻性。所以 `1 UNION SELECT NULL…` 必被拦，而 `alice' UNION SELECT NULL…#` 放行；`/**/`、`%0a`、
`%09`、双空格、`UNION ALL` 八种形态全部 403，且它们不套 WAF 时 MySQL 全部正常执行（不是语法问题）。
`dash2hash` 只规整尾部注释符，对这条无效。本批改动已排除（回退动过的 4 个引擎文件重跑，结果逐字相同）。
另一层：**942361 官方注释属 PL2**，而本仓自实现执行器默认全规则（≈PL3 最严档）——所以 8/8 是"最严档"
数字，**CRS 默认部署档 PL1 的绕过率仍未测**。

### 7.6 对发布结论的净影响

- 变得更可信的：门禁的 PASS 数字现在名副其实（SKIP 独立成态）、lint 真的覆盖到 e2e 与门禁脚本、
  对外 WAF 数字有了可复现来源和规则级边界说明。
- 变得更难看的（但都是真的）：本机默认环境下"全绿"其实是 **8/11**，另 3 项要求补环境
  （放行 `secure_file_priv`、常驻红队靶场）；WAF 绕过率从 10/11 降到 8；
  README「4 种真实引擎全链路 + 3 种部分通道」的分层里，那"3 种部分通道"（H2/HSQLDB/Derby）现在有了
  实测边界：**只有 H2 能被版本回显定库，HSQLDB/Derby 连这条通道都整条失效**（关掉 WAF 也一样）。
  分层措辞不用改（"部分通道"本就留了口），但任何"这三家的定库都可用"的理解都不成立。
- §3 的 P0 结论不变：**没有远端 CI 的一次真跑绿，"全部门禁通过"仍然只有"作者单机单次"这一种证据**。
  本节新增的一条纪律是：**门禁报出的数字，必须是它真验过的数字**——`11 PASS` 里有 3 个没跑断言，
  比直接报 8 个更危险，因为它让人以为剩下那 3 个也测过。
