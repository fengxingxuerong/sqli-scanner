## 一、这一轮真正暴露的问题（按实战痛感排序）

前几轮的清单都在优化「检出率」。从作战角度看，这个项目最大的风险不是漏检，而是三件事：

1. **「扫不出来」和「没有漏洞」在报告里长得一模一样。**
   网络失败被吞成 `null`，再被 `String(res?.data ?? '')` 变成「200 空页」；目标中途挂掉、被 WAF 封 IP、
   会话过期之后，剩余所有点都会被判「已测且无洞」。这是会写进交付文档的错误安心，比漏检更危险。
2. **引擎实现了的能力，在 API 层收不到。**
   `KNOWN_CFG_KEYS` 里有 13 个键从未被 `sanitizeStart` 透传（`delay`/`reqRate`/`maxReq`/`excludeSysdbs`/
   `nullConnection`/`testFilter`/`testSkip`/`useRegistry`/`hpp`/`forceSsl`/`ignoreRedirects`/
   `activeWafProbe`/`prefilter`）。其中 3 个是**限速与请求预算治理**——也就是「别把客户生产系统打挂」的
   那三个开关，UI 上传了、引擎也支持，中间断了一截，用户以为生效了。上一轮「补白名单」的修复只做了一半。
3. **没有授权范围（scope）这个概念。**
   SSRF 防护管的是「别打自己人」，管不了「别打没授权的人」。而目标 302 到未授权主机（统一登录、CDN 回源、
   灰度切流）时，扫描器会跟着跳，把后续全部注入请求连同 Cookie 打到圈外。手滑扫到隔壁系统在这个行业里
   是事故，不是 bug。

### 本轮额外捐出的两个体系性结论

1. 「白名单有、透传没有」必须有守卫。只查 `defaults → KNOWN_CFG_KEYS` 方向不够，必须同时查
   `KNOWN_CFG_KEYS → sanitizeStart 透传`（`configWhitelist.passthrough.test.js`）。本轮一上来就
   抱出 13 个断链键，其中 `delay/reqRate/maxReq` 是限速与请求预算治理——即「不要伤害客户」那几个开关。
2. 子 agent / 二手审计结论必须逐条回代码核实。本轮 4 份报告里共 9 条不实（已列入文末表），
   典型如「index.js 把完整 URL 写访问日志」「导出落 report.json」「unknown(0.5) 会触发全站 tamper 重跑」
   ——它们听上去完全合理，但对应行号里的代码不是那样写的。不核实就开工，会白花一轮工时去修不存在的洞。

### P0 —— 影响结论正确性，先修

1. **网络错误仍被吞成「空响应」**。`core/httpClient.js:1566-1586` catch 后 `return null`；各检测器统一
   `String(res?.data ?? '')` → 失败响应与「200 空页」不可区分。守卫只在**连续**失败时熔断，零星失败仍会
   污染判定。修法：失败时返回 `{status:0, data:'', __netErr:{code,message}}`（保持 `res` 为对象，
   调用方 `res?.status` 语义不变）；Boolean/Time/Union 在 `res.__netErr` 时抛 `INCONCLUSIVE` 而非判负；
   `res.__meta.truncated` 同步进判定（被截断的响应参与 diff/相似度会失真）。
2. **`risk` 与破坏性 payload 的关系要重写（本条已推翻初稿）**。事实核完：默认扇平路径的 stacked 池是
   **只读**的（`SELECT SLEEP` / `SET @x=1` / 查 information_schema），DROP/UPDATE/DELETE/写文件全部
   在 `engine/payloads/destructive.js` 隔离池里。但 `enableDestructivePayloads()` 在生产代码里
   **没有任何调用点**（只有声明式 registry 按 risk 合并）→ 于是：
     • `risk=3` + `useRegistry=false`（默认）→ 高危池永不投放，风险开关形同虚设（安全侧“失效”无害，
       但用户以为 risk 有语义）；
     • `risk=3` + `useRegistry=true` → 直接投放，此时**没有**任何「生产环境」二次确认。
   修法：① `defaults.js`/README 写清 risk 与 useRegistry 的耦合；② 给高危池投放加 `confirmDestructive:true`
   硬门 + 报告首屏标注；③ `enableExtract`（拖库）与 `secondOrder.enabled`（真实写请求）同样受
   `productionMode` 约束：该开关下需显式确认才放行，并在 `report.summary.constraints` 里写明本次抑制了什么。
3. **二阶写请求无 method 校验、无生产护栏**。`engine/detectors/SecondOrderDetector.js:198-205`：
   `secondMethod` 未走白名单（可传 `TRACE`/`CONNECT`），触发页硬编码 `GET`，store 请求沿用 `target.method`
   → 对 `/order/create` 这类 GET 写端点，「只读复核」的说法不成立。修法：method 白名单 + 复用 2 的开关。
4. **提取阶段「0 行」被当成已确认**。`Exploiter.js:275-281` 无长度校验，`scanRunner.js:654-660` 不看
   `rows.length` → 报告里写「已确认但为空」，是把假阴性写进结论。修法：0 行 → `confidence:'low'` +
   追加一次 `WHERE 1=1` 非空对照，对照仍为空才写「空表」。
5. **布尔盲注在多参数点位只注入第一个参数**。`detectors/BooleanBlindDetector.js:271-279` 在无 `point`
   时用 `Object.keys(bodyParams)[0]` 作模板键 → 其余参数全盲（同文件 :400-410 已有正确写法，属漏改）。
6. **500 页回显 payload 造成假阳**。`BooleanBlindDetector.js:192-201` 用裸 `includes` 判「真页含 payload」；
   `TimeBlindDetector.js:403-413` 的长度容差被 echo 绕过。修法：echo 感知的「无信息页」识别
   （`ErrorDetector.js:120-129` 同思路，搬过来即可）。
7. **时间 payload 无下限夹顶**。`engine/payloads/index.js:351-367` 的 Oracle/PG/Sybase/Informix/DB2 向量
   与 `payloads/mysql.js:156-158` 的 BENCHMARK 次数都是无界 `{SLEEP}` → `--time-sec 600` 会把目标库挂住
   10 分钟。修法：TIME_VECTORS 统一 `clamp(1,15)`，BENCHMARK 次数按 sleep 秒数换算并夹顶。
8. **OOB 启动失败被 `report.error` 掩盖**。`ScanManager.js:158` 置 error、`:289-290` 又写回 completed →
   报告有 vulns 但前端只渲染「扫描失败」。修法：OOB 不可用改为 `report.summary.oobUnavailable` 标注，
   不改 status。

### P1 —— 检出深度与作战可用性

9. **跳过判定用请求级并发**（`ScanManager.js:758-761` 读 `_currentConcurrency`）→ `concurrency=1` 时
   `skipStatic`/`prefilter` 完全不跑，省请求能力在最需要（慢目标/易封目标）时失效。修法：调度器创建后
   注入基准并发（照 `guard.onTrip` 的 `schedulerRef` 写法）。
10. **续跑丢失提取进度 + 中断报告不标未完成**（`scanRunner.js:542`、`:617-621`）：resume 后
    `report.data=null`，已提取的库表要重打；`status='stopped'` 的报告缺「部分完成」标记。
11. **404 页动态尾段被误标 dynamicBlock**（`Detector.js:230-240`）→ 真实「页面不存在」差异被抹掉。
    修法：只对 2xx 基线跑动态块检测。
12. **动态块检测不查变化率**（`Detector.js:247-254`）→ 每字节都变的模板（内嵌时间戳/nonce）退化为全页
    比对，布尔盲注必然漏检。修法：变化率 >70% 时降级为「状态码 + 长度」判定并在 trace 里注明降级。
13. **集合运算 / ORDER BY 点位缺专项提取模板**（`engine/extractionMaps.js:45-52` 仅 17 个 clause id，
    零集合运算、零 `COLLATE`）→ 实战里 MySQL collation 不匹配（`Illegal mix of collations`）是 UNION
    第一高频报错，没有对应模板就等于放弃这批点。
14. **MySQL 报错族偏窄**（`payloads/mysql.js:11-43` 缺 `floor(rand(0)*2)` group by、`GTID_SUBSET`、
    `json_object_agg` 系），且 `AND EXP(~0)` 被归到 error 族但写成 `13=1` 恒真 → 不闭合上下文里制造假阳。
15. **tamper 幂等声明不实**：`core/tamper/plugins/blindbinary.js:68-70` 声明幂等但第二次会解掉自己的输出
    （链式/重跑时数据损坏）；另有 4 个插件声明幂等未实现。最小修法：改 `idempotent:false` 或加 marker 包裹。
16. **`--invalid` / `--invalid-logical` / `--invalid-bignum` 缺失**（`server/bin/cli.js:116-179` 参数表）：
    这组是缓存页/静态页噪声规避，正是布尔盲注在真实站点上最常见的失败原因，优先级应高于「再加 200 条 payload」。
17. **没有「已知注入点直接利用」入口**（也无 `--gpage`）：手工找到点以后仍只能把 payload 塞回参数值并先跑
    一轮检测。修法：`config.knownPoint = {param, quote, paren, technique}` 跳过发现与指纹阶段。
18. **MSSQL 拖库中文 HEX 往返不一致**（`Exploiter.js:894-906` vs `:776-781`）→ 报告里出现不存在的字符差异，
    客户对着原库核会反过来质疑我们的结论。
19. **CORS 无 Origin 一律放行 + 无 content-type 守卫**（`server/index.js:70-80`）：当前靠 `express.json`
    只解析 `application/json` 侥幸挡住简单请求。修法：mutating 方法要求「无 Origin 或 Origin 在白名单」+
    `Sec-Fetch-Site: cross-site` 直接拒 + 非 JSON 请求体返回 415。
20. **`ssrfViaProxy='auto'` 且命中环境变量代理时，域名目标不再做任何 IP 判定**（本轮 5 的遗留）：若内网
    DNS 把域名指到 `169.254.169.254`，代理会照打（代理本身能解析元数据）。属「代理即边界」的设计后果，
    但需要逃生口：加 `ssrfViaProxy:'strict-dns'`（解析成功就判、失败才下放）并在 README 写明边界转移。
21. **`headRequest`（`--null-connection`）未走 `getScanClient` 的出口注入** → null-connection 模式下
    `insecureTls`/代理语义缺失（`ScanManager.js` 的 egressPatch 只包了 `request`）。
22. **`union_extract` fixture 阈值余量只有 3 请求**（max 120 / 实测 117），且 `nullSequence` 用
    `Math.random()` 选列 → 该场景易 flaky。修法：固定随机种子或阈值放宽到 150。
23. **声明式注册表里 5 条时间模板缺 `{SLEEP}` 占位符**（`engine/payloadRegistry.js:687,703,719,735,751`，
    均为 SQLite）→ 注册表路径下时间探测恒不延迟，且被 `timeFloorMs` 判成噪声。

## 四、已核实「不成立」的传闻（别再排期）

| 传闻 | 核实结论 |
