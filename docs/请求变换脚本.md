# 自定义请求变换脚本（签名 / 加密参数接口）

> 批次 D32（2026-10-10）· 实战 P0-1。入口：CLI `--request-script <file.js>`、
> REST `config.requestScript`、面板「授权范围与传输安全」分段。
> 实现：`server/src/core/requestTransform.js`（约束与理由写在文件头）。
> 批次 D34 补真机闭环靶场 `e2e/signed-api-lab`，实测数字与两条被换掉的"拍出来的"结论见 §8。

## 1. 这解决的是哪一类「扫不出」

前面几类缺口（ multipart、嵌套 JSON、二阶跨角色）都是**引擎没收到注入点**；
这一类更靠前：**引擎发出了合法-looking 的请求，但目标根本不认**。真实业务里三种形态占绝大
多数：

| 形态 | 例子 | 不带变换时的症状 |
|---|---|---|
| 签名参数 | `sign=md5(sorted(params)+key)`、`X-Sign`、`x-tumid` | 改一个字段 ⇒ 签名失配 ⇒ 目标回 400/「签名错误」 |
| 整参加密 | 请求体 AES/自定义编码，服务端解密后才拼 SQL | payload 被当密文解，永远解不出 SQL |
| 防重放 | `timestamp` + `nonce`，超窗即拒 | 抓包重放几秒后全废 |

三者的共同症状是**报告写「未检出」**，使用者读到的是一句安全结论，而实际一个注入都没抵达
SQL 拼接点。这是扫描器最贵的一类错（静默假阴性），所以本扩展点是**功能 + 判据**成对交付的，
见 §4。

## 2. 契约

脚本是一个本地 ES 模块，导出一个 `transform`：

```js
// D:\signers\sign.mjs
import crypto from 'node:crypto';

const KEY = process.env.MY_SIGN_KEY;   // 密钥走环境变量，不要写死在脚本里（脚本会进 git、报告里有它的 sha256）

export function transform(req) {
  // req = { url, method, headers, data, params, scanId }   ← 已经拼好 payload 的最终形态
  const u = new URL(req.url);
  const q = [...u.searchParams.entries()].sort(([a], [b]) => (a < b ? -1 : 1));
  const sign = crypto.createHash('md5').update(q.map(([k, v]) => `${k}=${v}`).join('&') + KEY).digest('hex');
  u.searchParams.set('sign', sign);
  return { url: u.toString() };        // 只返回要改的字段，其余沿用原值
}
```

- 可以是 `async`（要取时钟、调远端 KMS 都行）。
- 三种导出形态都认：`export function transform`、`export default fn`、`export default { transform }`。
- **返回什么都行，但只有五个字段会被采用**：`url` / `method` / `headers` / `data` / `params`。
- **扫描/检测阶段的每条请求都会过它一次** —— 包括保活页、CSRF 取页、登录提交这些非注入请求。
  ⚠️ **例外**：注入点发现阶段（`--crawl` / 表单收集）的请求不经此层，见 §7。
  按 URL 过滤是脚本自己的事（`if (!req.url.includes('/api/')) return req;`）。

## 3. 四条硬约束（不是实现细节，是使用前提）

1. **变换在 SSRF / 授权范围（scope）校验之前完成**，所以校验作用于**变换之后**的 URL。
   反过来挂，这个扩展点立刻变成 SSRF 跳板（脚本可把已授权请求改写到内网元数据地址）。
2. **脚本失败一律不发请求。** 抛异常、返回 `null`、返回空 `url`、返回非对象 headers ⇒
   上抛 `REQUEST_SCRIPT_FAILED(6008)`，**绝不退化成「算不出签名就把没签名的原始请求发出去」**。
   那等于用一次必然被拒的请求去填「已检测」的账。
3. **脚本改不动引擎控制权。** `signal`（stop/暂停）、`scanId`、`rateGroup`/限速、`retry`、
   `timeoutMs`、`cookieJar` 全部不在可替换集合里 —— 否则一句 `return {...req, signal: undefined}`
   就能把「随时能停手」和「总速率上限」这两个合规闸门摘掉。
4. **不原地改入参。** HttpClient 的重试与认证重放**复用同一个 opts 对象**，原地签一次就变成
   第二次签名挂在已签名报文上（恒错）。传进脚本的是副本，返回的是新对象。

外加一道入口闸门：**脚本必须位于环境变量 `REQUEST_SCRIPT_DIR` 指定的目录内**，未设置时一律
拒绝加载。这是出口层的代码注入面，且同一个引擎既跑在操作者终端也跑在长驻 HTTP 服务里 ——
按「谁调用的」分别放行迟早漏一处，所以用一道对所有入口同样的目录白名单。
加载/校验失败（路径非法、没有 `transform` 导出、脚本语法错）⇒ **扫描不启动**（`start()` 抛出，
REST 得 `code=6007`，CLI 直接报错退出），而不是"忽略脚本继续扫"。

## 4. 怎么知道它到底生效没有

两处强制显形，都不靠人自己判断：

**① 报告标注（每次都会写）**：启用后 `summary.constraints` 多一条
「本次扫描/检测阶段的每条出站请求都经过自定义变换脚本 <文件名>（sha256=…），含保活/CSRF 取页/登录；
注入点发现阶段的爬虫请求不经此层：报告中的 PoC curl **未**重算签名，
直接复制会失败，复现必须带同一脚本重放」。
这句不是客套 —— 交付时客户拿 PoC curl 复现不了，第一反应是工具在编。

**② 新判据 `transform_rejected`**（可信度守卫，只在启用变换时参与判定）：

| 观测 | 定性 | 后果 |
|---|---|---|
| 连**未注入的基线请求**都连续被目标判非法（400/415/422，且从未成功） | 脚本与目标不匹配（密钥、参与签名的字段集、拼接顺序错了） | `reliable:false` + **中止剩余检测**（后面每条必然同样被拒，继续跑只是白烧预算） |
| 基线正常，而注入请求 ≥8 次全被拒且没有一次成功 | 注入值破坏了签名（脚本没覆盖被改的那个参数） | 同上 |

两种成因的 `reason`/`advice` 文案不同（前者改脚本，后者把参数纳入签名范围），
且都会把 `summary.verdict` 打成 `inconclusive`、把「未检出」那句安全结论撤回。

⚠ 边界（刻意不收的）：403/406/429/503 属既有 `blocked` 族、401 属会话族、5xx 属
`target_error` / error 技术自身产物 —— 四套判据各管一件事，混用会互相踩。
连不上（无响应/超时）单独记 `netErr`，**不**算签名被拒。

## 5. 没做什么（别指望它）

- **不做自动逆向签名算法。** 它只是把「你来算」这件事接上，不猜你的 key、不还原你的 JS。
- **不覆盖验证码 / OAuth 授权码流程 / SAML**：登录编排仍只处理标准 HTML 表单
  （`server/src/core/loginFlow.js` 文件头列了同样的边界）。
- **不进任何默认链/默认配置**：`requestScript` 默认空串 ⇒ 不用它时行为与改造前逐位一致
  （连请求对象都不换引用，见 `server/tests/requestTransform.test.js` 的零变化契约）。

## 6. 上手检查表

1. `mkdir D:\signers` → `export REQUEST_SCRIPT_DIR=D:\signers`（服务侧同理，写进 systemd/容器 env）。
2. 拿一次真实抓包，把浏览器/客户端发出的报文与脚本产出的报文**逐字节对一遍**
   —— 90% 的「脚本配错」是字段顺序或空值参与签名规则不同。
3. 先对 1 个参数跑一次，看报告里 `transform_rejected` 出没出：
   出了就说明目标仍然不认这个报文，**不要**把这次的「未检出」写进交付。
4. PoC 复现说明里带上脚本文件名与 sha256（报告已自动写）。

## 7. 边界：哪些请求不经此层（实测确认，不是推测）

变换层挂在 **per-scan 客户端视图**上（`engine/scan/scanClient.js` 的 `getScanClient`），
它的覆盖面就等于「经过那个视图的流量」。下面这一路**不在**覆盖内：

| 阶段 | 用的是哪个客户端 | 后果 |
|---|---|---|
| 注入点发现：`--crawl` 链接爬取、`crawlForms` 表单收集、headless 浏览器采集 | `ScanManager` 构造时持有的**模块级单例** `httpClient`（`this.parser = new TargetParser(this.httpClient)`，`crawler.js` 再继承它），调用时不带 `scanId` | 这些请求**不签名** ⇒ 在签名型 API 上爬不到东西（目标按「非法请求」拒），注入点发现只能靠 URL/`--body`/`-r` 抓包显式给出 |

这不是 D32 新造出来的洞，而是既有架构属性：**同一一路请求此前也不受暂停闸与 per-scan 限速桶约束**
（F1 那批修的是「经 `getScanClient` 的 ad-hoc 客户端」，这一路连 `getScanClient` 都不走）。
把它一起改掉要给 `TargetParser`/`LinkCrawler` 传入扫描级视图，属另一个口子，
已按「D32 剩下的账」第 6 条记进 `TODO.md`，验证口径是：爬虫请求在带签名的靶点上必须**真的**带上签名，
或者报告里明确写出"发现阶段未签名 ⇒ 爬取结果为空不代表目标没有可爬的表单"。

不在这条边界内的（每一条都有接线用例钉着，`server/tests/requestTransform.wiring.test.js`；
把对应包装层从 `view` 改回 `sc` 会让那一条用例变红，实测过）：
`--safe-url` 保活页、`--csrf-url` 取页、`config.login` 的登录 GET/POST、HEAD（`--null-connection`）。
`detect.js` 里两支 ad-hoc 客户端（tamper 链验证、拦截驱动重跑）经 `sm.getScanClient` 取视图，
与上表同一条链 ⇒ 结构上覆盖，未单独写用例。

## 8. 真机实测（`e2e/signed-api-lab`，2026-10-10，连跑三轮逐字一致）

靶站：真 SQLite（sql.js）+ 真 md5 验签中间件（签名不对 ⇒ 业务代码根本不执行，位置与真实网关一致）；
执行方式：真 CLI 子进程 + 真签名脚本文件（`REQUEST_SCRIPT_DIR` 指向靶场自带的 `signers/`）。
**裁判不是引擎自己报的数，而是靶站计数的 `reachedPayload`**（"改了取值的请求真的进了 SQL"几次）。

| 场景 | 签名脚本 | 请求总数 | 靶站抵达 SQL（其中注入请求） | 报告结论 |
|---|---|---|---|---|
| D 对照 | **不带** `--request-script` | 11 | 0（0） | `verdict=no_vulnerability_detected` + `reliable=true` ⇐ **这就是没有该扩展点时的静默假阴性现场** |
| A | 正确（对当前参数集签名） | 83 | 83（**67**） | 检出 3 条；安全对照点（参数化查询）131 请求 **0 检出** |
| B | 只对"抓包那份副本"签名（漏掉被注入的 `id`） | 13 | 3（**0**） | `transform_rejected` / `kind=injection` / `inconclusive` |
| C | 字段集与算法都对、**密钥错** | 11 | 0（0） | `transform_rejected` / `kind=baseline` / `inconclusive`，且**早停**（83 → 11 请求） |
| E | 正确签名 + 目标对含 `union` 的取值回 400 | 91 | 72（56） | **不误报**（19 次注入被拒但 `injectOk=48`），仍检出 2 条 |

两条由此把 D32 里"拍出来的"结论换成实测：

1. **阈值的作用被搞清楚了**。判据成立那一刻实测：`kind=baseline` 在连续 2 次基线被拒时成立、
   `kind=injection` 在 `injectRejects=8` 时成立。但 E 场景是更值钱的一条证据：健康扫描里
   **天然就有 19 次注入请求被 4xx 拒**，只看被拒条数的判据会当场打它。
   ⇒ 安全边际来自 `baselineOk===0` / `injectOk===0` 这两条"另半边"，**不是**来自 8 或 2；
   那两个数的作用只是"多快停手"。据此保留 8 / 2（B/C 分别在第 13、11 条请求处停住，
   相对整轮 83 条已是早停，没有再压的必要）。
2. **反证接线不是空转**：把 `getScanClient` 里的变换层摘掉（`if (false && transformActiveForScan(...))`）
   重跑本套件 ⇒ **6 条断言变红**，且五个场景全部退化成"11 请求 / 0 检出 / verdict=未检出"——
   正是 D 场景钉的那个失效形状。还原后回到上表。

### 8.1 另两族（D35 补）：整包 AES 与 timestamp+nonce

| 族 | 场景 | 实测 |
|---|---|---|
| 整包 AES（`/api/enc`，POST 报文里**只有一个叶子是密文**） | 不带脚本 | 0 检出 + `verdict=no_vulnerability_detected`（4 次解密失败）⇐ 与签名族同一种静默假阴性 |
| | 正确脚本（把该叶子加密回去） | 86 请求、检出 1、注入抵达 SQL 76 次 |
| | 漏覆盖该字段（透传不加密） | 94 请求、84 次解密失败、`transform_rejected(kind=injection)`、`inconclusive` |
| 防重放（`/api/tick`：时钟窗 + 一次性 nonce + 三者参与 sign） | 每条现算 | 检出 3、nonce 复用拒 0；**靶站自证**：同一份合法报文连发两次，第二次必被拒 |
| | 沿用抓包时的过期时钟 | `transform_rejected(kind=baseline)`、早停（11 请求 vs 健康 83） |
| 利用阶段组合 | 正确脚本 + `--dbs --current-db` | 被拒 **0** 次、注入抵达 67 条 ⇒ `Exploiter`（复用 `Extractor._send`）确经 per-scan 视图；此前这只是"结构上应该" |

**判据可达性（D35 挖出的真问题，比多两族靶点更值钱）**：加密族第一版整轮只发 5 条请求，
`transform_rejected` 永不成立 —— `prefilter` 的"输入校验甄别"（基线 200 + 四路探针同构 400 且无 SQL 报错签名
⇒ 判为参数在进 SQL 前被白名单拦死）把唯一的注入点剪了。可在签名/加密目标上，那个"同构 400"
**就是**签名没覆盖的定义。⇒ 现规则：**启用请求变换时停用这条剪枝**（未启用时行为逐字不变，
差分单测两侧都钉）。所以 §8 上面第 1 条要补一句前提：安全边际来自 `injectOk===0` 那半边，
而**前提是有足够样本** —— 早剪的目标上阈值 8 本身不可达。

⚠️ 另一条既有限制：早停粒度是**点边界**（`scan/detect.js` 在每个点开始前判 `shouldAbort`），
单点目标内部几十上百条请求无从打断。所以"签名被拒能省多少预算"只在 ≥2 个注入点的目标上成立。

### 附：第一版靶站把自己的靶点剪掉了（prefilter 的正确行为）

第一版 `/api/item` 用 `500 + {"error":"unrecognized token: \"X\""}` 回显 SQL 错误，
结果 A 场景 0 检出、只发了 12 条请求。查下来是 `prefilter` 把两个靶点都"安全跳过"了，
实测其判据 `prefilterSimilar(单引号探针, 良性非法值探针) === true`：
SQLite 的错误文本只回显肇事 token，`unrecognized token: "'"` 与 `unrecognized token: "1zz9qx0"`
在它眼里同构 ⇒ 判为"是输入白名单在报错，不是 SQL 报错"。

**prefilter 没错，是靶站不像真实可注入目标**（那种报错确实是弱信号）。改成 sqli-labs 的形态
—— 200 页面内回显错误 —— 之后状态码不 ≥400，不走那条甄别（见 `prefilter.js` 的 OPT-FIX#2 口径），
完整检测照常执行，A 场景 3 条检出。

⇒ 给本仓加新靶点时的必查项：**先确认 prefilter 不会把你的靶点判成"输入校验"**，
否则第一个结论会是"工具 0 检出"，而该修的是靶站。
