## 一、monitorEventLoopDelay（事件循环滞后直方图）—— Windows / Node 24 实测

实测环境：本机 Windows，Node v24.20.0，`monitorEventLoopDelay({ resolution: 20 })`。
探针脚本（逐火逐值观察，2026-11-23，已随 D316 清理；复现方法见文末）：

| 场景 | 实测行为 | 对判据的含义 |
|---|---|---|
| 闲置观察 | 每次观察记录 ~30ms 滞后（有效观察间隔 ≈ 2×resolution，uv 定时器合并） | **闲置即有 ~30ms 本底**：`maxMs > 0` 不代表「发生了长条」，只代表「观察在流动」 |
| 同步长条 800ms（定时器回调上下文） | 首个观察如实记录 **815ms** | 长条幅值可以如实入账 |
| 同步长条 120ms（定时器回调上下文） | 首个观察 138.7ms（入账）✓ | — |
| 同步长条 120ms（inline 异步续体上下文） | 只有 ~32ms 本底，**长条幅值未入账** ✗ | 幅值是否如实记录**取决于阻塞发生所在上下文** |
| 同步长条 300/500ms（定时器回调上下文） | 分别只记 32.2 / 31.8ms（吞记）✗ | **幅值断言（≥ 长条时长-分辨率）在该平台不可靠** |
| 阻塞结束后首次落账时机 | 阻塞结束后 30~60ms 才落账 | 「阻塞后立即采样一次」的写法在忙机器上必然偶翻（D236 集成用例的 CI 红点根因） |

**推论（已写入 `eventLoopWatch.js` 口径注释与 D316 CHANGELOG）**：
- 跨平台稳定可断言的只有「**观察恢复流动**」（maxMs > 0）+ 有界轮询等落账；
- 幅值级断言（≥ 长条时长 - resolution）只在部分上下文成立，**不得**跨平台使用；
- Windows 上 `/api/health` 的滞后读数请当「存在明显长条」的强信号解读，勿当幅值。

## 三、判据标定守则（写时序敏感断言前先读）

1. **墙钟不当活性上限**（本仓既定纪律）：`Date.now()` 差值只可用于「宽松上限」
   （防挂死外闸），不得用于「必须等于/大于某值」的正向判据。
2. **事件循环滞后**：只断言「观察恢复流动」+ 有界轮询等落账；幅值断言需先在本表
   确认该平台/上下文已实测可靠，否则改用其它信号。
3. **外部依赖（DNS/网络/端口）不得进覆盖率跑批**：参考 D317 对 `exploitRoutes.validation`
   的处理——用既有缝（dnsCache / 注入点）预置确定性输入，真网冒烟单独登记。
4. **阈值按档标定**：一个常数只对它标定时所在的余量/规模档成立；跨档复用前先算
   「正常值与阈值的最小间距」，必要时参数化（参考 D316 slowWallMs + 真值表钉住）。
5. **单抽翻面 ≠ 回归**：先看本表已知家族 + 同码 schedule 轮是否绿，再定性；
   定性为环境的按上述既定处置修复，不许静默重跑洗绿。
